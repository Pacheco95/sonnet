# ADR-0012: GPU-driven culling and indirect draws

- **Status:** Accepted, amended by [ADR-0014](0014-indirect-draws-without-count.md)
- **Date:** 2026-09-20

## Context

M3 measured the engine against the README's target with `renderer_tests "[benchmark]"`: ten thousand draws and a hundred lights at 1080p on an RTX 4090 cost about 1.1 ms of GPU time and about 95 ms of CPU time ([roadmap.md](../roadmap.md#m3-assets-and-pbr)). The gap is entirely in recording: six passes — four shadow cascades, the depth pre-pass and the forward pass — each walk the same ten thousand draws and record `push constants, bind index buffer, draw indexed` per draw, and the editor adds the id pass on top. The GPU is idle waiting for the command buffer.

The draw loop is already close to indirect submission ([rendering.md](../rendering.md#frame-structure)): per-object data lives in a storage buffer addressed by an index, materials and textures are bindless, and vertices are pulled through a buffer device address rather than a vertex input state. Two things still vary per draw on the CPU: the push constants, which carry the object index and the mesh's vertex address, and the bound index buffer, which an indirect draw cannot change.

The open question the roadmap left is that last one. Either every mesh's indices move into a shared arena, leaving one call per pass, or one indirect call is issued per distinct mesh, which collapses ten thousand calls into a few dozen.

## Decision

- **One indirect call per batch, where a batch is a run of draws sharing a pipeline and a mesh.** The renderer already sorts the opaque draws by double-sidedness and then by mesh so index-buffer binds are rare; those runs become the batches. Recording a pass is then `bind pipeline, bind index buffer, drawIndexedIndirectCount` per batch — a few dozen calls for a scene of a few dozen meshes, two for the benchmark, instead of ten thousand. Meshes keep their own index and vertex buffers, so mesh creation, destruction and the skinning path are untouched.
- **The object index travels in `firstInstance`.** `VkDrawIndexedIndirectCommand` has no room for engine data, but `firstInstance` reaches the vertex shader as `SV_StartInstanceLocation` and nothing else uses instancing. The culling shader writes the draw's object index there, and the direct path passes the same value to `drawIndexed`, so the scene shaders have one way of finding their object and no indirect-only variant exists.
- **The mesh's vertex address moves from the push constants into `ObjectData`.** The object array is already indexed per draw and already written once per frame, so this costs nothing and leaves the per-draw push constants empty. What remains in them is the cascade index, which is uniform over a shadow pass and is pushed once per pass.
- **Culling is a compute pass per drawing pass, over a per-frame array of cull inputs.** One `cull.slang` dispatch per pass tests each draw's world-space bounds against that pass's frustum, derived in the shader from the pass's view-projection matrix, and appends a command for a survivor into its batch's range of a device-local command buffer, bumping that batch's counter atomically. The shadow cascades, the depth pre-pass and the forward pass share one cull input array and differ only in the matrix they are given; the id and selection-mask passes have a second array. A pass that draws nothing after culling submits a count of zero rather than being skipped, so the graph's pass list does not change with the camera.
- **Frustum culling only, on axis-aligned bounds.** No occlusion culling, no two-phase depth pyramid, no per-cluster or meshlet subdivision. Those are the next steps if a benchmark asks for them, and none of them changes the interfaces this ADR settles.
- **The renderer derives world-space bounds; `world` is unchanged.** The renderer already holds every mesh's object-space bounds and the draw's transform, and it already walks the draw list once per frame to fill the object array. Deriving the world-space box there keeps the knowledge in one place and gives every producer of a `DrawItem` — `world`, the editor, the tests — culling without a change. The roadmap put the bounds on `DrawItem`; that would have needed a sentinel for the items that carry none and a second path in the renderer for them, which is worth more than caching a box behind a transform that mostly changes anyway.
- **Blended draws keep the CPU loop.** Their order is view-dependent and back to front, which is a sort, not a filter, and sorting on the GPU is a milestone of its own. They are also the draws a scene has fewest of, and none of the six passes the measurement blamed draws them. The forward pass therefore records its opaque draws indirectly and its blended draws directly, with the same pipelines and the same shaders.
- **`rhi` gains exactly what this needs**: a `BufferUsage::Indirect`, the `DrawIndirect` stage and `IndirectCommandRead` access for the barrier, an `IndirectCommand` struct matching Vulkan's, and `ICommandList::drawIndexedIndirectCount`. The count form subsumes the plain one, and nothing here dispatches indirectly, so neither `drawIndexedIndirect` nor `dispatchIndirect` is added ([conventions.md](../conventions.md), nothing ahead of need).

## Consequences

- Recording a scene pass stops scaling with the draw count and starts scaling with the mesh count, which is the milestone's criterion. The per-frame object-array fill still walks every draw once on the CPU; M7 removes the recording, not that loop, and M8 is where it would be spread over threads if it still matters.
- Culling moves off the CPU entirely, and it is now done per pass rather than not at all: each shadow cascade sees only the casters its own frustum holds, which the CPU path never bothered to work out.
- The command and count buffers are device-local, rewritten every frame and read by the previous frame's draws, so they need the same barriers on both sides that the light clusters already have. They are sized from the frame's draw count for the six opaque jobs and the two editor jobs, and grown by recreation when the scene grows.
- Every scene shader loses its `draw.vertices` and `draw.objectIndex`, so `depth.slang`, `forward.slang` and `id.slang` change together with `sonnet.slang`. The shaders that do not draw objects — the skybox, the post passes, the outline, the debug lines and the skinning — are untouched.
- `drawIndirectCount`, `drawIndirectFirstInstance` and `multiDrawIndirect` become required device features. All three are core Vulkan 1.2 or earlier, supported by every desktop driver, by Lavapipe and by MoltenVK, so the 1.4 baseline of [ADR-0001](0001-vulkan-1.4-only.md) already guaranteed them.
- The null device's trace grows a `drawIndexedIndirectCount` line, so the tests above `rhi` assert on the number of indirect calls a pass makes rather than on ten thousand `drawIndexed` lines. What a pass actually draws is no longer visible to them, which is why the GPU tests on Lavapipe — the lit box, the shadow, the picked box, the outline — become the ones that prove culling keeps the right things.
- A draw whose bounds are wrong now disappears instead of being merely slow, which makes bounds a correctness concern. A skinned mesh is culled by its bind-pose bounds transformed by its object's matrix, so a pose that reaches far outside them can be culled early; widening those bounds is deferred with the rest of the skinning work.

## Alternatives considered

- **A shared index and vertex arena, one call per pass**: the endpoint every GPU-driven renderer reaches, and it makes the pass count independent of the scene. It needs a suballocator with a free list, chunking or reallocation as meshes come and go, and a copy path for growth, all of which is machinery in service of turning a few dozen calls into one. The batching above already collapses the cost by three orders of magnitude; the arena is what M8 or later builds if the mesh count ever becomes the bottleneck.
- **Instance data in a per-draw storage buffer indexed by `SV_InstanceID` instead of `firstInstance`**: avoids relying on `drawIndirectFirstInstance`, but `SV_InstanceID` restarts at zero per command, so the shader would need a second indirection the command cannot carry.
- **No count buffers: a fixed command slot per draw with `instanceCount` set to zero when culled**: no atomics, no counters and no clearing dispatch, but the GPU then walks every command of every pass and culling saves only the rasterisation, not the command fetch. The counter is one dispatch and one buffer.
- **One cull dispatch for all passes, writing every pass's commands at once**: fewer dispatches, but the id and mask passes are declared by the editor after the scene passes and would have to be known in advance, and the frustums would have to be gathered into a buffer instead of push constants.
- **Culling on the CPU, keeping direct draws**: the cheapest change, and it would cut the benchmark because most of the ten thousand draws are off screen for the cascades. It does nothing for the case the target actually describes, where the draws are visible, and it leaves the recording cost in place.
- **Bounds on `DrawItem`, filled by `world`**: lets the world cache a box until a transform changes, and would eventually let a skinned mesh report the bounds of its pose. It puts the same mesh bounds in two modules and needs every other producer of draw items to fill them or opt out.
