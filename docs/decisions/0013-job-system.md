# ADR-0013: The job system and who runs on it

- **Status:** Accepted
- **Date:** 2026-09-20

## Context

More of the engine waits on a job system than on anything else. Asset loading is synchronous, so opening a project stalls the frame that asks for a mesh. Jolt runs on `JobSystemSingleThreaded` because there was nothing else to give it ([ADR-0009](0009-physics-and-scripting.md)). `world` never uses flecs' multi-threaded pipeline. The renderer's per-frame object, material and light upload is, since M7 removed the recording cost, the larger part of what a frame costs on the CPU: 0.26 ms of the 0.28 ms the six scene passes spend ([roadmap.md](../roadmap.md#m7-gpu-driven-rendering)).

M7 also answered what does *not* need threads. Multi-threaded command recording was the obvious candidate before GPU-driven submission; recording a scene pass is now a handful of calls, so there is nothing there to spread.

The engine has one process-wide resource to spend — the machine's cores — and three clients that want it: flecs' pipeline, Jolt, and the engine's own parallel loops. How they share it is the decision, because the obvious arrangement deadlocks. flecs offers "task threads" (`ecs_set_task_threads`) explicitly as the hook for "an asynchronous job system rather than long-running threads", which reads like an invitation to run flecs' stage workers as jobs. It is a trap:

- `ecs_run_pipeline` creates task threads on entry and joins them on exit, on **every call** (`src/addons/pipeline/pipeline.c:533,542`).
- A task thread runs `flecs_worker`, which blocks on a condition variable for the whole pipeline run (`src/addons/pipeline/worker.c:80-103`).
- `World::progress` makes up to six `run_pipeline` calls per frame — input, `FixedUpdate` once per fixed step, then the frame pipeline (`modules/world/src/World.cpp:440`).

So running flecs' stage workers as jobs would, on every pipeline run, occupy every worker in the pool with a thread that is blocked rather than working. During the `FixedUpdate` pipeline — which is where `PhysicsStep` lives — Jolt would queue jobs that no worker can pick up, and `JobSystemWithBarrier::WaitForJobs` would drain them on the calling thread. Physics would stay single-threaded, which is the thing this milestone exists to fix. The only per-pipeline control flecs offers is `ecs_set_task_threads`, and `ecs_set_stage_count` has no early-out (`src/stage.c:198`), so it cannot be toggled per pipeline per frame without freeing and reallocating every stage and its allocators.

## Decision

- **`core` owns one job system, `core::JobSystem`, and it is the only thread pool the engine schedules work on.** It has a fixed set of worker threads, `std::thread::hardware_concurrency() - 1` by default, named and carrying Tracy zones. `schedule` takes a callable and the handles it depends on and returns a handle; `wait` blocks until a handle is done and runs other jobs while it waits, so a job may wait on its children without deadlocking the pool. `parallelFor` splits a range into grains across the workers and waits. There is one implementation, so the type is `JobSystem`, not `IJobSystem` ([conventions.md](../conventions.md#code-style)).
- **The main thread is a place jobs can ask for, not a worker.** A job scheduled with main-thread affinity is queued separately and run by `runMainThreadJobs`, which the application loop calls once per frame. This is what lets an asset load finish on the thread that owns the `rhi` device, since recording an upload is not thread-safe ([rendering.md](../rendering.md#frame-structure)).
- **A flecs stage worker never runs on the pool.** It blocks for the length of a pipeline run rather than running to completion, so occupying a worker with one is the category error the Context describes. Should `world` ever be threaded, it is through `ecs_set_threads`, which creates flecs' own stage workers once (`src/addons/pipeline/worker.c:113-116`) and leaves `ecs_run_pipeline` neither creating nor joining them, both sites being guarded on `ecs_using_task_threads`. `ecs_set_task_threads` is never called.
- **`world` is not threaded in this milestone, and the reason is the shape of its systems rather than the cost of threads.** flecs splits a system across stages only when it is marked `multi_threaded` (`addons/system.h:97`), and `ecs_worker_next` gives every worker a slice of each matched table while all of them walk the same table sequence with no barrier between tables (`src/iter.c:963`). What that leaves:
  - `TransformSystem` may **not** be marked `multi_threaded`. It depends on `cascade()` to write parents before children, and two workers may be on different tables at the same instant, so a child could read a parent's matrix before it is written.
  - `immediate` and `multi_threaded` are mutually exclusive (`addons/system.h:99-101`), which excludes `AnimationPlayback`, `SkinPalette` and `ScriptUpdate` as they are written. `ScriptUpdate` holds a Lua state and `Audio` a miniaudio device; neither would be marked anyway.
  - What remains is `SpinSystem`, which exists for a sample.

  Stage workers pay off when a phase holds many independent systems that can each be split. This engine has few systems, and the one that would benefit at scale is the one `cascade` excludes. Making the hierarchy parallel needs a dispatch per depth level with a barrier between levels — which flecs cannot express *within* a system, and which `parallelFor` expresses directly. So the tool that engine will reach for when `TransformSystem` is restructured is the pool, not the stages, and building the stages now would add N-1 threads to every `World`, and flecs' stricter multi-threaded readonly mode to every system, in service of a system that exists for a sample.
- **Parallelism inside `world` is a `parallelFor` in the system that needs it, measured first.** A system that only writes components of the entities it matched, with no structural change, is safe to split without stages. That is the form `TransformSystem` would take, per depth level, if it measures hot enough to be worth the barrier.
- **`physics` implements `JPH::JobSystem` on `core::JobSystem`**, deriving from `JobSystemWithBarrier` so Jolt's barriers and dependency counting stay Jolt's, and implementing `QueueJob`, `QueueJobs`, `FreeJob` and `GetMaxConcurrency` over the pool ([ADR-0009](0009-physics-and-scripting.md) said this is where it would go). It replaces `JobSystemSingleThreaded`. Because the `FixedUpdate` pipeline holds no flecs stage workers under the decision above, Jolt has the whole pool for the length of a step.
- **`assets` gains a request form beside the loading one, not instead of it.** `requestMesh` and its siblings return at once: the asset if it is loaded, otherwise a placeholder handle and a job that imports on a worker. Importing is CPU work — parsing, decoding, mip generation — and ends in a main-thread job that creates the renderer resource and publishes it under the identity. Callers already resolve identities through the database every frame ([assets.md](../assets.md#database)), so a request that completes reaches the next frame with no one holding a stale handle. The synchronous form stays, because the cook tool and the tests want a load that has finished when it returns.
- **The renderer's per-frame upload is a `parallelFor`.** Filling `ObjectData` per draw and the cull candidates per batch are indexed loops over the frame's draw list with no dependencies between iterations, which is what `parallelFor` is for. Materials and lights are bounded by `MaxLights` and the material count and stay on the calling thread.
- **A `linux-tsan` preset**, since `linux-asan` is address and undefined-behaviour only and nothing in the engine has run under a thread sanitizer.

## Consequences

- There is one pool to size, one place where worker threads are named, and one set of Tracy zones for them. A second pool arriving later — for audio decoding, say — would be a decision to revisit, not a detail.
- Physics scales across cores for the first time. The gain is bounded by what Jolt can parallelise in a step, which is broad-phase and the solver's islands; a scene with one island scales no better than it does today.
- Asset loading stops stalling the frame that asks, at the cost of a frame or more showing a placeholder. Every caller of the request form has to be able to draw nothing for that asset, which the draw list already does for a mesh that failed to import.
- The engine now has threads that outlive a frame, so teardown order matters in a way it did not: the job system is destroyed after the subsystems that schedule onto it, and `World` releases flecs' threads before the pool it named them beside.
- Running under a thread sanitizer is now part of what CI means by passing, and tsan will find races in code that has been correct only because it was single-threaded. That is the point, and it is why the preset lands with the job system rather than after it.
- `world` is unchanged by this milestone, and every `World` stays single-threaded and free of stage workers. The prize — a parallel `TransformSystem` over the whole hierarchy — is deferred until a benchmark asks for it, and is a restructure of that system around `parallelFor` rather than a flag on it.
- Nothing in the engine calls `ecs_set_threads` or `ecs_set_task_threads`, so the Context's analysis is what stops the next person reaching for task threads and quietly starving physics. That is the durable half of this ADR.
- Jolt's own thread pool, `JobSystemThreadPool`, is never constructed, so the process has no threads the engine did not create.

## Alternatives considered

- **flecs' stage workers as jobs, through `ecs_set_task_threads`**: the arrangement flecs' documentation suggests, and the one the roadmap implied. It starves Jolt for the length of every `FixedUpdate` pipeline run, for the reasons in the Context, and the per-pipeline escape hatch reallocates every stage on each toggle.
- **flecs stage workers now, through `ecs_set_threads`, with the safe systems opted in**: honours the milestone's original plan and puts the machinery in place for later. Rejected because the machinery would be unused: the systems that can opt in amount to `SpinSystem`, while every `World` would carry N-1 threads and every system flecs' stricter multi-threaded readonly mode. When `TransformSystem` is eventually made parallel it will want a barrier between depth levels, which the stages cannot express, so the machinery would still be unused afterwards.
- **flecs' pipeline for the command merging alone**: flecs' pipeline is what maintains a command queue per stage and merges them at sync points, which hand-rolled parallel iteration would have to do itself. It does not apply to the systems in question: a system that only writes components of the entities it matched makes no commands to merge, and one that makes them is one that may not be split anyway.
- **Jolt on `JobSystemThreadPool`**: Jolt's own pool, and the least work. It puts a second set of threads in the process that the engine does not size, name or profile, and ADR-0009 already said physics would move onto the engine's system once there was one.
- **A work-stealing deque per worker**: the standard answer for a job system, and what the engine would need if jobs spawned jobs deeply. Every client here schedules a wide, shallow batch from one thread — a physics step, a parallel for, a set of imports — which a shared queue serves without the per-worker machinery. The interface does not change if this is revisited.
- **Making the pool elastic, so a blocked worker is replaced**: would let flecs' stage workers run as jobs after all, since a blocked one would no longer count against the pool. It makes the worker count a moving target, which is exactly what the sanitiser preset and Jolt's `GetMaxConcurrency` want to be fixed.
- **A simulation thread running `World::progress` alongside the render thread**: the other way to use a second core, and a much larger change. It requires the world to be double-buffered or the draw list to be snapshotted, which is a milestone of its own and not what the measurements ask for.
