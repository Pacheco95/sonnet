# ADR-0018: Mobile export: builds, ASTC, packaging and device checks

- **Status:** Proposed
- **Date:** 2026-09-23

## Context

M9 puts the player on Android and iOS ([roadmap.md](../roadmap.md#m9-mobile-export)): an NDK build packaged as an APK, an Xcode build on MoltenVK packaged as an app bundle, ASTC textures, touch input and the OS-owned loop, done when the basic sample runs on an Android 16 device and an iOS device. [ADR-0001](0001-vulkan-1.4-only.md) settles the floor: Vulkan 1.4, which Android guarantees on devices launching with Android 16, and MoltenVK on iOS. The engine already runs on SDL3's callbacks ([platform.md](../platform.md#lifecycle)), so the loop is not the problem. What the repository and vcpkg say today:

- **Two ports in `vcpkg.json` refuse the mobile triplets.** A dry run of `vcpkg install` with the manifest as it is stops on `shader-slang`, which supports only `(arm64 | x64) & (linux | osx | windows)`, for both `arm64-android` and `arm64-ios`, and on `vulkan-loader`, which supports `!android`. Nothing else fails the `supports` check. Slang is needed in two places: `slangc` compiles the shaders at build time, and `assets::ShaderCompiler` links the library, which only the editor's shader hot reload calls. No module links `vulkan-loader`; SDL loads the Vulkan library at run time. With `shader-slang` declared as a host tool plus a desktop-only target entry, and `vulkan-loader` and `imgui` restricted to desktop, both mobile dry runs get past the `supports` check and stop at compiler detection, which needs the NDK or Xcode. Neither is on this machine.
- **`vulkan-memory-allocator-hpp` depends on the `vulkan` stub port**, which on every platform but Android depends on `vulkan-loader` and runs `FindVulkan` at install time. Its CMake config needs nothing from either: it is an include directory. On iOS that means vcpkg builds a Khronos loader the engine will not link.
- **ASTC needs no new library.** The `ktx` port keeps KTX-Software's vendored astc-encoder (the portfile excludes `astc-encoder` from the vendored libraries it deletes), and the installed `libktx` exports `ktxTexture2_CompressAstcEx`, with block sizes from 4×4 to 12×12, a quality level, a normal-map mode and a perceptual mode, and `ktxTexture2_DecodeAstc`. On x64 it builds astcenc as `KTX::astcenc-avx2-static`. The Basis transcoder the engine already calls can also transcode UASTC to `KTX_TTF_ASTC_4x4_RGBA`.
- **The engine knows sRGB or linear per image, not normal map or colour.** `TextureSettings` holds `srgb`, `mipmaps` and `compress`, and the glTF importer sets `srgb` from how materials use an image. `forward.slang` reads a normal map's `xyz`, so astcenc's normal-map mode, which keeps two channels and leaves Z to the shader, would need a shader change.
- **No GPU on hand samples ASTC.** Lavapipe and the RTX 4090 both report `textureCompressionASTC_LDR = false` (and `textureCompressionBC = true`), so an ASTC upload can be tested only on Apple silicon or a phone.
- **There is no `moltenvk` port** at the baseline. Khronos publishes release archives: v1.4.2 (2026-07-24) has `MoltenVK-ios.tar` with a static `libMoltenVK.a` and a dynamic framework in `ios-arm64` xcframeworks, device only, minimum iOS 15. The static library exports `vkGetInstanceProcAddr`, `vkCreateInstance` and `vkEnumerateInstanceExtensionProperties`, and does not contain the string `VK_KHR_portability_enumeration`, which is the loader's extension. On iOS, SDL3 first looks for `vkGetInstanceProcAddr` in the process with `dlsym(RTLD_DEFAULT, ...)`, "the case where Vulkan Portability is linked statically", and only then for a bundled `libvulkan.dylib` (`SDL_uikitvulkan.m`). vk-bootstrap adds the portability enumeration extension and flag only when the instance offers them.
- **An APK can be built without Gradle.** SDL3's CMake builds its test APKs with the SDK's build tools alone (`aapt2`, `d8`, `zipalign`, `apksigner`, `keytool`), through functions in `cmake/android/SdlAndroidFunctions.cmake`. The vcpkg port does not install those functions or SDL's Java sources. It builds `SDL3.jar` only if Java and an Android platform are found while the port builds. The Java glue has to match the native library's version, since it is JNI. `SDLActivity` is meant to be subclassed: `getLibraries()` names the shared objects to load (by default `SDL3` and `main`), and `getArguments()` supplies the native arguments (by default none).
- **An APK's files are not files.** The player finds `game.sbundle` and `shaders/` beside itself through `std::filesystem` and `std::ifstream` (`Bundle`, `core::readFile`, `Renderer`). On Android those would be in the APK's `assets/`, where only the asset manager can reach them. `SDL_IOFromFile` opens a relative path from the app's internal storage and then from the APK's assets, and supports seeking there (`AAsset_seek64`).
- **Mobile lifecycle events arrive in `SDL_AppEvent` synchronously** with the main callbacks, which SDL documents as the reason those events need no event watch. `platform` does not translate them yet, nor any touch event. SDL synthesises mouse events from touches by default (`SDL_HINT_TOUCH_MOUSE_EVENTS`). On Android the window's surface goes away when the app is backgrounded, and iOS does not allow GPU work from a background app.
- **The editor's `--screenshot` capture lives in `editor`** (`Capture.cpp`, the readbacks in `Editor.cpp`), so the player cannot capture.

## Decision

### Builds

- **Four presets, `android-debug`, `android-release`, `ios-debug` and `ios-release`**, as [build.md](../build.md#presets) already names two of them. They build the player alone: `SONNET_BUILD_EDITOR` is forced off (so `ui`, `editor` and `apps/cook` are not built) and `SONNET_BUILD_TESTS` is off, since a device cannot run `ctest`.
  - Android uses Ninja and vcpkg's `arm64-android` triplet, chain-loading `$env{ANDROID_NDK_HOME}/build/cmake/android.toolchain.cmake` through `VCPKG_CHAINLOAD_TOOLCHAIN_FILE`, with `ANDROID_ABI=arm64-v8a` and `ANDROID_PLATFORM=android-36`, which is Android 16. The triplet builds the ports against API 28, and a library built for a lower API level links into an app with a higher one. arm64 is the only ABI.
  - iOS uses the Xcode generator with `CMAKE_SYSTEM_NAME=iOS`, `CMAKE_OSX_ARCHITECTURES=arm64` and vcpkg's community `arm64-ios` triplet. The deployment target is the lowest iOS whose libc++ has everything the engine calls (see Open questions). Xcode signs and installs the app, and the generator is what lets it.
  - Both triplets link statically, so the player is one shared library on Android and one executable on iOS.
- **The manifest changes, and no registry port is patched for the target.**
  - `shader-slang` is declared twice: with `"host": true` for `slangc`, which `cmake/SonnetShaders.cmake` then finds under the host triplet, and with `"platform": "!android & !ios"` for the library.
  - `vulkan-loader` and `imgui` get `"platform": "!android & !ios"`.
  - `vulkan-memory-allocator-hpp` gets an overlay port whose only change is to depend on `vulkan-headers` instead of the `vulkan` stub, as the `imgui` overlay already does for its Vulkan binding, so no loader is built for iOS and the stub's `FindVulkan` never runs. The overlay is needed only if the iOS install fails without it, which is the first thing to check (see Open questions).
- **`ShaderCompiler` moves from `assets` to `editor`.** The editor is its only caller, so `assets` stops linking Slang and nothing below `editor` does. The dependency rule is untouched, since a module only loses a dependency, and there is no `#if`: the mobile build never adds the module that needs Slang.
- **The rest of the dependency set is expected to build as it is**, on the evidence of the port files rather than a build: `sdl3`, `flecs`, `joltphysics`, `lua` (the port's own `CMakeLists.txt` defines `LUA_USE_IOS`, and Lua 5.5.1's `loslib.c` uses it to stub out `system`, which iOS does not have), `miniaudio`, `ktx` (the registry port carries `0006-fix-ios-install.patch`), `fastgltf`, `simdjson`, `spdlog`, `tracy`, `glm`, `vk-bootstrap`, `nlohmann-json`, `sol2` and `stb`. A port that fails gets an overlay under `ports/`, described in `ports/README.md`.

### Textures

- **A mobile bundle's textures are ASTC, encoded by the cook with KTX-Software.** `CookPlatform` gains `android` and `ios`, and `sonnet_cook --platform android|ios` and the export dialog take them. For these platforms the cook encodes each compressed texture's decoded RGBA8 mip chain with `ktxTexture2_CompressAstcEx`, into a KTX2 file whose `vkFormat` is ASTC. It does not re-encode the UASTC it cached, which would stack two lossy encodings. The payload is still "a KTX2 file", as [ADR-0011](0011-cooked-bundles-and-the-player.md) defines it, so the bundle format does not change.
- **The block size follows the colour space the importer already records.** An sRGB texture (base colour, emissive) is 6×6, 3.56 bits per texel, in perceptual mode. A linear texture (normals, metallic-roughness, occlusion) is 4×4, 8 bits per texel, the same as BC7 on desktop, because its error turns into shading error rather than colour error. The quality level is `MEDIUM` for both. The normal-map mode is not used, since `forward.slang` reads three channels. An uncompressed texture (`compress` off) stays RGBA8, and the environment map stays RGBA16F, as ADR-0011 already accepts.
- **The encode is cached like the UASTC one**, as `.sonnet/cache/<uuid>.astc.ktx2` under the same rule for freshness, so a second mobile export does not encode again. The two mobile platforms cook the same texture bytes.
- **One bundle per platform, as today.** The manifest's `platform` says which. `rhi` gains the ASTC 4×4 and 6×6 formats in sRGB and UNORM, and `DeviceInfo::astcSupported` for `textureCompressionASTC_LDR`, which is enabled where present, the way `blockCompressionSupported` is. `readKtx2` uploads an ASTC file as it is. A texture in a format the device cannot sample is an error when it loads and falls back like a failed import. `Game::open` refuses a bundle cooked for a platform whose formats the device lacks, and names the platform. Transcoding UASTC keeps its targets: BC7 with block compression, and ASTC 4×4 in place of RGBA8 where the device has ASTC but no BC. The second is one line and removes the 32-bit-per-texel fallback on phones.

### Packaging

- **The APK is built by CMake with the SDK's build tools, not Gradle.** `cmake/SonnetAndroid.cmake` adapts SDL's `SdlAndroidFunctions.cmake` (zlib licence, attributed in the file) into a `sonnet_add_apk(<target>)` function: it compiles the resources and `AndroidManifest.xml` with `aapt2`, compiles SDL's Java glue and one activity with `javac` against the platform's `android.jar`, dexes them with `d8`, zips in `lib/arm64-v8a/libsonnet_player.so` and, stored uncompressed, `assets/game.sbundle` and `assets/shaders/`, aligns with `zipalign` and signs with `apksigner`. The tools come from `ANDROID_HOME` and a JDK.
  - **SDL's Java glue comes from the `sdl3` overlay port**, which already exists and will install `android-project/app/src/main/java/org/libsdl/app/*.java` into `share/sdl3/android-java/` for Android triplets. The Java sources then always match the native library they were built with.
  - **`SonnetActivity` subclasses `SDLActivity`**, in `apps/player/android/`, beside the manifest and the icon. `getLibraries()` returns `sonnet_player` alone, since SDL is linked into it statically, and `getArguments()` reads a string extra from the launch intent, so a device run takes the same arguments as the desktop player.
  - **The manifest** sets `minSdkVersion` and `targetSdkVersion` to 36, and requires `android.hardware.vulkan.version` at `0x404000` (1.4) with `required="true"`, so a device without Vulkan 1.4 cannot install the app.
  - **Development signing** uses a debug keystore that the build generates once under the build directory with `keytool`, as SDL's functions do. Release signing and Play Store bundles (AAB) are not part of M9.
- **The iOS app bundle is the player target built as a `MACOSX_BUNDLE`** by the Xcode generator. No Xcode project is checked in. `apps/player/ios/` holds `Info.plist.in` (bundle identifier, `UIRequiredDeviceCapabilities` with `arm64` and `metal`, a launch screen, orientations) and the launch storyboard. `game.sbundle` and `shaders/` are copied in as resources, where `Platform::basePath()` already points on iOS. Signing is Xcode's automatic signing with `CMAKE_XCODE_ATTRIBUTE_DEVELOPMENT_TEAM`. The team comes from the environment or a `CMakeUserPresets.json`, so none is committed.
- **MoltenVK comes from a new overlay port, `moltenvk`, and is linked statically.** The port downloads the pinned Khronos release archive by hash (v1.4.2 today) and installs the static library and its xcframework for `arm64-ios`. There is no loader on iOS: `vkGetInstanceProcAddr` is in the process, where SDL looks first, and vk-bootstrap asks for portability enumeration only when it is offered. The player links with `-Wl,-u,_vkGetInstanceProcAddr`, because nothing references the symbol at link time and the linker would otherwise drop MoltenVK's objects from the archive. `ports/README.md` gains a section for ports that are not patched copies of the registry.
- **Where the files are read from is `platform`'s business.** `Platform::openContent(relativePath)` returns a seekable read-only stream over `SDL_IOStream`. It reads the APK's assets on Android and ordinary files beside the binary elsewhere. `Bundle` reads its index and payloads through it, and the renderer loads its shaders through it. `core::readFile` stays for the desktop tools and the tests. Storing the two uncompressed in the APK means a payload read is a seek and a read, not an inflate.

### Where it lives

No module is added and the order in [architecture.md](../architecture.md#module-map) does not change:

- **`platform`** translates finger events into `TouchDown`, `TouchUp` and `TouchMotion` (finger id, position in window pixels) and the lifecycle events into `WillEnterBackground`, `DidEnterForeground`, `LowMemory` and `Terminating`. `InputState` keeps the active touches. SDL's synthesised mouse events stay on, so one finger works as the left button for scripts written against the mouse. `platform` also owns `openContent`, and on Android the log gains spdlog's logcat sink.
- **`rhi`**: `ISwapchain::suspend` releases the swapchain and its surface, and `resume` creates both again. While suspended, `acquire` returns nothing, as it does for a minimised window, so `Game::render` already knows what to do. The ASTC formats and `astcSupported` are also here.
- **`assets`**: the mobile cook platforms, the ASTC encode and its cache entry, and the loss of Slang.
- **`scripting`**: `input.touches()` returns the active touches, each with its id, position and this frame's motion.
- **`runtime`**: the capture moves here from `editor` (below).
- **`apps/player/main.cpp`** keeps the frame order and handles the lifecycle. On `WillEnterBackground` it waits for the device to go idle, suspends the swapchain and pauses the audio device. On `DidEnterForeground` it resumes both. These arrive inside `SDL_AppEvent`, before the OS takes the surface away.
- **`cmake/`** holds `SonnetAndroid.cmake` and the iOS bundle properties. `sonnet_add_executable` makes a `SHARED` library on Android, since SDL's Java side loads the player with `System.loadLibrary`. No engine module knows what an APK is.

### CI

- **An Android job** on `ubuntu-24.04` configures `android-release`, builds the player and the debug-signed APK, cooks the basic sample for `android` with the Linux `sonnet_cook`, packages it and uploads the APK as an artifact. [build.md](../build.md#continuous-integration) already promises this job. Nothing runs, since no emulator is known to offer Vulkan 1.4.
- **An iOS job** on the macOS runner configures `ios-release` and builds for the device with `CODE_SIGNING_ALLOWED=NO`, to prove that the player compiles and links against MoltenVK. There is no simulator run: the release's iOS archive has no simulator slice.
- **Linux tests cover everything but the GPU side of ASTC**:
  - an ASTC cook of each kind decoded back with `ktxTexture2_DecodeAstc` and held above a PSNR floor, on the basic sample's textures;
  - a mobile cook whose texture payloads are ASTC KTX2 and whose manifest names the platform;
  - `platform_tests` with synthetic SDL finger and lifecycle events, as the other events are tested;
  - `InputState` and `input.touches()`;
  - `ISwapchain::suspend` and `resume` on Lavapipe's headless surface;
  - `openContent` over plain files;
  - the player's capture flags, headless.

  The ASTC upload test skips without `astcSupported`, which is every Linux device, and runs on the Mac.

### Device checks and reports

- **The player gets the capture.** The readback and PNG writing move from `editor` into `runtime`, which `editor` already links, and both applications share the flag table and its parser. The player takes `--screenshot`, `--play`, `--scene`, `--shading-term` and `--settle-frames` with the editor's meaning: the fixed 1/60 s step, the seeded `math.random`, exit code 0 once the file is written and 1 with the reason in the log. `--screenshot-window` and `--select` stay in the editor, which has panels and a selection. A relative output path resolves against `Platform::prefPath`, the one writable place on a phone. A capture run also logs the device's name and Vulkan version, and the mean CPU frame time and GPU time per pass over its last hundred frames.
- **"Done" is the following, on one Android 16 device and one iOS device**, each on a player built by the preset and a bundle cooked for its platform from `apps/samples/basic`:
  1. The device's Vulkan description is recorded: `adb shell cmd gpu vkjson` on Android, and on iOS the device-selection log line. Every feature and limit in [rendering.md](../rendering.md#vulkan-baseline) must be present.
  2. The app installs and starts from its launcher icon and draws the start scene.
  3. A capture run of the start scene, `--play 3`, is taken for the `final`, `albedo` and `normal` shading terms, and one of the playground. Each exits 0 with no error and no warning in the log. The albedo and normal terms are the ones that caught MoltenVK's red-only colour reads ([ADR-0017](0017-depth-images-in-their-own-bindless-array.md)).
  4. The app is sent to the background and brought back. The log shows the swapchain suspended and resumed with no error, and the scene is still drawing.
  5. A finger held on the playground rolls the ball towards it, which `player.lua` gains alongside its keys.
  6. The frame times from step 3 are recorded in the roadmap beside the desktop and Mac numbers.
- **How a device's agent reports.** It runs the commands this ADR's implementation writes into [player.md](../player.md) (on Android `adb install`, `adb shell am start` with the arguments as an intent extra, `adb shell run-as <package> cat files/<name>.png`, and `adb logcat` filtered to the app; on iOS `xcrun devicectl` to install, launch with arguments and copy from the app's data container). It returns the PNGs, the log, the Vulkan description, the device model and OS version, and a line per check saying pass or fail. The PNGs are compared by eye with a Linux capture of the same arguments, not byte for byte, since the GPUs differ. That is how the Mac's captures were read. Checks 4 and 5 need a person's hand on the device, and the report says who did them.

## Consequences

- The player runs on the three desktop platforms and the two mobile ones from one source tree and one manifest. The only platform-specific directories are `apps/player/android` and `apps/player/ios`.
- The editor keeps shader hot reload, and `assets` gets lighter by one large library. Any other code wanting Slang at run time would have to live in `editor` or justify a module of its own.
- A mobile bundle's colour textures take less than half of BC7's memory and bandwidth, and its linear textures the same. [The per-frame fill](../roadmap.md#the-per-frame-fill-is-bandwidth-not-computation) showed this engine is bandwidth-bound where it is anything, and phones have less of it. The mobile cook is slower than the desktop one by the ASTC encode, once per texture thanks to the cache.
- ASTC on the GPU is tested only on the Mac and on devices. A regression in the upload path would pass Linux CI. The CPU decode test covers the encode, not the upload.
- iOS has no validation layers, because there is no loader to load them. Validation happens on desktop and on Android, where a debug APK can carry the layer. The same static MoltenVK would make the macOS export self-contained, closing the gap that an exported Mac game runs only where the SDK is installed. That is left for a change of its own, since the Mac editor still wants the SDK's loader for validation.
- Leaving Gradle out keeps one build system, and the APK is a CMake target a CI job or an agent can build with no IDE. It also means no Android Studio project, no dependency resolution for Java libraries, and no AAB. A game that wants the Play Store needs a Gradle wrapper later, and that would be a new decision.
- The adapted SDL functions are code the engine now owns. When SDL's build tools change, they are updated by hand.
- The player's capture makes a device run reproducible from a command line, and the remaining agent-driven checks follow the editor's screenshot rules. `runtime` gains stb's PNG writer.
- `ISwapchain` gains two methods that every implementation provides. The null device records them in its trace.

## Alternatives considered

- **Gradle and the Android Gradle Plugin, with CMake as `externalNativeBuild`**: the standard route, which gives Android Studio, AABs and Play signing. It adds a second build system with its own versions to pin, runs the native build and vcpkg under Gradle's control, and serves a release pipeline that M9 does not need. SDL's CMake-only APK build shows the smaller route works.
- **SDL's prebuilt Android archive (`.aar`)**: carries the Java glue and a shared SDL, but it is SDL from outside vcpkg, and a second copy of a library the manifest already provides, which [ADR-0004](0004-vcpkg-first.md) rules out.
- **UASTC in every bundle, transcoded to ASTC 4×4 on the phone**: no encoder and one bundle for every platform. Every texture costs 8 bits per texel, and the roadmap's "ASTC texture cooking" would really be transcoding. Kept as the fallback for a UASTC texture on a device without BC, not as the mobile format.
- **One bundle holding every platform's texture formats**: one cook for all targets, at the price of shipping formats a device never reads, which on a phone is download size. ADR-0011 already keys a bundle to one platform.
- **A block size per material slot instead of per colour space**: finer, and it needs a texture kind that the importer does not record today. The colour space draws the same line for the textures the samples use. A packed texture that should get a different size can wait for a sidecar setting.
- **ETC2 alongside ASTC**: Android GPUs that reach Vulkan 1.4 are expected to have ASTC LDR (checked per device in step 1), and Apple GPUs have it. A second format would be a second cook path for no device M9 targets.
- **MoltenVK from the Vulkan SDK for macOS**: the LunarG SDK is a developer install, versioned apart from the manifest, and not what CI has. A pinned release through a port gives every machine the same bytes and uses vcpkg's binary cache.
- **MoltenVK built from source in a port**: MoltenVK's build fetches its own copies of SPIRV-Cross and others through its scripts, which vcpkg cannot pin or share. The release binaries are what Khronos tests.
- **The Khronos loader and a dynamic MoltenVK framework, with an ICD manifest in the bundle**: keeps the layer mechanism on iOS, at the cost of embedding and signing two frameworks, and of a loader that the `vulkan-loader` port does not build for iOS without trying. Static linking is what SDL expects first.
- **Extracting the bundle from the APK to internal storage on first run**: keeps `std::ifstream`, doubles the storage the game takes, and slows the first launch. SDL already reads the APK's assets with seeking.
- **A `#if` around `ShaderCompiler` in `assets`**: breaks the rule that the device factory is the only switched site, to keep code in a module that does not use it.
- **The editor on mobile as well as the player**: rejected. The editor's shader hot reload needs the Slang library, which has no Android or iOS build. The editor is driven by mouse and keyboard: a right-drag fly camera, pixel-precise gizmo handles, Ctrl shortcuts and docked Dear ImGui panels. It also works on a project folder that it polls, and it opens scripts in an external editor, where a phone has an app sandbox and no such editor. The need behind the idea, seeing the game on a device while editing, is better met from the desktop editor by exporting to a connected device, which would be a decision of its own when a need for it appears.
- **No capture in the player, and screenshots taken with `adb exec-out screencap` or Xcode**: works for one look, but the frame taken is whatever is on screen at that moment, not a reproducible frame, and there is no equivalent that an agent can drive on iOS without a person.

## Open questions

What this ADR states but no one has checked on this machine, which has no Android SDK, NDK or `adb`, no macOS host and no device:

1. **Whether every port builds for `arm64-android` and `arm64-ios`.** The dry runs got past `supports` and no further. The first NDK and Xcode configures are the test. `tracy` and `miniaudio` on iOS are the likeliest to need attention (Tracy's network code, miniaudio's run-time linking of Apple frameworks).
2. **Whether the `vulkan` stub port installs for iOS**, which decides whether the `vulkan-memory-allocator-hpp` overlay is needed.
3. **The iOS deployment target.** Floating-point `std::to_chars`, which `std::format` needs, is believed to be available in Apple's libc++ from iOS 16.3; that is recalled, not read from the SDK here. The first build against the Xcode SDK says what the engine really needs. ADR-0001's iOS 15 is MoltenVK's floor, not the engine's.
4. **Static MoltenVK in practice**: that `-Wl,-u,_vkGetInstanceProcAddr` keeps the objects, that SDL's `dlsym(RTLD_DEFAULT)` finds a symbol in the main executable on iOS, and that `Platform`'s loader pinning, `dladdr` then `dlopen` of the library that holds the entry point, is harmless when that library is the executable.
5. **MoltenVK on iOS against the baseline**: `textureCompressionASTC_LDR` and the descriptor-indexing limits (4096 update-after-bind sampled images and storage buffers) on the iOS device chosen. The M4 Max passes on macOS, which says nothing about a phone's Metal family.
6. **The Android device, and what its GPU reports.** Which device is not decided. Update-after-bind descriptor limits, `multiDrawIndirect`, `drawIndirectFirstInstance`, scalar block layout and ASTC LDR are the features most likely to differ from desktop. Step 1 of the checks answers it before any engine code is written.
7. **GitHub's runners**: that `ubuntu-24.04` provides an NDK r27 or newer and SDK build tools, and that the macOS runner's Xcode is 16.3 or newer.
8. **The ASTC block sizes' quality** on real textures. The PSNR test sets the floor, and the numbers go into the roadmap with the change. A 6×6 base colour that shows banding on the samples would move to 5×5.
9. **The command forms in the report**, `am start` with a string extra and `devicectl` launching with arguments and copying from the data container, are from the tools' documentation, not from a run.
