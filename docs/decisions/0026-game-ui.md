# ADR-0026: Game UI is scene entities drawn by a `gui` module

- **Status:** Accepted
- **Date:** 2026-10-11

## Context

[M15](../roadmap.md#m15-game-ui-and-the-game-module-hook) adds a UI that ships in a game: menus, a heads-up display, a pause screen. What the engine has is Dear ImGui in the `ui` module, which the editor and debug builds use and which the player never links (`tools/check_dependencies.py` enforces it, [architecture.md](../architecture.md)). A game's UI has to be authored in the editor, saved in the project, cooked into the bundle and run on all five targets, like everything else a game is made of ([ADR-0007](0007-data-driven-game-structure.md)).

Constraints found in the code:

- A scene is a hierarchy of entities with registered components. The inspector, undo, prefabs, the JSON serializer and the Lua bindings all enumerate fields through one reflection system, which handles scalars, strings, enums, identities, vectors of floats and nested structs, and repeated members of structs (`world.md`). Siblings keep an order (`World::children`), and a `Disabled` tag makes the draw list and the simulation skip an entity.
- The scene is drawn into a target of the renderer's own formats, tone mapped and display-encoded; the player then copies it into the swapchain image ([rendering.md](../rendering.md#frame-structure)). The editor's Game panel draws the same scene into a target of its own and shows it through ImGui. Screenshots and the capture runs of [player.md](../player.md#capture-runs) copy that scene target.
- Input reaches a game as `platform::Event`s, which `Game::event` hands to `InputState`; positions are in window coordinates, touches and the mouse alike, and scripts read them through `input` ([scripting.md](../scripting.md)). Nothing sits between the event and the game, so a tap on a button would also be a tap on the world behind it.
- Events cross upward as data: physics records, scripting delivers ([ADR-0022](0022-gameplay-events-and-script-properties.md)). `scripting` sits before `audio` and `runtime` in the dependency order, so a module whose events scripts hear has to sit before it.
- `rhi::uploadImage` fills an image once, right after it is created. There is no update of a region.
- `platform` reports no safe area (notches, the home indicator, rounded corners), and the phones are the first targets.
- `stb_truetype` is installed with the `Stb` port already (`audio` uses its neighbour `stb_vorbis`). It reads TrueType and OpenType outlines, renders signed-distance glyphs, and reads the legacy `kern` table, not GPOS.
- The bundle carries each asset type as a payload; a sound is "the encoded file, as it is" ([assets.md](../assets.md#what-each-payload-is)). A new asset type changes the index, so `BundleVersion` becomes 5, before the M14 format freeze rather than after it.

## Decision

**A UI element is an entity with `Gui*` components, in the scene; a new `gui` module lays them out, hit-tests them and draws them.**

- *The components* are registered by `gui` through `World::registerComponent`, as `physics` and `scripting` register theirs, so nothing new is needed in `world`, the serializer, the inspector or the Lua bindings, and the scene format does not change (components are added, none is changed, so the scene stays at version 3).
  - `GuiCanvas`: the root of a tree. `referenceSize` (default 1920×1080), `match` (0 scales by width, 1 by height, between blends the two logarithmically), `safeArea` (inset by the platform's safe area), `order` (canvases draw in this order, then by entity).
  - `GuiRect`: an element's place inside its parent's rectangle: `anchorMin` and `anchorMax` (0 to 1 over the parent), `pivot`, and `offsetMin` and `offsetMax` in reference pixels from the anchors. One representation covers a fixed-size element at a corner, a stretched panel and a centred button. An element's parent is its parent entity, which holds a `GuiRect` or a `GuiCanvas`; the `Transform` that every entity has is not read.
  - `GuiImage`: a `texture` (an identity), a `tint` (sRGB, with alpha) and `slice` (nine-slice borders in texture pixels; zero draws the texture whole). Without a texture it is a coloured rectangle. `blocksInput` makes it take pointer events even without a button.
  - `GuiText`: a `font` (an identity), `text`, `size` (reference pixels), `color`, horizontal and vertical alignment, and `wrap`.
  - `GuiButton`: `interactable`, and three tints (normal, pressed, disabled) applied to the `GuiImage` of the same entity. It carries no script; a `Scripts` component on the same entity hears its events.
  - `GuiLayout`: `row` or `column`, `spacing`, `padding` and the children's alignment, which sizes and places the children from their `GuiRect` sizes in sibling order. No grid.
  - An entity with the `Disabled` tag is hidden and takes no input, and so is everything under it: layout and hit testing apply the tag to the subtree themselves. A script shows and hides a panel with `entity:add("Disabled")` and `entity:remove("Disabled")`.
- *Layout* is a plain function from the entity tree and the target's size to a rectangle per element in target pixels, run once a frame after the world has updated, over every canvas. The target's size and the canvas's `referenceSize` and `match` give the canvas's scale; the platform's safe area insets its rectangle when `safeArea` is set. Nothing is cached in version 1: a HUD of two hundred elements is a few microseconds of arithmetic, and a dirty flag comes only if a measurement asks for it.
- *Drawing.* `gui` builds a draw list (rectangles and glyph quads: position, texture coordinates, colour, a texture index and a kind) in element order, and one pass, `addGuiPass(graph, target)`, draws it after the scene's last pass into the same target, which the game, the editor's Game panel and the screenshot all share, so a capture shows what the player sees. One pipeline with alpha blending reads the renderer's bindless texture array; consecutive quads of one kind are one draw. The pass is not declared when no canvas is visible, so a game without a UI pays nothing. Colours are authored in sRGB and blended as they are, in the display-encoded space, as Dear ImGui does (the target is already encoded); a glyph's coverage comes from its signed distance and `fwidth`, so it stays smooth at any scale.
- *Text.* A `Font` asset (`.ttf`, `.otf`) is imported with a sidecar (`preload` ranges, default Basic Latin and Latin-1) and cooked as the file itself. At run time `gui` rasterises a glyph on first use with `stbtt_GetCodepointSDF` at one size per font (48 pixels with a 6-pixel border), packs it into an R8 atlas page of 1024², and draws it at any size by scaling the quad. The ranges in `preload` are rasterised when the font loads, on the job system, so a game's own text does not hitch. Because an image is uploaded once, a page that gains glyphs is created and uploaded again whole (1 MB) and the old one is released through the device's deferred destruction; at most one re-upload per page per frame. Layout is left to right with the advance and the `kern` table: no shaping, no right-to-left text, no input method, no GPOS kerning.
- *Input.* `Game::event` offers each pointer event to `gui` first. A press that lands on an interactable `GuiButton` or a `blocksInput` image, front to back over canvases and then over the tree in reverse order, is consumed and its pointer is captured by that element until release; the world and `input.touches()` never see a captured finger. Everything else goes to `InputState` as today. The mouse synthesised from a touch follows the rules of [M9](../roadmap.md#m9-mobile-export), since `gui` sees the events after the platform's translation.
- *Events.* `gui` records `GuiEvent`s (kind, entity, pointer), and `scripting` delivers them at the start of each `update` frame, as it does animation events: `onClick(self)` when a pointer was pressed and released over the same button, `onPress(self)` and `onRelease(self)`, on the instances of the button's entity, in slot order. A script changes a label with `entity:set("GuiText", ...)` and a panel with the `Disabled` tag; no `gui` API is added to Lua.
- *Module order.* `gui` sits between `physics` and `scripting`: it links `core`, `platform`, `rhi`, `renderer`, `assets` and `world`, and `scripting` links it to read its events, as it links `physics`. The roadmap's "between `audio` and `runtime`" is corrected to match. `ui` stays Dear ImGui and the player still never links it.
- *Platform.* `IWindow` gains `safeArea()`, a rectangle in window pixels, from `SDL_GetWindowSafeArea` (SDL 3.2 and later; the tree has 3.4) and the full window on a desktop.
- *Editor.* Components are edited in the inspector. The Game panel can show the canvases in edit mode, at the panel's size, so a layout is seen while it is made; moving an element by dragging in the panel is not in this version, the offsets and anchors are fields. A canvas selected in the hierarchy is outlined in the panel.
- *Format.* `AssetType::Font` is added; the bundle's index and `BundleVersion` 5 carry it; `docs/assets.md` and `docs/scripting.md` follow.

**Acceptance for the implementation.** `gui_tests` on Lavapipe: anchors, offsets, pivots and nine-slice quads against hand-computed rectangles; row and column layouts; the canvas scale for widths, heights and `match` between; a safe-area inset; hit testing and capture over overlapping canvases; one `onClick` for a press and release inside and none for a release outside; glyph metrics and wrapping of a bundled test font; and a captured frame of the sample's menu against a golden. On the Galaxy S25 Ultra and the iPad, a heads-up display of 200 elements (a third of them text) adds no more than 0.2 ms of GPU time to the stress scene's frame, cold, and the first frame of a new line of text does not miss a frame. The player still links no `ui` and no `editor`; a game with no canvas draws a frame byte-identical to today's.

## Consequences

- The UI is authored, saved, prefabbed, undone and scripted by the machinery that already exists, and a prefab can hold a whole panel (a health bar, a dialog) that a scene instances.
- A UI element carries a `Transform` it does not use, because every entity has one. The inspector shows it; hiding it for `Gui*` entities is a polish step.
- Text is limited to what `stb_truetype` does: scripts that need Arabic, Hebrew, Indic or Thai shaping, or a modern font whose kerning lives in GPOS, have to wait for the upgrade below. Latin, Cyrillic, Greek and most CJK fonts draw correctly, left to right.
- One SDF size per font costs sharpness at the extremes: very large text (over about twice the stored size) rounds its corners, and very small text (under about 12 pixels on the screen) is less crisp than a hinted bitmap font. The 48-pixel size is a guess to measure, and the sample checks both.
- The pass loads and stores the finished target once more: at 1080p RGBA8 that is 8 MB read and 8 MB written, not free on a tile-based GPU. The acceptance number is the measurement of it. If it misses, the quads move into the present pass (which already writes the backbuffer in one render pass), and screenshots then take the image after it; that is a change to where the pass is recorded, not to the components.
- Dragging in the panel, the rect gizmo, a grid, scrolling lists and styles are all absent, and a UI is built with numbers in the inspector at first. This is the largest cost to the person making a menu, and the first thing to add after the version works end to end.
- The UI is drawn at the target's size. A future dynamic resolution scale would blur it unless the pass moves after the upscale, into the present pass, where it also avoids the extra load and store.
- `BundleVersion` 5 is a break before the format freeze, not after it. A project made before it keeps its scenes; the bundle is cooked again.
- The Lua API grows three hooks, which are public API ([conventions.md](../conventions.md#versioning)); 1.0.0 freezes them.

## Alternatives considered

- **Dear ImGui in the player.** Already in the tree and immediate, but it is the editor's look, would put ImGui in every release player, which the architecture rules out, and a scene cannot hold it, so nothing is authored, cooked or prefabbed.
- **RmlUi, or another retained library with its own markup.** A full layout engine with styles, FreeType text and a Lua binding. It brings a second document model, a second layout and a render interface beside the ECS, so the inspector, undo, prefabs and scene references stop at its edge, and it adds FreeType and a large dependency to every target. It is the upgrade if a game needs HTML-like layouts, and nothing here prevents it.
- **A UI document asset (`.gui.json`) of its own.** A new file format to freeze, with references, an editor and a prefab story of its own. Scene entities get all of them for free.
- **Pre-baked bitmap or SDF atlases at cook time.** No rasteriser in the player and no first-use work, but a fixed character set per font, a localisation step before any new language, and one more cooked format. On-demand rasterising with a preloaded range keeps the cook trivial; baking stays available as an optimisation if first-use cost shows on a phone.
- **Multi-channel SDF (`msdfgen`).** Sharper corners at large sizes; needs an offline generator and a dependency. Later, if the rounding is noticed.
- **UI as meshes in the 3D scene.** Reuses the forward pass, but tone mapping, bloom and TAA would act on it, and the colours the author picked would not be the colours on screen. It is also the right shape for world-space UI, which is not in this version.
- **The pass inside the present pass from the start.** No extra target traffic, and sharp under a render scale; but screenshots and the editor's Game panel, which read the scene target, would then miss the UI or need a second path. Kept as the fallback the measurement can trigger.
- **The module after `audio`, as the roadmap wrote it.** Scripts could not hear its events without `scripting` linking a module above it, or `gui` calling into Lua; events as data from a lower module is the pattern the engine already uses.

## Open questions

- Is 48 pixels with a 6-pixel border the right stored size for text from 12 to 96 pixels on the phones' densities? Rasterise the sample's font at 32, 48 and 64 and compare captures at 12, 24 and 96 pixels before the size is fixed.
- Does a re-uploaded 1 MB page miss a frame on the S25 when a line of new text appears? If it does, add a region upload to `rhi` or preload more.
- Should a `GuiText` measure itself for a parent `GuiLayout` (a button that fits its label), or does version 1 take sizes from `GuiRect` only? The ADR assumes the latter; a button sized to its text is the first request to expect.
- Gamepad and keyboard focus: version 1 has neither. Is `GuiButton` the right place for a `focusable` flag later, or a component of its own?
