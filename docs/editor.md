# Editor

Two modules, both editor-only and never linked by the player ([architecture.md](architecture.md#editor-and-player)): `ui` wraps Dear ImGui, `editor` is the editor. `apps/editor` is the executable that owns the window, device and swapchain and calls the editor's steps in frame order.

## The ui module

`sonnet/ui/ImGuiLayer.h` is the whole public surface. `ImGuiLayer` creates the Dear ImGui context with docking, keyboard navigation and DPI-scaled fonts, initialises the SDL3 backend on the platform window and the Vulkan backend in dynamic-rendering mode on the device, with multi-viewport on when the platform is not headless.

Per frame, in this order:

1. `processEvent` for every raw SDL event, from `IApplication::nativeEvent`.
2. `beginFrame`, the application's ImGui calls, `endFrame`. `endFrame` runs `ImGui::Render`, once per frame whether or not anything is drawn.
3. `draw` inside a rendering scope on a swapchain image, from a render-graph pass.
4. `renderPlatformWindows` after the device's `endFrame`, which renders and presents the extra OS windows the Vulkan backend owns.

`registerImage` turns a sampled-capable `rhi::ImageHandle` into an `ImTextureID` for `ImGui::Image`; the image has to be in `ShaderReadOnly` when the draw data is recorded, which the graph guarantees when the ImGui pass declares it sampled. `unregisterImage` releases the descriptor after the frames in flight that may still reference it. Every registered image takes a descriptor of the backend's pool, which holds 1024: the font atlas, the viewport and game targets and the Assets panel's thumbnails ([Thumbnails](#thumbnails)).

`ui` is the documented exception to the backend rule: it links `sonnet::rhi_vulkan` to reach the Vulkan objects behind the device, the command list and the images. Nothing else above `rhi` sees Vulkan. The overlay port builds the backend without Vulkan prototypes and without linking a loader; the layer hands it the instance's `vkGetInstanceProcAddr` through `ImGui_ImplVulkan_LoadFunctions`, so the loader SDL opened stays the only one in the process ([ADR-0006](decisions/0006-vulkan-object-ownership.md)). Linking vcpkg's loader instead put it ahead of the system one on Linux, and it is built without X11 or Wayland surface support.

`ui_tests` refuses a non-Vulkan device and, on Lavapipe, draws ImGui frames with a registered image into a headless swapchain and checks that validation stays silent.

The frame, as `apps/editor/main.cpp` orders it:

1. Events arrive through `nativeEvent` (to ImGui) and `event` (mouse deltas for the camera, and the game's input while playing; the app itself handles quit and resize). While the viewport camera is looking with the right button held, `nativeEvent` keeps mouse motion from ImGui (likewise while panning or orbiting) so its cursor stays over the viewport; button events still reach it. When the look ends, SDL returns the visible cursor to its position before the drag, and the editor sends that position to ImGui.
2. `update(dt)` opens the ImGui frame, lays out the dockspace (hierarchy left, viewport and game as tabs in the centre, inspector over statistics right, log and assets bottom, built once with the dock builder unless a saved layout is restored), draws the menu bar, the shortcuts and the panels, and closes the ImGui frame. The panels edit the world; then the asset database polls for changed sources ([assets.md](assets.md#hot-reload)), the world's frame runs (`World::progress`: in play mode the fixed steps with physics and the scripts' `fixedUpdate`, the scripts' `update`, the animators' playback, physics interpolation and the spin system; the transform system, the skin palettes and the audio always), the game input's one-frame presses are cleared, the draw list, the light list and the environment are built from it ([world.md](world.md#draw-list)), the colliders' outlines when they are shown, and the outline list from the selection and everything under it.
3. `render(commands, swapchainImage)` first polls the picker, then resets the graph, imports the viewport target and declares the scene passes, the debug line pass for the colliders, the id pass into a transient id image, the selection mask pass into another, the outline pass over the colour and the pick readback, then, when the Game panel is on screen, a second `addScenePasses` into the game target from `m_gameView`, a `SceneView` of its own over the same lists and the scene camera, with no id, mask, outline or debug-line pass ([ADR-0021](decisions/0021-two-views-in-one-frame.md)), then the ImGui pass into the swapchain image (cleared, with the viewport and game colours declared sampled) when there is an image, and executes the graph. It then records the frame's statistics, the Game view's own (`Renderer::statistics(view)`) on a line of their own while it is declared.
4. `afterPresent` renders the platform windows.

The Debug build of the application turns on the flecs explorer through `World`.

## Axis views and orthographic navigation

Numpad 1 snaps to Front (looking down -Z), Numpad 3 to Right (-X), and Numpad 7 to Top (-Y). Ctrl selects Back (+Z), Left (+X), and Bottom (+Y). Top has -Z up; Bottom has +Z up. Numpad 9 switches to the opposite axis view. View > Axis view offers the same commands without a numpad. The viewport labels its view and projection in the lower-left corner, with light text on a compact translucent black backing for contrast over bright and dark scenes. The backing fits the measured text and scales its padding with the font; it is clipped to the viewport and does not take input or change the image rectangle. `editor_tests "[.view-label-captures]"` writes Basic sample window captures for Front, Top and Bottom (with the environment darkened) at 100% and 200% font scales to the temporary directory in `sonnet-view-label-captures`. Each scene tab keeps its own projection, axis view and auto-perspective state alongside its fly camera.

The upper-right axis widget shows X in red, Y in green and Z in blue, with filled, labelled positive ends and outlined negative ends. Ends are drawn back to front. Hover highlights an end; clicking snaps to its axis view, and clicking the current axis flips to its opposite. Left-drag anywhere inside the widget orbits around the same pivot as Alt + left-drag, including when the pointer leaves the widget. The adjacent P/O button toggles perspective and orthographic projection. These controls consume their pointer input before picking and gizmos; they scale with the UI font and are hidden if the viewport cannot fit them. [Verification images and tests](reports/viewport-axis-widget.md) cover perspective and axis views at two UI scales.

An axis snap turns around the current pivot: the focus target, or a point `focusDistance` ahead when there is none. It switches to orthographic, preserving the size at that pivot with `orthoHeight = 2 * distance * tan(fovY / 2)`. Turning with Alt + left-drag or right-drag returns an automatically snapped view to perspective, preserving the zoomed size. Numpad 5 or View > Orthographic explicitly toggles projection; explicitly chosen orthographic views remain orthographic when turned.

View > Smooth view duration sets the ease-in-out transition time for axis snaps, projection toggles and Frame Selected (0.2 seconds by default, 0 to disable, up to 2 seconds). The preference is saved per user. Rotations use quaternion slerp around the pivot; framing blends the pivot and distance. Projection changes dolly the camera while narrowing the field of view towards parallel rays, preserving the size of the pivot plane, then switch projection at the endpoint. Navigation input cancels from the current pose. Headless editors and command-line screenshot runs always apply view changes immediately. [Transition recording](reports/smooth-viewport.gif) shows axis snaps, both projection switches and framing at three times slow motion; reproduce the engine frames with `editor_tests "[.smooth-view-captures]"` (under the temporary directory in `sonnet-smooth-view-captures`).

The orthographic wheel scales the view height around the focused object (around the cursor when nothing is focused). Middle-drag pans in the view plane, as the keys do while flying. While flying, W/S and Q/E pan up/down in the view plane and A/D pan left/right; Shift keeps its speed multiplier. F frames the selection without leaving its orthographic orientation. Picking uses the rendered id image; gizmo rays start on the near plane and their handles scale with view height. Orthographic views omit the perspective floor grid. The viewport draws an orthographic view from an eye `FlyCamera::renderView` pulls back ten view heights along the view direction, with the far plane and `dollyDepthOffset` extended by the same distance: an orthographic near plane cuts through whatever is level with or behind the camera, which a tilted view over a ground plane reaches once a pan or zoom lowers the camera, and the pullback changes no pixel of the projection. Picking and gizmo rays use the camera itself, not the pulled-back eye.

Showcase verification on Linux/Lavapipe: [user view with TAA](reports/orthographic-viewport/user-final-taa.png), [shadow factor](reports/orthographic-viewport/user-shadow-factor.png), [top](reports/orthographic-viewport/top-final-taa.png), [front](reports/orthographic-viewport/front-final-taa.png). Reproduce with `editor_tests "[.orthographic-showcase]"`; the hidden test copies the showcase to a temporary project and writes captures under the temporary directory in `sonnet-orthographic-captures`.

## Shader hot reload

The engine's shader sources are found in the checkout the way the log's source links are, `modules/renderer/shaders` under `sourceRoot` or above the executable. Every half second the editor compares their modification times; a changed entry-point file is recompiled with `editor::ShaderCompiler` and its pipelines rebuilt through `Renderer::reloadShader`, and a changed module, `sonnet.slang`, recompiles every entry point ([rendering.md](rendering.md#shaders)). Compile errors go to the log with the `file:line:column` the compiler reports and leave the previous pipelines running. Tools, Reload shaders does the same for every shader at once. Without a checkout around the binary the poll turns itself off.

## Selection and picking

The hierarchy filters like the asset browser: a text box (case-insensitive name) and the same multi-select combo over the kinds of entity, decided by which components an entity has: Meshes, Skinned meshes, Animators, Lights (point, spot, directional), Cameras, Audio (source or listener), Scripts, Rigid bodies, Colliders and Environments. Nothing checked means every entity; checked kinds are a union, and the name is an AND. While a filter is active the tree shows the matches and their ancestors, the ancestors open and greyed when they do not match themselves; selection, drag and drop and the context menu work on the filtered rows. The filter is editor state: it is not saved with the scene.

The selection holds UUIDs, so it survives undo, play mode and reloads; the last selected entity is the primary one, what the inspector shows and the gizmo moves. Clicking in the hierarchy selects, Ctrl toggles, Shift adds. Clicking in the viewport, away from a gizmo handle and with the camera idle, asks the `renderer::Picker` for the id under the cursor; the answer comes two frames later, when the readback of that frame has completed, and the selection changes then, with the same modifiers. Selected entities and their descendants are drawn into the selection mask and outlined from it ([rendering.md](rendering.md#the-renderer-module-today)), so an object in front of a selected one is never outlined itself. Escape clears the selection. F, a double-click on a hierarchy row, the row's context menu (Focus) and a double-click on an object in the viewport turn the camera towards it, from a distance that fits the world-space bounds of every mesh under the entity, keeping the heading but never looking up, so a camera turned to the sky ends above the object (its position and scale when there is none, as for a light).

### Reordering

Dragging a row onto the middle of another makes it that row's last child, and onto the empty area below the tree the last root. Dropping on the upper or lower quarter of a row puts it before or after that row among its siblings, a line showing where; the lower quarter of an open row with children puts it first among them. A drop that is not allowed draws no target: part of a prefab instance cannot change parent ([ADR-0028](decisions/0028-nested-scene-instances.md)), and an entity cannot go under itself or a descendant. An instance's own children reorder among their siblings, added children included, at every depth; the scene then stores the order ([ADR-0032](decisions/0032-instance-child-order.md), [world.md](world.md#scenes)). The move is one reparent command with a sibling index (`HierarchyPanel::moveEntity`, `canMove`). The order is `World::setSiblingIndex` ([world.md](world.md#hierarchy)): it renumbers the siblings, and a save writes the tree in that order, so saving, reopening and play mode keep it. An instance's `order` entry is the one place the scene format needs more than file order.

## Gizmos

W, E and R over the viewport choose translate, rotate and scale (the same keys fly the camera while the right button is held). Translation and rotation work along the world axes, scale along the entity's own. A drag starts on the handle under the cursor and resolves every mouse position against the axis line or the rotation plane from the drag's fixed start position, never from the object's current one, so the maths never chases what it moves; the handles themselves are drawn at the object's current position, taken from its local transform in the same frame, so they follow it as it moves. The live edit writes the local transform directly; when the button is released, one command with the transform before and after goes on the stack. In translate mode the three squares between the axes are plane handles: dragging one moves the entity in that plane, resolving the mouse ray against the plane from the drag's start point, and the axis handles win where they overlap. Snapping rounds a drag to a grid: translation to a world-space step per moved axis, rotation to a step in the angle, scale to a step in the factor (1 m, 15° and 0.1 by default, editable in the Edit menu). The Edit menu's Snap to grid toggles it and holding Ctrl during a drag inverts it; `GizmoView::snap` carries the decision so the tests need no Dear ImGui. The maths (`project`, `rayDirection`, `axisRayParam`, `planeRayHit`) is public for the tests, which drive drags through `GizmoView` without Dear ImGui.

The orthographic picking and snapped translation integration test runs with both Dear ImGui shortcut modes: Ctrl on Windows/Linux and Cmd on macOS. It sends the corresponding physical modifier so macOS Ctrl-click emulation does not turn the gizmo's left press into a right-click, and checks selection, drag start, snapped movement and the undo command.

## Inspector

The inspector walks the selected entity's registered components ([world.md](world.md#components)) and generates a widget per reflected member: drag fields for floats and integers, degrees for members with the radians unit and for the rotation quaternion, colour pickers for `vec3` and `vec4` members named `color`, a combo for enums, a checkbox for booleans, nested structs recursively. A component header has a close button that removes it, except `Transform`; "Add component" lists what the entity lacks. A prefab instance shows the component as inherited until a widget touches it, which gives the instance its own copy ([world.md](world.md#prefabs)).

Part of an instance, an entity copied from its prefab, says which instance it belongs to, and marks each component whose value differs from the prefab entity it came from, or that the prefab entity lacks, as changed: that is what the scene stores of it, and a changed component no longer follows the prefab ([ADR-0028](decisions/0028-nested-scene-instances.md)). "Revert to prefab" on a changed component copies the prefab's value back, or removes a component the prefab lacks, and a component the prefab has and the part no longer does is listed as removed with a Restore. An instance's own override of a component its prefab has is marked the same way, and reverting it removes the override so the prefab's value shows through; the transform places the instance and is never marked. Each is one undoable command.

Widgets change the world live. The value before the first widget of a component is activated is kept, and when a widget is released after an edit one command with the values before and after is pushed, so a long drag is one undo step. The name field works the same way with a rename command.

A member of type `core::Uuid` is an asset reference and gets a picker: a button naming the asset (`name (Type)`, `(none)`, or `(missing)` for an identity the database does not know) that opens a filtered list of the assets of the member's type, decided by the member's name (`mesh`, `material`, `map`, `script`, `...Texture`), and a drop target for rows dragged from the asset browser. A pick is one command.

The physics components, the audio components, `SkinnedMesh`, `Animator`, `MorphWeights` and `ParticleEmitter` are registered components like the others, so the inspector shows and adds them with no code of its own, `Scripts` apart ([below](#script-slots)); a body type is a combo, a collider's `mesh` a mesh picker, and the `script`, `sound`, `skin` and `clip` members get pickers of their own type.

### Script slots

`Scripts` is a list of structs, which the generic widgets do not draw, so the inspector has a section of its own for it ([ADR-0022](decisions/0022-gameplay-events-and-script-properties.md)). Each slot is a numbered block with `up`, `down` and `remove` buttons, a script picker (a pick clears the slot's property values, which belonged to the old script), and one widget per property its class declares, sorted by name: a drag field for numbers, limited by `min` and `max` when the class sets them, and for integers, a checkbox, a text field, three drag fields for a `vec3`, a colour picker for a `color`, an asset picker for an `asset`, and for an `entity` a button naming the entity that opens a filtered list of the scene's, with a drop target for rows dragged from the hierarchy. A property that differs from the default has a `revert` button; one the script no longer declares is listed as kept. "Add script" appends an empty slot. A script asset dragged from the asset browser onto the Scripts header, the Add component button or an entity in the hierarchy appends a slot, adding the component first when the entity has none, as one undo step.

The properties come from `IScriptRuntime::properties`, which loads the class the way play mode does ([scripting.md](scripting.md#properties)), so the declarations follow the file as it changes and a script that does not load shows the reason instead. A slot stores only what differs from the default: setting a property back to it removes the entry. Dragging a widget edits the component live and the release is one command, like any other component; structural edits (a pick, a button) are one command each. In play mode the edit reaches the running instance on the next frame, and the snapshot restore on stop discards it ([below](#keeping-the-plays-edits)). The pure operations, on values, are in `ScriptSlots.h`.

## Asset browser

The Assets panel opens at the project folder and shows one folder at a time. Folders come
from disk and sort before files; the Name, Type and Source columns keep their header sorting.
Scenes, prefab files and ordinary files such as README and glTF buffers appear alongside
imported assets. Sidecars, hidden files and editor state are omitted, and symbolic links are
not followed. Built-in assets remain available at the project root. A model's sub-assets
keep separate rows with their source file, and a loaded model's prefab is not listed twice.

Double-click a folder or select it and press Enter to open it. Breadcrumbs show the project
and every folder on the path; clicking a segment goes there. Backspace or Alt+Up goes up,
Alt+Left goes back and Alt+Right goes forward, as do the Back, Forward and Up buttons.
The current folder is remembered for each project in the layout ini's
`[SonnetAssets][Folders]` section. A missing saved folder falls back to the project folder.
Double-clicking a scene, or pressing Enter on it, opens it in its own scene tab as File > Open does.

With text in the filter, search covers the current folder and every folder below it,
ignoring case; Source distinguishes equal names. Without text it lists only immediate
children. The type combo has a checkbox for each asset type, Prefabs, Scenes and Files;
nothing checked means All and Clear unchecks everything. Folders remain available for navigation.
Clicking an imported asset inspects it without touching the entity selection or gizmo.
Asset and prefab rows remain drag sources for inspector pickers and the hierarchy;
a model or prefab dropped there becomes an instance, and an environment sets the scene's sky.

Ctrl-click (Command-click on macOS) toggles rows and Shift-click selects a range using ImGui multi-select.
The New asset menu's New folder entry and the background menu create an empty folder in
the current folder as one undo step. Material creates a fresh `.material.json` in `assets`;
Script creates an empty script with every hook in `scripts`, or the first asset root.

The row menu offers Copy path and Show in file manager for files and folders, and Open
for a script in the configured external editor. Rename and Delete, also F2 and Delete
while the panel has focus, act on the selection. Built-ins and glTF sub-assets cannot be
renamed or deleted independently. A single rename edits the Name column in place: Enter
commits and Escape cancels. A selection rename opens a dialog with a name for each source,
applied as one undo step. Extensions, including `.scene.json`, `.material.json` and
`.prefab.json`, stay; folder names have no preserved extension. Folder renames use the same
file commands as asset renames. Folders created directly under the project can be renamed
in place too; configured asset roots and folders containing them cannot be renamed. Imported
assets stay within the database's permitted roots. A failed rename keeps the field available
for correction and shows its error above the table.
Renames keep identities and references and update loaded prefab paths, open scene tabs and
the saved start scene. A possible `require` reference to an old name is logged for manual updating.

Moving rows needs no rename. Dragging rows onto a folder row or a breadcrumb segment moves
them there, the whole selection when the grabbed row is in it, and Ctrl+X then Ctrl+V in
another folder (Command on macOS; also Cut and Paste in the row menu) moves what was cut
into the current folder. Both are `moveFilesCommand`s, one composite undo step for the
selection; a row dropped on the folder it is in, on itself or into its own subfolder is
skipped, and a move the database refuses (the project folder is no asset root, a name is
taken) shows its error above the table and changes nothing. An asset row keeps the
`SONNET_ASSET` payload the inspector's pickers and the hierarchy accept, and the browser
adds the paths of the rows to move from its own state; a folder, scene or plain file row
carries the `SONNET_ASSET_PATHS` payload, which only the browser accepts. Duplicate
(Ctrl+D while the panel has focus, so the hierarchy's Ctrl+D is not also triggered) copies
the selected sources beside themselves under a numbered name (`wood 2.png`) through
`editor::duplicateAssets`, which reuses `importAssets`' copy step: the copy has no sidecar
of the source's, so it registers with a fresh identity and default import settings, and a
glTF file is copied into a folder numbered the same way (`crate 2`) with the files its URIs
name. Duplicating is one undo step, and undo and redo keep the copy's identity. Folders,
scenes and files no importer reads cannot be duplicated.

The browser also notices changes made outside the editor. When the window gains the focus,
and when the Assets panel is shown after being hidden, the editor calls
`AssetDatabase::rescan` ([assets.md](assets.md#rescan)): files that appeared are registered, assets
whose source is gone are unregistered (logged), and a file moved in the system's file manager
together with its `.meta` keeps its identity, with its open scene tab and the project's start
scene following it. A file moved without its sidecar is a new asset with a new identity, as
when the project is opened. Prefab files are compared with the prefabs loaded: one that came,
went or moved, like a model that came, went or moved, rebuilds the prefabs the way a model
re-import does ([Model re-import](#model-re-import)), which keeps the history cut that rebuild
makes and waits for stop during play. A prefab file that failed to load is not counted as new
again on every focus. Nothing runs on a timer, so an editor that keeps the focus costs nothing.

Delete's confirmation lists the selected files and folders and counts references in open
scenes, materials and prefab instances, including assets inside selected folders. Scenes
that are not open are not counted. Deletion unregisters assets and drops loaded prefabs,
moving source files and sidecars to `.sonnet/trash/<id>/`. Undo restores the same files and
identities and redo deletes them again, as one command for the selection. The command erases
its trash when dropped from history or when the project closes; opening a project clears
trash left by a crash. Undoing folder creation removes it only while empty, preserving
files added outside the command history.

The inspector shows an asset's name, type, source and identity, with a Reimport button, and per type:

- A material: its authored values ([assets.md](assets.md#materials)), edited live through the database like a component, one command per widget release or pick; Save writes the file. A glTF material is edited in memory only. Emissive is shown as a colour and a Strength drag whose product is the stored value: seen afresh, the strength is the largest channel and the colour the value divided by it (black at strength 0 when there is no emission). Editing the colour keeps the strength, editing the strength scales the colour, and a colour picked at strength 0 sets the strength to 1 so it shows. Under each texture slot that names a texture, a collapsed UV row holds how the slot reads its UVs: the offset, rotation (in degrees; the file stores radians) and scale of its `KHR_texture_transform`, and the UV set it samples (0 or 1). The row also offers Wrap S, Wrap T and Filter (Linear, Nearest, Nearest without mips) for that slot. Imported finer filter combinations are preserved until a preset is selected.
- A texture file: the import settings of its sidecar (sRGB, mipmaps, compression); a change is a command that re-imports at once. An image inside a glTF file follows its materials.
- A glTF model: the import settings of its sidecar, a **Light scale** field above its sub-assets ([assets.md](assets.md#skins-and-animations)), with Blender (`1/683`) and Photometric (`1`) buttons for the two usual conventions. A typed value is one command when the field is left; a negative or non-finite one is refused. Like a texture's, a change rewrites the sidecar and re-imports at once, so the model's imported lights change, and so do the model's prefab and its instances in the open scene ([Model re-import](#model-re-import)).
- A mesh: its submeshes and default materials. A model: its sub-assets. An environment: whether it is loaded.
- A script: its length, and an Edit button that opens it in the external editor of the preferences, as the log's links do. Saving it there reloads it into a running game ([scripting.md](scripting.md#errors-and-hot-reload)).
- A sound: its length, channels and sample rate, with Play and Stop, which preview it through the audio device in edit mode ([audio.md](audio.md#playing)). A skin: its joints by path. An animation clip: its length and channel count.

### Grid view

Two buttons beside Import choose how the folder is shown: the list above, or a grid of tiles. A tile is a picture over the asset's name, with a slider for its side (48 to 128 pixels, 96 by default) beside the buttons while the grid is shown. The grid lists the same rows in the same order, the one the list's header sorts by, and everything the list does works on a tile: click, Ctrl-click and Shift-click select, double-click or Enter opens a folder or a scene, F2 renames in place under the tile, Delete confirms, rows are dragged to the inspector, the hierarchy, a folder tile or a breadcrumb, Ctrl+X, Ctrl+V and Ctrl+D act on the selection, and the row menu is on right-click. Hovering a tile shows its full name and type, since a long name is clipped at the tile's edge.

The choice is kept per project in `preferences.json` under `assetsView`, a map keyed by the project folder to `{"grid": true, "tileSize": 64}` and kept the way `openScenes` is, so only the recent projects keep an entry; a size outside the limits is clamped on load. It is not in `project.json`, a versioned format that a view setting should not change, nor in `layout.ini`, which belongs to the window. The editor hands the panel the open project's view when it opens one (`AssetBrowserPanel::setView`), and the panel calls its view handler when the mode changes or the slider is let go, which saves the preferences.

### Icons

A tile that has no picture, and every other place that wants an icon, draws a glyph of [Lucide](https://lucide.dev): a folder, an image for a texture, a globe for an environment, a palette for a material, a box for a mesh, a package for a model, blocks for a prefab, a code file for a script, a speaker for a sound, a type glyph for a font, a play triangle for an animation, a bone for a skin, a film for a scene and a plain file for anything else (`iconForType`). The font is a 6 KB subset of sixteen glyphs, cut from `font/lucide.ttf` of the `lucide-static` package by `tools/generate_lucide_font.py` into `LucideFontData.cpp` and merged into the text font by `addFonts` ([Fonts](#fonts)), so an icon is text: `ImGui::Text("%s Folder", IconFolder)`. The glyphs sit in the private use area (`Icons.h` names their UTF-8). To add one, name it in the script's `ICONS` list, add its constant to `Icons.h` and run the script on the package's font (the script's header says how). Lucide is ISC licensed and the icons it took from Feather are MIT licensed; both licences travel with the font in [THIRD_PARTY_NOTICES.md](../THIRD_PARTY_NOTICES.md).

### Thumbnails

A texture, an environment, a material, a model or a prefab that is a file of its own shows its picture in the grid, and so does a mesh, a glTF sub-asset or a built-in one; glTF's other sub-assets, KTX2 files and every other type show their icon. `assets::makeThumbnail` makes the picture of a texture or an environment on the job system ([assets.md](assets.md#thumbnails)) and caches it at `.sonnet/cache/<uuid>.thumb.ktx2`, remade when the source or its sidecar is newer, so reopening a project reads small files instead of decoding the images. `ThumbnailCache` turns it into an `ImTextureID`:

- A picture is asked for only while its tile is on screen (`ImGui::IsRectVisible`), the first request schedules the job, and the tile shows its icon until `update` has uploaded the result. Scrolling a folder of hundreds of textures asks for the ones that come into view and nothing else.
- `update`, once per frame, uploads at most eight finished pictures (`UploadsPerFrame`), so a first look at a big folder fills in over a few frames and no frame carries the whole upload.
- A picture nobody asked for in 180 frames is released (`IdleFrames`), and at most 768 are resident (`MaxResident`), below the descriptor pool; past that a tile keeps its icon until others are released.
- A source changed on disk is noticed by `AssetDatabase::pollChanges`, which drops the picture, and the next request makes it again. A picture dropped while its tile was drawn this frame is destroyed three frames later, since the frame's draw data still names it.
- A capture waits for the pictures its tiles asked for (`busy`), so `--screenshot-window` of the grid shows them.

Measured on Lavapipe in a debug build with validation, a 2560 × 1440 window and 48 px tiles over 300 uncompressed 1024 × 1024 textures: 180 tiles were in view, filled in 22 frames, and the slowest `Editor::update` was 14 ms against a mean of 5.6 ms; with the cache warm the slowest was 8.6 ms.

#### Rendered pictures

A material, a mesh, a model and a prefab are drawn by the engine, since no file holds their picture. `ThumbnailRenderer` declares one view per subject in the editor's graph, as the Game view is ([ADR-0021](decisions/0021-two-views-in-one-frame.md)): up to four a frame (`PerFrame`), each its own `RenderTarget` of 128 × 128 pixels and its own `SceneView`, whose address the renderer keeps the view's state under, so it is the same one every frame. The view has no sun, since the sun's four 2048² cascades would be 64 MiB of shadow maps for every thumbnail; its light is a sky the renderer makes for itself (a 128 × 64 equirectangular map, a grey gradient with a soft box above and in front of the subject on the left and a cooler, dimmer fill on its right) and creates once, with the sphere, when the first picture is asked for. The scene's own environment is not used, so a picture does not depend on the scene that is open. Bloom is off, and TAA starts over for every picture (`resetHistory`), so the picture is the same every time.

- A material is a sphere of radius 0.5 seen from 2.2 m with a 30° field of view.
- A mesh is drawn with its own materials, white. A model and a prefab are drawn from the tree the world already holds for them: `world::buildDrawList(world, assets, root, ...)` reads the `MeshRenderer`s under the prefab's root (a model's prefab is the model, under its identity) with the root at the origin, without instantiating anything, so the open scene, the selection and the undo history are not touched. A skinned mesh has no `SkinPose` in a prefab, so it is drawn in its bind pose, and a part with `Disabled` is left out. Cameras, lights and emitters in the tree are ignored.
- A mesh, a model and a prefab are framed on the bounding sphere of what is drawn (the meshes' bounds through their transforms), from the front, a little above and to the right, at the distance where that sphere fits the 30° field of view with 10% to spare.

The picture reaches the cache the way the picking id does ([Picker](rendering.md#editor-viewport-and-imgui)): a pass of the same graph copies the target into a readback buffer of the frame slot, and `ThumbnailCache::render` reads it `FramesInFlight` frames later, so nothing waits for the GPU. A tile asks in this order:

1. `get` schedules a job that reads `.sonnet/cache/<uuid>.thumb.ktx2` (`assets::cachedThumbnail`), which is used when it is no older than the file, its sidecar and its dependencies: a material's is as old as the source files and sidecars of the textures it reads; a mesh's and a model's, the glTF file and its sidecar; a prefab's, the prefab file and the files of the prefabs it nests and of the models, meshes and materials it draws. A prefab is not an asset, so `ThumbnailCache` builds its request from the world's `PrefabFile`. A built-in mesh has no file, so its picture is rendered when asked for and not kept on disk.
2. Without a usable entry the subject is queued for the renderer, at most `Backlog` (8) at a time, so a folder of hundreds of models imports its meshes a few at a time and the uploads that follow stay small; the tiles in view wait for a place. Queueing asks the database for the meshes and materials the subject draws, and rendering waits until no asset is loading, so a picture is made after what it draws has arrived and not with fallbacks; a folder fills in as the project finishes loading.
3. The picture is uploaded as every other one is, and a job writes it to the cache (`assets::storeThumbnail`), except when the material has edits that are not saved: the file would not match the picture, so it is shown and not kept. A prefab that draws such a material is not kept either.

`AssetDatabase::takeChangedMaterials` names the materials whose look changed since the last call (edited through `setMaterialSource`, saved, or reading a texture that was published or re-imported), and the editor invalidates their thumbnails each frame, which also deletes the cache entry, since an edit made in the editor does not touch the file the entry's age is compared with. Invalidating an asset also drops what is made from the same file or lists it as a dependency: a re-imported model takes its meshes' and the prefabs' that draw them along, and a changed material the prefabs that use it. When the prefabs are built again (a model was re-imported, or a prefab file appeared, went or moved) the resident models' and prefabs' pictures are dropped with their cache entries (`invalidatePrefabs`), since what they were drawn from may be older than what they show; a prefab file that changed on disk is also stale by its age, for a picture that is not resident. A picture rendered for a request that was invalidated since is dropped (each request carries a ticket the answer must return). Dragging a value in the inspector therefore shows the new picture when the drag stops, and a restart shows the saved material. Unregistering the asset removes the entry with the others of its identity.

Measured on Lavapipe in a debug build with validation, an 800 × 600 window and 300 copies of five sample models (`editor_tests "[.thumbnail-budget]"`), all asked for in one frame, the worst case for the scheduling: the 307 pictures took 225 frames, a mean of 39 ms, a median of 37 ms and a 95th percentile of 50 ms against a mean of 37 ms, a median of 31 ms and a 95th percentile of 61 ms for frames with nothing to make (the slowest, 136 ms against 95 ms, is the first frames after opening); the next run read all of them from the cache in 38 frames at 33 ms, as an idle frame takes. The cost of a frame that renders is the four views, not the number of models.

### Importing assets

The Import button beside New asset opens a file chooser that takes any number of files, filtered to images (PNG, JPEG, TGA, BMP, KTX2), glTF models (`.gltf`, `.glb`) and equirectangular `.hdr` skies, and dropping files from the operating system's file manager on the Assets panel does the same with whatever was dropped. A drop anywhere else in the editor does nothing. Either way `editor::importAssets` copies the files into the current folder when it is inside an asset root, or the first asset root otherwise and registers them with the database (`AssetDatabase::registerFile`), which writes their sidecars as opening the project would have; the copies are then ordinary assets, so a model's clips play, a texture goes in material slots and an `.hdr` file is an environment. A model is also placed in the world as a prefab, as opening the project places every model, so it can be dropped on the hierarchy at once; undoing the import leaves that prefab loaded, as undoing Save as prefab does, and an instance of it draws nothing until a redo brings the files back. The originals are not touched, and a sidecar beside one is not copied: the copy gets an identity of its own.

A glTF file goes into a folder of its own named after it, with the buffers and images its URIs name copied at the same relative paths (`assets::gltfDependencies`, which refuses a URI that leaves the file's folder), so the model keeps working; an image among them is registered as a texture too, as opening the project would register it. A name already taken, by a file or by another file of the same import, gets a number as Save as prefab does: `wood 2.png`, `crate 2/`, `steel 2.material.json`. A file no importer reads is logged and skipped. Nothing is left behind when nothing could be imported or a copy failed, a missing dependency for one.

One import, however many files, is one undo step ([Undo and redo](#undo-and-redo)). Undo unregisters what it added (`AssetDatabase::unregister`, which destroys what was loaded from it, so an entity using the model draws without it and a material reading the texture falls back) and deletes the copies, their sidecars and the folders it made, keeping a folder something else has been put in since; redo copies the same files again from where they were and puts the sidecars back, so the assets return under the same identities and the scene's references to them work again. It is not a scene edit, so it does not make the scene unsaved, like the material and texture commands.

## Model re-import

A re-import of a glTF file (the inspector's Reimport button, a settings change, or the hot reload of an edited file) reports the model to `AssetDatabase::takeReimportedModels`, and the editor rebuilds what was built from the old import in the same frame. Instances copy their prefab's tree ([ADR-0028](decisions/0028-nested-scene-instances.md)), so rebuilding the prefab alone would leave them as they were. `Editor::refreshModelPrefabs` makes the round trip a tab switch makes: it saves the scene, clears it, rebuilds every prefab (the models' and the prefab files, because a prefab file that nests a model holds a copy of the old tree), and loads the scene again. Overrides re-attach by the identity of the node they were made on, which comes from the node's name path ([ADR-0030](decisions/0030-model-node-identities.md)), so a node inserted ahead of an overridden one does not move the override. Changed values, added nodes and removed nodes show in the open scene; the undo history and the selection survive (the selection drops what no longer exists), and the scene does not turn unsaved. Other tabs are scene JSON and load against the rebuilt prefabs when switched to. During play the refresh waits for stop; the running scene and the snapshot are left as they are.

Commands on the assets (import settings, materials, file moves) do not make the scene unsaved: it is unsaved exactly when a scene edit lies between the history's position and the position of the last save. Such a command made during play is kept on the history that play set aside, so it can still be undone after stop, and is not listed among the play's changes.

## Export

File, Export... cooks the open project and assembles a directory that runs on its own ([player.md](player.md#what-an-export-is)). The dialog asks for the target platform (Windows, Linux, macOS, Android or iOS) and the folder to write into, which defaults to `export/<platform>` under the project. "Current scene only" becomes available when a scene file is open. It starts the bundle in that scene and omits the project's other scenes; prefabs and assets still travel with it. The scene is read from disk, so the dialog warns when the open scene has unsaved changes. After a successful export it reports what it wrote and replaces OK and Cancel with Close; Enter or Escape closes it too. A failed export leaves the dialog open with its error and OK and Cancel.

An export is the bundle ([assets.md](assets.md#cooking-and-export)), the target's player binary, the compiled engine shaders and, on Windows, the libraries beside the binary. The player and the shaders are taken from the editor's own directory, which is right for the host platform. When the editor is built, a post-build step on `sonnet_player_app` copies the player there, which in a build with a game module is the module's player, so its export ships the module ([player.md](player.md#game-modules)); exporting for another one writes the bundle and warns that no player was found, so a player built by CI can be dropped beside it. Cross-compiling one is not the editor's job ([ADR-0011](decisions/0011-cooked-bundles-and-the-player.md)). Exporting for Android or iOS writes the bundle alone, with its textures in ASTC ([assets.md](assets.md#textures)), and copies no player or shaders: the phone's player is an APK or an app bundle, which the build makes around the bundle, and the editor builds neither. The dialog says so when a mobile platform is chosen ([player.md](player.md#running-on-android)).

The dialog is `Editor::exportProject` with the fields it collected, and `editor::exportProject` is the function under both. Cooking asks the editor's own database for every asset, so what is exported is what play mode has been running, including a glTF material edited in the inspector, and the texture cache the editor has already filled is reused rather than rebuilt.

## Undo and redo

Every edit is an `ICommand` with `apply` and `revert`, pushed on the `CommandStack`, which applies it, drops the redo list and keeps the last 256. Commands refer to entities by UUID, never by flecs id, and a deleted subtree comes back with the identities it had, so later commands keep working after undo and redo. The commands: an asset import ([Importing assets](#importing-assets)), a material edit, a texture's settings, create, delete, duplicate (fresh identities, decided once so redo makes the same copy, with a prefab instance's descendants taking the identities the copy derives for them), reparent (keeping the world transform, restoring the exact local one on undo; with a sibling index it also reorders, and undo puts the entity back at its old place among the old siblings), rename, a component set, add or remove holding both values, prefab instantiation, "Make local", "Save as prefab", and a composite for a multi-selection delete or duplicate. A part of a prefab instance cannot be deleted, since the instance would bring it back on load: Delete hides it with `Disabled` instead, and it is neither duplicated nor dragged to another parent, though children can be added under it ([world.md](world.md#prefabs)).

"Make local" on an instance turns it into ordinary entities that keep their identities (`World::makeLocal`, which makes the instances copied inside it local too), and undo brings the instance back. "Save as prefab" writes the entity and its descendants to `prefabs/<name>.prefab.json` in the project, with a number added when the name is taken, loads the prefab, and replaces the entity by an instance of it under the same parent with the same name and identity, as one undoable command; the file stays written and the prefab loaded after an undo. The instance's descendants have new, derived identities. An entity that is part of an instance cannot be saved as a prefab. Ctrl+Z and Ctrl+Y (or Ctrl+Shift+Z) and the Edit menu, which names what they would do. The stack remembers how many commands were done at the last save, and the scene counts as unsaved (the asterisk in the window title, the dot on a tab) exactly when the history is not at that position: undoing back to the saved point is clean again, redoing away from it is dirty, and an edit followed by its undo changes nothing. When the saved position can no longer be reached, because a new edit dropped the redo branch it sat in or the 256-command limit trimmed the state before the first kept command, the scene stays unsaved until the next save. Play mode does not change this: Play sets the history aside and starts an empty one for the play's own edits, Stop puts the earlier history back, so an edit made before Play can still be undone after Stop, and the scene is as saved or unsaved as it was when Play was pressed (saving while playing writes the snapshot, so that counts as saved). The play's own edits are what [Keeping the play's edits](#keeping-the-plays-edits) offers to bring back. A command also has `reapply`, which applies it to a restored scene after re-reading what it captured from that scene, and says whether the entities it needs were there.

## Play mode

Particle emitters preview in the viewport: in edit mode only the selected `ParticleEmitter`s are handed to the renderer, simulating while their `playing` is set, so an unselected emitter leaves the scene still and a selected one runs live; the inspector shows a Restart button under the component that starts its particles over, burst included. In play mode every emitter runs ([rendering.md](rendering.md#particles)). Colour members whose names begin with `color` get HDR colour pickers.

Play (Ctrl+P, the Play menu, the button on the menu bar) serialises the scene to an in-memory snapshot and switches the world to the simulation pipelines: the fixed steps with physics ([physics.md](physics.md)), the scripts ([scripting.md](scripting.md)), the animators ([world.md](world.md#animation)) and the audio sources ([audio.md](audio.md)) start running. The editor camera, gizmos, inspector and hierarchy keep working on the live entities; moving a dynamic body with the gizmo teleports it. Pause (Ctrl+Shift+P, the Play menu, the button beside Stop on the menu bar, which then reads Resume) freezes a playing scene: the world runs its edit pipelines, so no fixed step, physics, script or animation runs, and the audio device is paused, while the title reads `[paused]` and the fixed-step remainder is kept, so Resume carries on from the same state. Game input goes to the scripts only while running; held keys are released at the pause. The inspector, hierarchy and gizmos act on the frozen scene, and their edits show at once: moving a body with the gizmo places its entity, and the body follows on the first step after Resume, as it does when a script or the gizmo moves it while playing. Stop from a pause restores the snapshot exactly as from play. A script's `game.quit()` is the Stop button, prompt included, and the editor stays open; its `game.loadScene(path)` replaces the running scene in the open tab with the project's file, as the player does, without opening a tab or touching the snapshot, so Stop goes back to the scene play started from. The play's edits until then were made to the scene that left and are dropped rather than offered back, and so are the ones made to the loaded scene ([scripting.md](scripting.md#game)). `Editor::pause`, `resume` and `isPaused` are the API for tests. Stop restores the snapshot, which also discards every body, resets the script runtime so the scripts' state starts over, stops every sound, asks what to do with the edits made while playing ([below](#keeping-the-plays-edits)), and keeps the selection by identity. A scene without an `AudioListener` is heard from the editor's camera, which the editor hands the audio device every frame; skinned meshes are posed in edit mode too, so a model stands in its skin's rest pose rather than its bind pose. Saving while playing writes the snapshot, not the running state. The rotating object of the roadmap's M2 criterion is the `Spin` component's system.

The game gets input while playing when the viewport has the keyboard focus (click into it) and the fly camera is idle: the editor then hands the platform's events to the `platform::InputState` the scripts read ([scripting.md](scripting.md#input)), with pointer positions made relative to the viewport image, mouse presses only over the image, and W, E, R and F going to the game instead of the gizmo shortcuts. A touchscreen's fingers go the same way: positions relative to the image, and a finger that lands outside the image's rectangle is not the game's. The rectangle decides rather than ImGui's hover, which follows a finger's synthesised mouse only from the next frame. Dear ImGui and the viewport never see the finger events themselves, only the mouse SDL synthesises from the first finger ([platform.md](platform.md#events)), which clicks, picks and drags gizmos as a left button does; the fly camera needs the right button, which no finger is. Scripts get the viewport's camera and the image's size for `camera.ray` ([scripting.md](scripting.md#camera)), and so does the audio listener of a scene without one. The game UI ([gui.md](gui.md)) sees the pointer first: a press on a button, with the motion and release that follow it, is the UI's and never reaches `InputState`, and everything else goes on to the game. While playing with the Game panel on screen all of that is the Game panel's instead: the game input needs the Game panel focused, positions are relative to its image, and the camera is the scene's. When the viewport loses the focus or the right button takes the camera, everything held is released. View, Physics colliders draws every collider's outline over the scene, in edit mode as in play mode. View, Light gizmos (off by default) draws each spot light's volume as a wireframe cone in edit mode only: the apex at the light, the axis along its direction, a ring of radius `range * tan(outerAngle)` at `range` with four lines to it, and a dimmer ring for the inner angle, in the light's colour. It follows the entity and the inspector's values live; play mode, captures and exported players draw nothing. The Camera inspector shows a projection combo, FOV for perspective or height and far plane for orthographic. View, Camera gizmos (off by default) does the same for every enabled `Camera` entity, from `world::buildCameraList`: a rectangle on the near plane, another 2 m past it (`CameraGizmoLength`; the projection has no far plane to draw), and four lines from the camera to that far rectangle, at the field of view and the Game panel's aspect ratio, or the viewport's while the Game panel is not on screen. Orthographic gizmos draw a box of the view height, with parallel sides between the near rectangle and the rectangle 2 m beyond it. Both toggles are saved with the layout like the panels.

### Keeping the play's edits

A change is an edit the user made in the editor while play or pause was active: a command pushed on the play's own `CommandStack`, such as an inspector edit, a gizmo move, a rename, a reparent, or an entity added or deleted. What the simulation did (physics, scripts, animation, sounds, entities a script spawned) is not a change, which is why the list is the commands rather than a diff of the world, and neither are asset edits (materials, texture settings), which act on the database and outlive the stop. An edit that was undone is not listed.

Stop (Ctrl+P, the Play menu, the button) with no change stops at once. With changes it opens a dialog listing their descriptions in order, with four choices:

- **Keep** restores the snapshot, then re-applies the listed commands to it in order through `reapply` and puts them on the undo history. The scene is unsaved, and undo puts back what the restored scene held, not the value the simulation had reached.
- **Save as...** restores the snapshot, re-applies the commands, writes the result to the path in the dialog (the path field and Browse of Save scene as, starting in the project's `scenes` folder) and restores the snapshot again: the open tab keeps the original scene, its history and its saved state. A path that cannot be written, or the open scene's own file, is reported in the dialog and play goes on.
- **Discard** is what Stop always did: the edits are dropped.
- **Cancel** closes the dialog and plays on.

A command whose entity is not in the restored scene, such as an edit to something a script spawned, is skipped, logged, and counted: after Keep or Save as the dialog stays up to say how many, and Close ends it. A composite (a multi-selection edit) keeps the parts whose entities are there. The history holds 256 commands, so a long play drops the oldest; the dialog says how many fell out and cannot be kept.

The routes that stopped play silently go through the same dialog first, and continue once it is answered: switching or closing the scene's tab, New scene and the tab bar's `+`, Open scene and Project scenes, New and Open project, and quitting (after Keep, quitting then asks about the unsaved scene as usual). Cancel abandons the route too. The API calls `openScene`, `openProject`, `newScene`, `switchToTab` and `closeTab` still stop at once, dropping the edits. `Editor::requestStop`, `playChanges`, `keepPlayChanges`, `savePlayChangesAs`, `discardPlayChanges`, `cancelStop`, `skippedChanges` and `stopPromptOpen` are the API for tests.

## Game view

View, Game opens a second panel, tabbed behind the Viewport in the default layout and closed at start; drag it beside the Viewport to see both, and out to a window of its own where multi-viewport is on. It shows the scene as the player would: through the first enabled `Camera` entity at the panel's aspect ratio, or, when the scene has none, through `world::fallbackCamera()`, the view the player falls back to, with one warning in the log until a camera appears. It works in edit mode as in play mode. Exposure and bloom strength come from that camera; the Viewport fly camera uses exposure 1.0 and bloom strength 0.04. The Viewport keeps the fly camera, the gizmo, the picking, the outline and the debug lines; the Game view draws none of those. While it is on screen the editor declares a second `addScenePasses` in the same graph (ADR-0021), which costs what the Viewport's view costs, including its own shadow cascades; a closed or hidden panel has no target and declares nothing, so the capture flags and the default layout draw one view. The Statistics panel shows the Game view's draws and triangles on their own line. The game UI is part of that view. The editor lays the canvases out against the panel's image every frame, in edit mode too (the panel's size is the target's, with the whole image as the safe area), draws them over the Game view's scene with the same overlay pass the player uses, and, while playing, offers the Game panel's pointer events to the UI before the game. The UI takes no input in edit mode, and the panel being closed, hidden or paused lets go of any button held. An element selected in the Hierarchy, a canvas or anything under one, is outlined over the image. Moving an element by dragging in the panel is not there: the anchors and offsets are fields in the inspector. `editor_tests` covers it: the second view's statistics, the script view's camera and size in edit and play mode, the target released when the panel closes, the fallback with its one warning, and the UI laid out against the panel in edit mode and drawn into it.

The Game view can be a window of its own (drag its tab out of the editor's window). Pointer events carry the window they arrived in, and `WindowOrigins` (`WindowOrigins.h`, refreshed each frame from ImGui's viewports) gives that window's origin in ImGui's screen space, so a mouse or touch position reaches the scripts relative to the image whichever window it is in; a window it does not know is the main one. Game input goes to the scripts only while the Game panel has the focus, in whichever window; W/E/R/F belong to the Scene view's hover, and Ctrl+P and the other editor shortcuts work from every window. Closing or resizing a panel's window is not the editor's: `sonnet_editor` ignores a close request or a resize from a window other than its main one. The panel keeps drawing while the editor's main window is in the background, since the frame loop does not wait for the focus, and while play is paused. `editor_tests` covers the mapping through `WindowOrigins` without a window, and `platform_tests` the ids on the events.

## Projects and scenes

A project is a folder with a `project.json` ([assets.md](assets.md#project-file)), opened from the command line (`sonnet_editor <folder>`), the File menu, or the recent list in the preferences. A project whose `module` is not the one the editor was built with is refused before anything is read, so a generic editor never opens a game module's scenes and drops their components on save ([player.md](player.md#game-modules)). Opening a project loads every `.prefab.json` under it and then the start scene, or the tabs it had open when it was last closed ([Scene tabs](#scene-tabs)); New project writes the manifest and a starter scene (a ground plane, a box, a sun and a camera), which is also the scene an editor without a project starts from. The desktop editor started without a folder reopens the most recent project of the preferences (`reopenLastProject`, on by default; set it to `false` in `preferences.json` to start on the starter scene). A folder that is gone or no longer a project logs a warning, is dropped from the recent list and leaves the starter scene; only that one entry is tried. A folder on the command line wins, and a capture run or a headless platform never reopens. Open scene... asks for a `.scene.json` with the system's file chooser, and Project scenes lists the project's own; Ctrl+S saves, and Save scene as asks for a path ([File dialogs](#file-dialogs)).

### Scene tabs

Every open scene is a tab along the top of the viewport. Open scene and New scene add one (opening a scene that is already open switches to its tab), the `+` at the end of the bar adds a starter scene, a click switches, and the tab's close button, Close scene and Ctrl+W close one; the dot on a tab marks unsaved changes, and closing such a tab asks to save (when it has a file), discard or cancel. Closing the last tab leaves a fresh starter scene. Only the active scene lives in the world. Switching serialises it to scene JSON, the format play mode's snapshot uses, and loads the other from its own JSON, so each tab keeps its unsaved edits, its undo history its selection (commands refer to entities by UUID, which the round trip keeps) and its viewport camera (position, heading, speed and the pivot, so switching back restores the view exactly; a new scene starts from the default camera); the gizmo mode and the panels are shared. Switching or closing stops play mode first, asking about its edits ([Keeping the play's edits](#keeping-the-plays-edits)). A scene that fails to load leaves the tabs as they were. Opening another project closes every tab, discarding unsaved changes as it always has. `Editor::tabCount`, `activeTab`, `switchToTab`, `closeTab`, `tabTitle` and `tabDirty` are the API for tests.

**Reopening.** Closing a project, by quitting or by opening another, records its tabs in `preferences.json` under `openScenes`, keyed by the project folder: the scene files in tab order and the active one. Untitled scenes are left out, since [crash recovery](#crash-recovery) already keeps unsaved work, and only the recent projects keep an entry. Opening the project again, from the command line, the recent list or Open project, reopens those scenes as tabs instead of the start scene and activates the recorded one. A scene file that no longer exists is skipped with a warning; when none of them opens, the start scene opens as before. A capture run (`--screenshot`) and a headless editor neither read nor record the list. `Editor::setRememberOpenScenes`, `setPreferencesFile` and `openScenes` are the API for tests.

### File dialogs

The operating system's chooser, through SDL3's `SDL_ShowFileDialogWithProperties`, modal to the editor window. `editor::FileDialog` owns the call. SDL answers from its own thread, so the result waits in a mutex-guarded slot that `Editor::update` takes from; nothing touches ImGui off the main thread. One chooser is open at a time, so a second Browse does nothing until the first is answered.

- **Browse...** beside the Path field of New project, Open project and Export opens a folder chooser; in Save scene as it opens a save chooser filtered to `*.scene.json`. It starts at the field's value, or its nearest existing parent. The pick fills the field and the user still confirms with OK.
- **Import** in the Assets panel opens a chooser that picks several files at once (`FileDialogRequest::multiple`; every pick is in `FileDialogResult::paths`) and imports them ([Importing assets](#importing-assets)).
- **File > Open scene...** opens a `.scene.json` chooser and loads the pick as the asset browser does: in a tab of its own, or by switching to the tab that has it.
- **Ctrl+S and Save scene** on a scene with no file go straight to the save chooser, and so does Save scene as; the pick saves the scene. The result only applies while that scene is still the one in front and still has no file. A scene saved under a new name, picked in the chooser or typed in the path field, always ends in `.scene.json`, since the choosers keep the typed name: `helmet` and `helmet.json` save as `helmet.scene.json`, so the scene shows under Project scenes. The same goes for the Save as of the play-mode Stop dialog.
- A cancel changes nothing. An error, or no chooser at all, is shown in the modal (logged when there is no modal) and leaves the typed path as it was; a save that could not open its chooser falls back to the Path modal.

The typed Path field stays: it is the fallback when no chooser can open, and how headless tests drive the editor. A headless editor (the offscreen and dummy video drivers) never opens a dialog and reports that none is available. On Linux the backend depends on what is installed: `xdg-desktop-portal` with a backend for the desktop, or `zenity` or `kdialog`. With none of them the error says so and the typed field still works. `Editor::setFileDialogBackend` injects a fake `IFileDialogBackend` for tests; `chooseSceneToOpen`, `chooseSceneToSave`, `saveSceneOrChoose`, `browseModalPath` and `chooseAssetsToImport` are what the menu and the buttons call.

### Quitting

Every way out goes through `Editor::requestQuit`: the window's close button, the OS quit request, File > Quit and Ctrl+Q. With no unsaved scene the editor quits at once. Otherwise a dialog lists the scenes with unsaved changes and offers Save All, Discard and Cancel (Esc); a second request while it is open does nothing. Save All makes each dirty tab active in turn to save it, then quits. If a save fails, or a scene has no file yet, the editor stays open and the dialog says which; the tab the user was in comes back, except that a scene without a file stays in front so Save scene as can name it. Discard quits without saving, Cancel keeps running. A `--screenshot` capture run exits without asking. `dirtyTabs`, `quitPromptOpen`, `saveAllAndQuit`, `discardAndQuit` and `cancelQuit` are the API for tests.
 Failures (a missing prefab, a newer file version, an unreadable file) are logged with their origin and the editor keeps a usable scene.

The panel layout is kept: the desktop editor writes it to `layout.ini` beside `preferences.json` (Dear ImGui's ini: the dock tree, window positions and sizes) a few seconds after a change and when it closes, and reads it on the next start, so a log split from the assets stays split. The same file carries the view state, in a `[SonnetView][View]` section written by a custom `ImGuiSettingsHandler` (`LayoutSettings`): which of the Viewport, Game, Hierarchy, Inspector, Log, Assets and Statistics panels are shown, the statistics overlay, the physics colliders and the light gizmos. A file from before that section leaves them at their defaults. A missing file, or one whose dockspace is not split, gets the default arrangement. A file that is not sound is not handed to Dear ImGui at all ([Layout checks](#layout-checks)). A headless editor keeps no layout file unless `Editor::setLayoutFile` is called.

#### Layout presets

View > Layouts switches the whole arrangement at once. There are two built-ins, built in code with the dock builder, and the user's own:

- **Default** is the arrangement above (the Game panel closed, colliders and light gizmos off). View > Reset layout is the same thing (`Editor::resetLayout`).
- **Play** puts the Viewport and the Game panel side by side between a narrow Hierarchy and a narrow Inspector, with Log, Assets and Statistics closed (View brings them back as tabs beside those two) and the colliders drawn.
- **Save current as...** asks for a name and writes `<prefPath>/layouts/<name>.ini`, the same ini as `layout.ini`: the dock tree, the view state and the dock root's size. The name is sanitized to a file name (letters, digits, space, `-` and `_` stay, anything else becomes `_`). `Default` and `Play` are reserved, whatever their case, and a name that exists asks before it is replaced. **Delete** removes a saved preset.

A preset is applied between frames: `Editor::applyLayout` records the name and the next `update` loads it before the ImGui frame opens (`LoadIniSettingsFromMemory` replaces an already docked tree, so no node needs removing first). Because ImGui keeps the saved absolute split sizes and only clamps the root, every dock `Size` and `SizeRef` is scaled by the current dock root over the size the preset recorded, so a preset saved on a larger display keeps its split fractions. `layout.ini` itself is not scaled across display sizes. A missing preset, or one without the view section or a dock tree, or one that fails the [layout checks](#layout-checks), is skipped with a log warning and the current layout stays. The load is always between frames: `LoadIniSettingsFromMemory` inside a frame loses dock data upstream ([ocornut/imgui#8518](https://github.com/ocornut/imgui/issues/8518)).

#### Layout checks

Dear ImGui trusts the ini it reads. Its dock reader accepts a node with no size, a missing parent, a repeated id or a node that is its own parent without a word, and what follows is an assertion, a crash or a hang ([ADR-0036](decisions/0036-dear-imgui-stays-the-editor-ui.md); upstream [#7480](https://github.com/ocornut/imgui/issues/7480), [#7705](https://github.com/ocornut/imgui/issues/7705)). So `layoutIniProblem` (`Layout.cpp`) reads the file as text first, with no `imgui_internal.h` dock structures, and refuses it when:

- the file does not end at the end of a line (a cut file);
- a dock line is not `DockSpace` or `DockNode` followed by `key=value` pairs in the order ImGui reads them (a line out of order is skipped silently by ImGui), has an unknown key, or has a value out of range (ids are non-zero hex, positions and sizes are within 16 bits, flags are 0 or 1, `Split` is X or Y);
- a root has no `Pos` and `Size`, or a child has no `SizeRef`;
- a root `Size` or a child `SizeRef` is zero or negative;
- an id appears twice, a parent is missing or comes after its child, the parent is not a split, or it already has two children, or the tree is deeper than 64 or has more than 1024 nodes;
- a `[SonnetView][View]` line is not `key=value`, a panel flag is not 0 or 1, or `DockSize` is not `W,H`;
- a `[Window]` entry is docked (`DockId=`) in a node the file does not describe.

A file with no dock tree or no view section passes this check (an ini from before them still loads); a preset also needs both, as above. Unknown keys of the view section are ignored, as the reader ignores them. The check does not read the windows' own `Pos` and `Size`. A zero size did not assert in a Debug build here (the splits just load without proportions), but it is refused all the same, as the upstream reports ask for.

The startup `layout.ini` is checked in `Editor::setLayoutFile`, before Dear ImGui is pointed at it on the first frame. A file that fails is renamed to `layout.ini.rejected` beside it (an earlier `.rejected` file is replaced), never deleted; the reason, with the line, is logged as a warning, and the editor builds the default arrangement. If the rename fails, the editor keeps no layout file for that session. A refused preset stays where it is.

Preferences live in `preferences.json` under `Platform::prefPath("sonnet", "editor")`: the recent projects, the scene tabs each had open ([Scene tabs](#scene-tabs)), whether the Assets panel shows a list or a grid ([Grid view](#grid-view)), whether to reopen the last one at start and the external editor command. A `file:line` in the log panel is a link that runs that command with the placeholders filled in (`code --goto {file}:{line}` by default). Log records name repository-relative files and binaries carry no build-machine paths, so the editor finds the file at click time: under `sourceRoot` when set, otherwise in the directories from the executable's upwards, which finds the checkout a build directory lives in. A file found nowhere is a warning, not an empty document in the external editor.

The log's rows are selected like a list: a click selects a row, Shift extends to it, Ctrl toggles it, Ctrl+A selects every row shown, dragging from empty space draws a selection box, and Escape or a click on empty space clears it. Ctrl+C, or Copy in the right-click menu, puts the selected rows on the clipboard, one line each as `time [level] [module] file:line message` (the location left out when the record has none); Copy all copies every row the level and text filters show. Rows the filters hide are not copied even when selected. A click on the `file:line` link opens the file and leaves the selection alone; a click anywhere else on the row selects it. The selection follows the records, not the row positions, so new records, the oldest rolling out and a change of filter keep it; Clear empties it.

### The main window

The desktop editor opens its window where it was closed: `window.json` beside `layout.ini` holds the window's logical size, its position, whether it was maximized and the display it was on. It is a file of its own, not part of `preferences.json`, because `main` reads it before the window exists, while `Preferences::load` runs inside the `Editor` constructor and `Editor` rewrites that file whole. It is written when the editor closes. A layout preset leaves the window alone (a preset must not move or resize it), and a capture run or a headless platform neither reads nor writes it and opens at 1600x900.

The display is stored by its name and bounds, which survive a restart where SDL's display ids do not, and the position is relative to the display's top-left, so it follows a monitor that moved in the arrangement. On restore (`editor::placeWindow`) the display is the connected one with the same name and bounds, else the same name and size, else the same name. A saved rectangle with at least 64 pixels each way on some display's usable area (taskbar and dock excluded) opens as it was, its size clamped to the display's usable size. The window is created with the position and the maximized flag, so it does not flash at the wrong place first; a maximized window still returns to the saved rectangle on restore, which `platform` tracks ([Window](platform.md#window)).

**Fallback.** When the saved display is not connected, or the rectangle would be off every display, the window opens centred on the primary display at the saved size clamped to its usable area, keeping the maximized flag. That display is not the user's choice, so `WindowPlacement::fallback` is set, and a window still as it opened (the same size and display, a position within 48 pixels, which absorbs a window manager's title-bar shift) does not overwrite the saved state: a laptop undocked once keeps its monitor for the next time it is docked. Moving or resizing the window makes the new place the saved one. There is no second remembered display. **Wayland** ignores a requested position (`Platform::canPositionWindows`), so only the size and the maximized flag are restored there. Without a saved file the window opens centred on the primary at 1600x900, clamped to its usable area.

`layout.ini` is not scaled across display sizes ([Layout presets](#layout-presets)); opening the window at its saved size on the saved display removes most of that mismatch.

### Crash recovery

The desktop editor keeps the unsaved scenes where a crash cannot take them, in `Platform::prefPath("sonnet", "editor")/recovery/<project>/`, one folder per project (the project folder's name and a hash of its path; `no-project` for an editor without one). `editor::Recovery` owns the files and `Editor` the tabs; a capture run (`--screenshot`) and a headless editor keep none.

```
recovery/<project>/
  session-<session>.lock          locked for as long as that editor runs, removed on a normal exit
  recovering-<session>.json       written before a restore, removed once it has proved itself
  <session>-<tab>.recovery.scene.json   one unsaved scene
  quarantine/<unix time>/         files that are never restored automatically
```

Several editors can have one project open, so every file belongs to a session (a random 64-bit name, so two editors started in the same millisecond differ). A session is **live** while its lock file is locked: `core::FileLock` holds an OS lock (`flock`, `LockFileEx`) on it for the life of the editor, and the OS drops it when the process ends, however it ends, so there is no PID to look up and none to reuse. A session whose lock file can be locked, or that has none, is **stale**: that editor died. An editor on a filesystem that cannot lock runs with recovery off and says so in the log.

A recovery file is the scene JSON itself with one extra `recovery` key (the scene's own path, which may be empty), which the scene loader ignores, so it is an ordinary scene file.

- **Autosave.** Every 30 seconds, and when the window loses the focus, each tab with unsaved changes is written to its recovery file through a temporary file and a rename, so a crash mid-write leaves the previous file whole (leftover `.tmp` files are deleted at the next start). Nothing is written while playing, whose scene is the snapshot, nor before the restore decision below. The user's own scene files are never touched. Serialising a large scene is on the main thread; it is once per interval.
- **Clean exit.** Saving a tab, closing it (Save, Discard or the quit dialog's Discard), opening another project and quitting through the normal path remove that tab's recovery file; the editor's destructor removes the rest and the lock. A start with no lock and no files has nothing to ask.
- **Unclean exit.** A stale session found at start means that editor did not end normally. With its recovery files present a dialog lists the scenes and offers **Restore**, **Discard** (deletes them) or **Open without restoring** (Esc; keeps them, and they are offered again at the next start). A project's session begins when it is opened, so a crash is offered when that project is next opened, from the command line or the menu. A start offers the files of stale sessions only: a live editor's files, lock and restore marker are never listed, quarantined, restored or deleted, so a second editor opened on a project the first still has open is offered nothing and the first's autosaves survive its Discard and its exit. Starting takes the stale session's lock and keeps it until the answer is final (Restore finishes, or Discard), so two editors started together cannot both be offered the same files: the loser sees them as live. **Open without restoring** releases the lock and leaves the files and the lock file, so the next start offers them again. Two editors can still save the same scene file; recovery does nothing about that, so save before switching.
- **Restore.** Each scene opens in a tab of its own, unsaved, with its file path when it had one (a tab of the same file, such as the start scene a project opens, is replaced rather than doubled, and the untouched starter scene of a fresh editor makes way). A recovered scene with no path is untitled, so Save asks for one ([File dialogs](#file-dialogs)). The undo history is not part of a recovery file, so a restored scene starts with an empty one: its edits from before the crash cannot be undone, and the scene stays unsaved until it is saved.

**The crash-loop guard.** A recovered scene may be what crashed the editor, so a recovery set is tried at most once. `recovering-<session>.json` (named after the restoring session, the files it names and the attempt) is written before anything is loaded. It is deleted only when the restored scenes loaded without error and the editor has then run 10 seconds or 600 frames of normal updates (not while playing); the restored tabs' own recovery files are written then, and the old set deleted. A normal exit before that counts as success. If the marker of a stale session exists at the next start, that restore itself crashed (a live editor's marker is a restore in progress and is ignored): nothing is offered, the files it names are moved to `quarantine/<unix time>/`, the editor starts with the default scene and the log warns with the quarantine path. A file that does not parse, or that `world::loadScene` rejects, is quarantined the same way and the rest are still offered. Autosave does not start until the decision is made, and after a Restore not until the marker is gone, so a new crash cannot overwrite the set being restored. Quarantined files are never restored or written to; open one by hand as an ordinary scene file (File > Open scene).

`Editor::setRecoveryDirectory`, `recovery`, `recoveryPromptOpen`, `recoverableScenes`, `restoreRecovered`, `discardRecovered`, `keepRecovered` and `autosaveNow` are the API for tests, which simulate `kill -9` by copying the recovery directory while an editor runs (the copy's lock files are unlocked, so its sessions are stale). `Recovery`'s own tests cover the interval, the atomic write, and the lock and marker state machine (clean exit, crash, crash during restore, settling) without a device, and simulate several editors in one process, since two handles of one process conflict like two processes do and dropping a `Recovery` without `end()` is `kill -9`: a second editor offered nothing while the first runs, the first's files surviving the second's Discard and exit, a crash found after the other editor exited normally, one editor's restore marker leaving another's files alone, and two starts racing for one crashed session.

## Fonts

The editor draws its text in [Inter](https://rsms.me/inter/), embedded so every platform shows the same glyphs. `tools/generate_ui_fonts.py` cuts it from Google Fonts' variable `Inter[opsz,wght].ttf` (checked at 4.001) into `InterFontData.cpp`: ImGui's stb_truetype reads only a font's default instance, so the script pins the axes to Regular at the 14 pixel optical size, then keeps Basic Latin, Latin-1, Latin Extended-A and a few punctuation marks, 23 KB in all. `addFonts` adds it at 14 pixels and merges the [Lucide icons](#icons) into it, moved down two pixels (`IconOffsetY`): Lucide's glyphs are centred in their em box, which sits above the baseline of Inter's text, and the offset puts an icon in the middle of a button's label. The offset belongs to the font and its size, so changing either means measuring it again: a capture of the Assets toolbar (`--screenshot-window`) shows the List and Grid buttons, and the icon's ink should be centred in the button.

What is read character by character is drawn in [JetBrains Mono](https://www.jetbrains.com/lp/mono/), cut by the same script (`JetBrainsMonoFontData.cpp`, 2.211, the same subset, Regular) and added to the atlas after Inter as its second font. A `ScopedMono` draws what is in its scope in it, at the size around it, and does nothing before `addFonts` has run: the Inspector's UUIDs and source paths, and every row of the Log panel. Anything measured with `CalcTextSize`, such as a column width, has to be measured inside the same scope. Keep it to data: labels stay in Inter.

Both fonts' licences, the SIL Open Font License 1.1, travel with them in [THIRD_PARTY_NOTICES.md](../THIRD_PARTY_NOTICES.md). The subset keeps none of Inter's private use area, where the icons live, so nothing of Inter's can win the merge over an icon.

## Floor grid

View > Floor grid toggles the viewport grid: the XZ floor at y = 0 in perspective, and the plane through the origin facing each orthographic axis view (XZ for Top/Bottom, XY for Front/Back, YZ for Right/Left). X is red, Y green and Z blue. User orthographic views omit the grid. It defaults on and is saved in user preferences. The Game view and player never draw it. Captures omit it unless `--grid on` is supplied; this does not change the saved preference.

Orthographic grids use parallel view rays and linear reversed-Z depth. Their level visibility depends on projected spacing (`orthoHeight`), with no distance or grazing-angle fade. Switching back to perspective restores the floor in that same frame.

The grid has 1 m lines, 10 m major lines and a 100 m coarse level. Each level fades out as its projected spacing becomes too small, and the whole grid fades with distance and at grazing angles. It is drawn after temporal anti-aliasing with unjittered rays and pixel-width filtering, depth-tested without writing depth; scene surfaces, including a coplanar floor, hide it. [Verification images and tests](reports/viewport-grid.md) show both the visible grid and a lit ground.

Snap to grid uses the Edit menu's Move step, 1 m by default. It remains fixed while zooming: changing a camera must not change where a drag snaps, and both perspective and orthographic images can show several grid levels at once. Orthographic zoom fades dense levels but keeps the 1 m world lattice; it does not change Move step. A custom Move step can therefore subdivide or skip visible lines. Translation snaps the moved axes to multiples of Move step in world space, so a cube snaps onto the 1 m lines even if its drag starts between them.

## Screenshots

An agent or a script often cannot capture the screen: on macOS that takes the Screen Recording permission and a window to find, and on a headless machine there is no screen. So the editor writes its own screenshots, from the command line, and quits:

```bash
sonnet_editor apps/samples/basic --scene scenes/playground.scene.json --play 3 --select Ball \
  --screenshot shots/playground.png --screenshot-window shots/playground-window.png
```

| Flag | Effect |
|---|---|
| `--screenshot FILE` | The viewport's scene, at the viewport's size, as a PNG |
| `--screenshot-window FILE` | The whole window, with the panels, as a PNG |
| `--scene FILE` | Opens this scene, relative to the project, instead of its start scene |
| `--play SECONDS` | Plays for this many seconds, not steps, before the capture, and captures while playing: `--play 3` is 180 steps of 1/60 s |
| `--grid on\|off` | Include the floor grid in the captured viewport and window; off by default |
| `--select PATH` | Selects the entity at this path of names, `Parent/Child`, so the outline and the gizmo show |
| `--shading-term TERM` | One term of the forward shading instead of the final image: `final`, `albedo`, `normal`, `sun-direct`, `shadow-factor`, `ibl-diffuse`, `ibl-specular`, `brdf-lut` or `cascade`, the View > Shading term menu's names in any case |
| `--settle-frames N` | Frames drawn after the assets have loaded, before playing or capturing; 10 by default |
| `--render-size WxH` | The player's: draws the scene at this size and scales it to the window. The editor takes the flag and refuses it, since its viewport is its panel's size |
| `--transmission-downscale N` | The player's: sets `RendererSettings::transmissionDownscale` (1 to 8) for the run. The editor takes the flag and refuses it |
| `--transmission on\|off` | The player's: sets `RendererSettings::transmission` for the run. The editor takes the flag and refuses it, since it always draws transmission |

The table, its parser and the run that steps a capture through its frames live in `runtime` (`sonnet/runtime/Capture.h`) and are shared with the player, which takes `--screenshot`, `--scene`, `--play`, `--shading-term` and `--settle-frames` with the same meaning and writes its scene at its window's size ([player.md](player.md#capture-runs)); `editor::CaptureRun` steps that run through the editor. `sonnet_editor --help` prints the same list, from the table the parser reads, with the shading terms and the exit codes, and opens no window; `tools/check_docs.py` fails when a flag in that table is missing from this section, or a flag the player takes from [player.md](player.md#capture-runs). A project and one of the two screenshots are required, and any mistake in the arguments fails the run rather than starting a different one. The run waits until the viewport has a target and `AssetDatabase::loading` is false, giving up after two minutes, then draws the settle frames, plays, selects, draws three more frames so the panels lay out what the selection shows, and captures both images from one frame. With `--play`, those three frames play too. Meanwhile the editor steps at a fixed 1/60 s instead of the wall clock, so `--play 3` is 180 steps however fast the machine draws. Before playing it seeds the scripts' `math.random` with a fixed value, which Lua otherwise seeds differently in every process, so a scene whose scripts draw random numbers, like the playground's spawner, plays the same too: the same arguments give the same image run after run, byte for byte. Five runs of the playground with `--play 3`, and three with `--play 10` and six crates on the multi-threaded physics, each wrote one image. The exit code is 0 once both files are written and 1 on any failure, which the log says. The viewport image is the render target's bytes, already display-encoded by the tone mapper, so it matches the screen; the window image is the swapchain image the frame presented, which needs `ISwapchain::readable` (every desktop driver, Lavapipe's headless surface and MoltenVK have it). Both are opaque: the scene's alpha is not coverage.

The same thing is an API for tests: `Editor::requestScreenshots` copies the next frame's viewport and window out, `afterPresent` waits for that frame and writes them, and `takeScreenshotResult` reports the outcome. The copies and the PNG writing are `runtime::Screenshots`, which the player's game uses too. `editor_tests` runs a capture of a new project's starter scene on Lavapipe, playing and with the box selected, and reads both PNGs back.
