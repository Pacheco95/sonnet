# platform

Window, input events, the application callback interface and file-system paths, behind interfaces owned by this module, with SDL3 as the only implementation ([ADR-0002](decisions/0002-sdl3-over-glfw.md)). Depends on `core`, SDL3 and the Vulkan headers.

| Header | Contents |
|---|---|
| `Platform.h` | `Platform`: owns the SDL video subsystem, creates windows, exposes paths, opens content and exposes the Vulkan loader |
| `Content.h` | `ContentStream`: a seekable, read-only stream over the game's content |
| `Window.h` | `IWindow` and `WindowDesc`; the SDL window handle for Dear ImGui's backend and relative mouse mode |
| `Input.h` | `Key` (physical positions), `MouseButton`, `Modifiers`, and their names both ways |
| `InputState.h` | `InputState` and `Touch`: the keyboard, mouse and touches as state, fed from events |
| `MouseLock.h` | `MouseLock`: when a game's request to lock the pointer is applied, let go and taken back |
| `Event.h` | The event structs and the `Event` variant |
| `Application.h` | `IApplication` (`iterate`, `event`, `nativeEvent`), `AppResult`, the `createApplication` declaration every executable defines |
| `EntryPoint.h` | Included once per executable; provides `main()` through SDL's callbacks |

## Lifecycle

The engine does not own `main()`. `EntryPoint.h` defines SDL's `SDL_AppInit`, `SDL_AppIterate`, `SDL_AppEvent` and `SDL_AppQuit` and forwards them to `platform`, which:

1. On init, initialises logging ([Logging](#logging)), constructs `Platform` (SDL video subsystem only), converts the arguments (without the program name) and calls the executable's `createApplication`. An exception here is logged at `critical` and ends the process with a failure code.
2. On iterate, calls `IApplication::iterate` and emits the Tracy frame mark.
3. On event, hands the raw SDL event to `IApplication::nativeEvent` (Dear ImGui's SDL3 backend consumes it in `ui`), then translates it and calls `IApplication::event` when the engine has a type for it; SDL events without an engine type go no further.
4. On quit, destroys the application, then `Platform`.

`IApplication::iterate` and `event` return `AppResult`: `Continue`, or `Success` and `Failure` to end the loop. On desktop SDL calls iterate in a loop; on iOS and Android the OS calls it, which is why frame ordering lives in the application and not in a loop the engine writes.

### Background and foreground

On Android and iOS the OS sends the application to the background and brings it back, and the engine has four events for it: `WillEnterBackground`, `DidEnterForeground`, `LowMemory` and `Terminating` ([ADR-0018](decisions/0018-mobile-export.md#where-it-lives)). SDL dispatches its lifecycle events to `SDL_AppEvent` at once, from an event watch, after the events already queued, so they arrive on the main thread between two iterations. What the player does with them is in [player.md](player.md#the-lifecycle); the editor runs only on the desktop, where they do not arrive.

**Which SDL events get a type.** An SDL event gets an engine type when an application acts on it. SDL has two more, `SDL_EVENT_DID_ENTER_BACKGROUND` and `SDL_EVENT_WILL_ENTER_FOREGROUND`, which stop at `translateEvent`: on Android SDL sends each straight after its partner, from the same pause or resume, with nothing in between (`Android_OnPause` and `Android_OnResume` in `SDL_androidevents.c`). On iOS they are `applicationDidEnterBackground` and `applicationWillEnterForeground`, and an application that has stopped drawing at `WillEnterBackground` (`applicationWillResignActive`) and starts again at `DidEnterForeground` (`applicationDidBecomeActive`) has nothing to do at either. SDL also sends `WindowMinimized` before `WillEnterBackground` and `WindowRestored` after `DidEnterForeground`, and takes the keyboard focus away, which releases every key and finger held ([Input state](#input-state)).

**What happens on Android**, read from SDL 3.4's source and checked on a Galaxy S25 Ultra with `adb logcat -v threadtime -s Sonnet SDL`:

- **The surface goes before the event.** SDL's Java side calls `surfaceDestroyed`, which queues the pause for the native thread and then releases the `ANativeWindow` at once, on the UI thread. It waits for the native thread only for an OpenGL window, not a Vulkan one. The engine hears `WillEnterBackground` at its next event pump, a few milliseconds later, so a frame in between can find the surface gone: acquire or present then fails with `VK_ERROR_SURFACE_LOST_KHR`. On the phone this happened on one screen-off out of ten trips to the background, 6 ms after `surfaceDestroyed`. The swapchain handles it ([rendering.md](rendering.md#suspend-and-resume)). ADR-0018's "before the OS takes the surface away" does not hold on Android.
- **Nothing iterates in the background.** With `SDL_HINT_ANDROID_BLOCK_ON_PAUSE` at its default, SDL's event pump blocks while paused until the resume, and the generic main-callbacks loop pumps before every `SDL_AppIterate`, so iterate is not called: the player counted no frame in any background period.
- **The pause comes from `surfaceDestroyed` or `onStop`,** whichever is first. From Android 7, SDL pauses in `onStop` rather than `onPause`, and `surfaceDestroyed` came about 0.4 s after `onPause`. The resume comes after `surfaceCreated` and `surfaceChanged`, so the new `ANativeWindow` exists when `DidEnterForeground` arrives.
- **The window keeps its size.** In portrait and back, the surface was 1080×2340 before and after, and no `WindowResized` arrived. A size that did change would arrive first, since SDL delivers the queued events ahead of the lifecycle event.
- **`LowMemory` arrives on every trip to the background.** SDL maps `onTrimMemory` to it whatever the level, and Android trims a hidden application's UI each time.
- **`Terminating`** comes from `onDestroy`, with a `QuitRequested`. SDL ends the loop after it.

`EntryPoint.h` is the one public header that includes SDL, because `SDL_main.h` has to be compiled into the executable's translation unit. It is the reason `SDL3::SDL3` is a public dependency of the module; no other public header includes SDL. `Application.h` and `Window.h` forward-declare `SDL_Event` and `SDL_Window` so that `ui` can hand both to Dear ImGui's SDL3 backend without the headers.

## Logging

The log itself is `core`'s ([core.md](core.md#logging)); `platform` only adds to where it goes. On Android the entry point adds spdlog's `android_sink_mt` through `core::Log::addSink` before the first line is logged, with the tag `Sonnet`, the one `SonnetActivity` logs its arguments under, so `adb logcat -s Sonnet` shows the engine's log from startup. Android discards a process's stdout, which is why the sink is needed. The console sink stays. `platform` links `liblog` for it on Android. Nothing changes on desktop.

## Window

`Platform::createWindow` returns an `IWindow`, which reports its logical and pixel sizes, its title and minimised state, toggles relative mouse mode (the cursor hidden and motion reported as deltas, for the editor's fly camera; it reports failure, which SDL's X11 driver does without XInput2 and the offscreen driver always), exposes the `SDL_Window` for Dear ImGui, and creates a `VkSurfaceKHR` for a given instance. The surface belongs to the caller (`rhi` wraps it in a RAII object) and must be destroyed before the window. Windows are created with `SDL_WINDOW_VULKAN` and `SDL_WINDOW_HIGH_PIXEL_DENSITY`, so the pixel size is what the swapchain has to match.

`WindowDesc::frameRate` is the display rate the window asks for, 0 leaving it to the system. Only Android honours it. There `createVulkanSurface` passes it to `ANativeWindow_setFrameRateWithChangeStrategy` for the window's current `ANativeWindow`, with the default compatibility and a change only if it is seamless. It does this with every surface, since Android gives the window a new `ANativeWindow` on each resume ([Background and foreground](#background-and-foreground)) and the swapchain creates a surface for each one. The rate is a request: the display follows it while nothing else on screen asks for more, and it is back at its own rate once the window is gone. `platform` links `libnativewindow` for it on Android. The player asks for 60 fps ([player.md](player.md#frame-rate)).

**Displays and position.** `Platform::displays()` lists the connected displays, the primary first: SDL's id (valid until the display goes away), the name, the bounds and the usable bounds (the bounds without the taskbar, menu bar and dock), all in the desktop's logical coordinates, and `contentScale`, the desktop's scale in window units (`SDL_GetDisplayContentScale`, 1 when SDL cannot tell): the scale on X11 and Windows, where windows are sized in pixels, and 1 on macOS and Wayland, which size windows in points and scale them themselves. `IWindow::display()` names the one the window is mostly on. `WindowDesc::position` and `WindowDesc::maximized` open the window at a place and maximized, through SDL's creation properties so there is no flash at the default place; with `maximized`, `size` and `position` are the rectangle a restore returns to. `IWindow::position()` and `isMaximized()` report the live state. Wayland ignores a requested position and cannot report one, so `Platform::canPositionWindows()` is false there and callers keep the size and the maximized flag only.

`IWindow::safeArea()` is the part of the window that a notch, rounded corners or the home indicator leave free, from `SDL_GetWindowSafeArea`, in the window's own coordinates (the ones of `size()` and of the input events, origin at the window's top-left). Where SDL reports none, which is every desktop window, it is the whole window. The game UI insets its canvases by it ([gui.md](gui.md#layout)).

SDL3 has no query for a window's non-maximized rectangle, so `IWindow::restoredRect()` is tracked: an event watch on the window feeds `RestoredRect` every move and resize SDL reports while the window is not maximized, minimized or full screen (Windows reports a minimized window at -32000, -32000). It starts from the requested rectangle, and since only the flag decides, a window maximized by the window manager is covered too. The watch runs as SDL queues the event, on the thread that pumps events.

**A maximized window after a display scale change (Windows).** SDL 3.4.16's `WM_DPICHANGED` handler moved the window to the top-left corner Windows suggests and sized its frame for the client area at the new DPI, whether or not the window was maximized. Going down in scale that left the old DPI's frame: maximized at 100 % on a 2560x1440 monitor, then 200 % and back to 100 %, the window kept the 200 % frame at -13,-13 to 2563,1373 rather than -8,-8 to 2568,1400, with its title bar off the screen ([issue 423](https://github.com/Pacheco95/sonnet/issues/423), [the repro](reports/sdl-maximized-dpi-repro/README.md)). SDL fixed it in 3.4.20 ([libsdl-org/SDL#16641](https://github.com/libsdl-org/SDL/issues/16641)): a resizable window now takes the whole rectangle Windows suggests, which keeps a maximized layout. A restored window is not affected: resizable or fixed-size, it kept its client area (1280x720 pixels) through a scale change to 125, 150, 175, 200 and 225 % and back, and through a drag between a monitor at each of those scales and one at 100 %, and a maximized window matched Windows' own maximized rectangle at every one of them. The `sdl3` overlay port is on 3.4.20, so the engine's restore-and-maximize workaround is gone ([issue 428](https://github.com/Pacheco95/sonnet/issues/428)).

The Vulkan loader is reached through `Platform::vulkanGetInstanceProcAddr` and `Platform::vulkanInstanceExtensions`, which load the library through SDL on first use. `rhi` seeds vk-bootstrap and the Vulkan-HPP dispatcher from that pointer, so one loader is used in the process ([ADR-0006](decisions/0006-vulkan-object-ownership.md)). The library is then kept mapped for the life of the process: `Platform` takes a reference of its own to whichever library the loader pointer belongs to, through `dladdr` and `dlopen` or, on Windows, a pinned module handle, and never releases it. SDL unloads the loader when its video subsystem quits, while vk-bootstrap caches the entry points in a table it initialises once and never refreshes, so a second `Platform` in one process would otherwise leave those pointers in an unmapped library: a crash on macOS, and elsewhere a crash whenever the library does not land at its old address. `rhi_tests` covers it with a device created after an earlier device and its platform are gone.

**Wayland.** SDL picks Wayland over X11 on its own only when the compositor offers the `wp_fifo_manager_v1` protocol (fifo-v1), which SDL requires so that frame pacing does not regress; GNOME 46's mutter does not, so on it the editor and the player run through XWayland and the log says `video driver "x11"`. To test native Wayland there, set `SDL_VIDEODRIVER=wayland`; the log then says `video driver "wayland"` and the window's `client_type` is `wayland`. The engine does not set the hint itself. On Wayland the window matches its desktop entry by the application id, which the entry point sets from the executable's name ([branding.md](branding.md)); there is no per-window icon property there.

## Events

Events are values of the `Event` variant: window resize (pixel size), move (desktop position), minimise, maximise and restore, focus, the mouse leaving the window (`MouseLeftWindow`, SDL's `WINDOW_MOUSE_LEAVE`), close request, quit request, key press and release with modifiers and repeat, UTF-8 text input, mouse motion with delta, mouse buttons with click count, wheel, a finger's `TouchDown`, `TouchMotion` with delta and `TouchUp`, the active gamepad's `GamepadConnected`, `GamepadDisconnected`, `GamepadButtonPressed`, `GamepadButtonReleased` and `GamepadAxisMoved` ([Gamepads](#gamepads)), files dropped from the operating system (`FileDropped`, one per file with its UTF-8 path, then `DropCompleted` with where the drop landed; SDL's `DROP_FILE` and `DROP_COMPLETE`), and the mobile lifecycle's `WillEnterBackground`, `DidEnterForeground`, `LowMemory` and `Terminating` ([ADR-0018](decisions/0018-mobile-export.md#where-it-lives), [Background and foreground](#background-and-foreground)). `Key` names physical positions with US-layout names, so game bindings survive keyboard layouts; text input carries the layout-aware characters. The window events (resize, move, maximise, focus, the mouse leaving, close request), the pointer events (mouse motion, buttons, touches) and the drop events carry the `WindowId` of the window they came from, since the editor's panels undocked into OS windows are windows of their own and a position is relative to its window; the wheel and the key events do not, and 0 stands for a window SDL did not name. An application with one window ignores it.

Positions, the mouse's and the touches' alike, are in window coordinates: SDL's for the mouse, and for a finger SDL's fraction of the window times the window's size, which is how SDL places the mouse it synthesises from the same finger. On Android the window's size is its surface's in pixels, so these are pixels there. On a desktop with a high-density display they are the logical coordinates, smaller than the pixel size. A touch carries SDL's finger id, which stays the same from down to up. A cancelled finger, which Android sends when a system gesture takes it, ends with a `TouchUp`.

**Touches and the mouse.** SDL's synthesised mouse events stay on (`SDL_HINT_TOUCH_MOUSE_EVENTS`), so one finger works as the left button for scripts written against the mouse. A finger therefore arrives twice, once as a touch and once as the mouse, and the rules keep each report whole:

- **Only the first finger drives the mouse.** SDL tracks one finger at a time, so a second finger is a touch and nothing else.
- **A finger's landing is not motion.** Before pressing the left button, SDL moves its mouse to where the finger lands. That move (`which` is `SDL_TOUCH_MOUSEID`, the left button not yet held) keeps its position with a zero delta, since it is a jump from wherever the last finger lifted. Its moves while held are motion like a mouse's.
- **The synthesised mouse says so.** Its motion and button events (`which` is `SDL_TOUCH_MOUSEID`) carry `fromTouch`, since a finger is no cursor: the game UI does not hover with them ([gui.md](gui.md#input)).
- **A mouse or a pen is never a touch.** On Android and iOS SDL reports a mouse as a touch too (`SDL_HINT_MOUSE_TOUCH_EVENTS` defaults on there, under `SDL_MOUSE_TOUCHID`), and a pen as a touch everywhere (`SDL_PEN_TOUCHID`). Both already arrive as the mouse, so their finger events are dropped.

`InputState` keeps the two apart: the mouse's buttons and position, and the touches. A script reading the left button sees the first finger, and a script reading the touches sees every finger. A script that reads both sees the first finger in each and should use one or the other.

## Input state

`InputState` turns the event stream into what a game asks for: which keys and buttons are held, which went down or up this frame, where the pointer and the fingers are and how far they and the wheel moved this frame. The application hands it the events the game should see and calls `beginFrame` once its frame has consumed them; a key's repeats are not new presses, and losing the window's focus, or `releaseAll`, releases everything held, since those releases would never arrive. The touches are the fingers down now, in the order they went down, each with its id, position and this frame's motion (`touches()`, a span of `Touch`). `beginFrame` zeroes the motion as it does the mouse's, and a `TouchUp` removes the finger. A finger whose down the state never saw, because it landed before the game was listening, is ignored until it lifts, and losing the focus or `releaseAll` ends every touch. A tap shorter than a frame shows as the left button's press and release, not as a touch. At most `InputState::MaxTouches` (10) fingers are kept, in a fixed array, so handling an event never allocates. `toString` and `keyFromName` convert keys to and from their enumerator names (`"A"`, `"Digit1"`, `"LeftShift"`), and likewise for mouse buttons, which is how scripts name them ([scripting.md](scripting.md#input)). `setMouseLocked` and `mouseLocked` hold whether the pointer is locked to the game (`Window::setRelativeMouseMode`), as the application reports it after applying a game's request; it is not an event and neither `beginFrame` nor `releaseAll` changes it, so it is false until the application says otherwise.

### Gamepads

The platform opens one gamepad at a time, the active one, and reports only its controls (issue #498). SDL reports every gamepad present at start as added, and the first that opens becomes active; a gamepad plugged in while one is active waits. When the active gamepad is removed, the first other gamepad that opens takes its place with a `GamepadConnected`, and with none left a `GamepadDisconnected` follows. `GamepadConnected` carries SDL's name for the device and is followed by the value of each of its six axes, so a stick held while it was plugged in reads as held. The opening and the translation are `SdlGamepads` (`src/SdlGamepads.h`), which the entry point owns between the `Platform` and the application and asks after each SDL event; its events reach `IApplication::event` after the translated one. SDL's gamepad subsystem is initialised by a `Platform` that is not headless only, so tests and captures never hear a pad plugged into the machine they run on.

Buttons are named by position as SDL's `SDL_GamepadButton` is (`South`, `East`, `West`, `North`, `Back`, `Guide`, `Start`, `LeftStick`, `RightStick`, `LeftShoulder`, `RightShoulder`, `DPadUp`, `DPadDown`, `DPadLeft`, `DPadRight`): `South` is A on an Xbox pad and Cross on a PlayStation one, whatever the label. Paddles, the misc buttons and the touchpad's click have no engine name and are dropped. Axes are normalised in translation: the sticks' axes from -1 to 1 with +x right and +y up, away from the player (SDL's y is down), and the triggers from 0 to 1. SDL's range is one longer below zero; both ends reach exactly 1.

`InputState` keeps the active gamepad as it keeps the keys: `gamepadDown`, `gamepadPressed` and `gamepadReleased` with one-frame edges, and `gamepadConnected`. The sticks read through a radial dead zone (`leftStick`, `rightStick`): a stick within `StickDeadZone` (0.24) of its centre reads as centred, and beyond it the length is rescaled to start again at 0 and reach 1 at `StickFull` (0.95), the direction kept and the length never above 1, so a stick pushed part of the way reads as that fraction. Radial rather than per axis, a diagonal does not snap to an axis. The triggers have their own (`leftTrigger`, `rightTrigger`, `TriggerDeadZone` 0.12 to `TriggerFull` 0.95), and `gamepadAxis` is an axis before any dead zone. A lost focus, `releaseAll`, a gamepad replacing another and a disconnection let go of every button, the releases showing that frame, and centre the axes. SDL stops reporting a gamepad's controls moving away from rest while the application has no keyboard focus, and a stick held through the return sends no motion, so a regained focus re-sends the active gamepad's axes as SDL holds them. `reset` returns the state to a new one but for `gamepadConnected`, which only the connection events change: the editor uses it when play stops or loads a scene.

### Mouse lock

`MouseLock` decides when a game's request to lock the pointer (`input.setMouseLocked`, [scripting.md](scripting.md#input)) holds the pointer, so the player's `Game` ([player.md](player.md#the-pointer)) and the editor's play mode ([editor.md](editor.md#the-pointer-in-play-mode)) follow the same rules. The application owns one beside its `InputState`, with a function that turns relative mouse mode on or off and says whether it got it (`IWindow::setRelativeMouseMode`, or the editor's own for a Game panel in a window of its own). It offers the lock each event before the game: `event` returns true for the events that are the lock's and that the game must not see. Once a frame, before the game reads its input, `update(requested, focused)` takes the scripts' request and whether the game has the input now, applies the mode when either changes, and reports what it got through `InputState::setMouseLocked`, which is what `input.mouseLocked()` reads.

- **Locked** while the game asks and has the input. Losing the input (a pause, another panel focused) lets go, and having it back locks again.
- **Escape** while locked lets go, and is the lock's: the game does not see that press. A **lost window focus** lets go too, and stays the game's event, so its input releases what was held. SDL would take relative mode back by itself when the focus returns; the lock turns it off instead and waits.
- **A click into the game** takes it back after either, and that press is the lock's, so it is neither a shot nor the start of a drag. The click counts when the game has the input at the next `update`, which in the editor is the frame the click focused the Game panel. A request made afresh (the scripts asking false, then true) locks at once.
- **`release`** lets go and forgets a pending click: play stopping or pausing, a scene being replaced. Destroying the lock gives the pointer back too.
- **Changes of mode do not move the game's view.** The motion gathered that frame (`InputState::clearMotion`) and the motion events until the next `update` are dropped, since the first motion after the change can be the platform warping the pointer, and that jump is not the mouse's.
- **A platform that refuses relative mode** (SDL's offscreen driver, X11 without XInput2, a phone without a mouse) leaves the pointer unlocked, logs once at `info`, and is not asked again until the request or the input goes away and comes back. Escape and clicks then stay the game's, so a game that reads `input.mouseLocked()` falls back to dragging.

## Thermal state

`thermalState()` (`Thermal.h`) returns how hard the system says it is working to shed heat: `Nominal`, `Fair`, `Serious` or `Critical`, the four levels iOS names, or `Unknown`. It is cheap enough to call once a second. iOS and macOS read `NSProcessInfo.thermalState` (one Objective-C++ file, `ThermalApple.mm`). Android reads the NDK's `AThermal_getCurrentThermalStatus` and folds its seven levels into the four: none is `Nominal`, light and moderate are `Fair`, severe is `Serious`, and critical, emergency and shutdown are `Critical`. Linux and Windows have no such value and answer `Unknown`, which is deliberately not `Nominal`: a run that cannot tell has not been shown to stay cool. It is a level, not a temperature; no public in-app API gives degrees. The player's capture line reports it ([player.md](player.md#capture-runs)).

## Quitting

`canQuit()` in `Platform.h` is false on iOS and true elsewhere: whether a game may end itself. The game's `game.quit()` asks for it only where it is true ([player.md](player.md#quitting)).

## Headless

`PlatformDesc::headless` selects SDL's offscreen video driver: windows exist and report sizes, nothing is displayed, and the Vulkan library still loads, so the same code paths run in tests and CI. SDL assertions abort instead of opening their dialog, and the gamepad subsystem stays off ([Gamepads](#gamepads)). `platform_tests` uses it for every test that needs the subsystem.

## Paths

`Platform::basePath` is the directory next to the executable on desktop and the bundle on mobile; `Platform::prefPath` is the per-user writable directory, created on demand. Both come from SDL so the mobile milestone does not change them.

`Platform::openContent(path)` opens the game's content read-only, as [ADR-0018](decisions/0018-mobile-export.md#packaging) decides. It returns a `ContentStream` over an `SDL_IOStream`, which `Content.h` forward-declares so SDL stays out of the header. The stream has `read` (up to a buffer's size, short only at the end), `readExactly`, `seek` (from the start; past the end is an error), `tell`, `size` and `readAll`. Errors are `Io` errors naming the path. A stream has one position, so it is not shared between threads. The rules for the path:

- **A relative path** resolves against the content root. On Android that is the APK's `assets/`, which SDL reads in place, since the APK stores the content uncompressed. SDL first tries the relative path in the app's internal storage, so a file of that name there takes precedence. On every other platform the content root is `basePath()`.
- **An absolute path** is an ordinary file on every platform. On a phone, this is how a bundle pushed into the app's data directory runs.

`openContent` is static because it needs nothing that SDL initialises, and so `Bundle` and the renderer, which are handed a path rather than the `Platform`, can reach it. What reads through it: the bundle ([assets.md](assets.md#the-bundle)), the renderer's shaders ([rendering.md](rendering.md#shaders)) and the player's default `game.sbundle` ([player.md](player.md)). The desktop tools, project folders and the tests stay on `core::readFile`.

## Tests

`platform_tests` covers the displays (listed, the primary first, the window's among them), a window opened at a position, the restored rectangle following pushed moves and resizes and ignoring them while maximized, the move and maximise events, and `openContent` over plain files (relative and absolute paths, a missing file, seek, tell, size, a read at an offset, a short read, a move), the input state's held keys and one-frame edges, the mouse lock's rules against a stand-in for the mode (locking and letting go with the request and the input, Escape, a lost focus and the click that takes it back, `release`, the dropped motion around a change, a refused request asked once) and the headless driver refusing the real mode, motion and wheel, the release on focus loss, touches appearing, moving with a motion that resets each frame and ending, and the key names, the headless platform, window creation and sizes, paths, the Vulkan loader hook (skipped where no loader is installed) and, white-box through `src/SdlEvents.h`, the scancode and modifier mapping and the translation of every event type. The finger events go through the same translation in a headless window of known size: two fingers down at once, motion, up and cancel, scaled from SDL's fractions to window coordinates. So do a mouse and a pen reported as touches, which are dropped, the landing of a finger's synthesised mouse, and its motion and buttons marked `fromTouch` where a real mouse's are not. The mouse leaving a window translates with the window's id. The window id of each of those events is checked. The four lifecycle events translate, and SDL's `DidEnterBackground` and `WillEnterForeground` are dropped. For gamepads, `InputState` holds buttons with one-frame edges, reads the sticks through the radial dead zone with a partial push keeping its length and direction and a corner no longer than 1, reads the triggers through theirs, lets go of everything and centres the axes on a lost focus, a replacing gamepad and a disconnection, keeps `gamepadConnected` through `reset`, and names every button. With the gamepad subsystem started over the headless platform and virtual gamepads (`SDL_AttachVirtualJoystick`, limited by `SDL_HINT_GAMECONTROLLER_IGNORE_DEVICES_EXCEPT` to the tests' own vendor id), `SdlGamepads` maps SDL's buttons and axes and their ranges, makes the first pad active with its axes, ignores a second while the first is there, hands over to the second when the first goes, reports a disconnection when the last goes, and brings back a held stick's axes with a regained focus.
