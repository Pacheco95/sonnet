# Rendering

Two modules: `rhi` (render hardware interface plus the Vulkan 1.4 implementation) and `renderer` (render graph, materials, passes, engine shaders). Everything above `rhi` is API-agnostic; everything in `rhi` is deliberately shaped like Vulkan.

## Vulkan baseline

Vulkan 1.4 core is the minimum ([ADR-0001](decisions/0001-vulkan-1.4-only.md)). The device selector rejects anything lower. The engine relies on:

| Feature | Core since | Used for |
|---|---|---|
| Shader draw parameters | 1.1 | Slang lowers `SV_VertexID` through `gl_BaseVertex`, `SV_StartInstanceLocation` through `gl_BaseInstance`, and `SV_InstanceID` as `gl_InstanceIndex` less `gl_BaseInstance` |
| Timeline semaphores | 1.2 | Frame and upload synchronization |
| Buffer device address | 1.2 | Per-frame data without descriptor churn: materials, lights, clusters, the culling and skinning passes |
| Multi-draw indirect, indirect first instance | 1.0 features | GPU-driven submission ([ADR-0012](decisions/0012-gpu-driven-rendering.md), [ADR-0016](decisions/0016-instanced-batches.md)) |
| Descriptor indexing: partially bound, update-after-bind, runtime arrays | 1.2 (features required by this engine) | Bindless textures and buffers |
| Scalar block layout | 1.2 | Shared struct layouts between C++ and Slang |
| Dynamic rendering | 1.3 | No render pass or framebuffer objects |
| Synchronization2 | 1.3 | Barriers emitted by the render graph |
| Extended dynamic state | 1.3 | Fewer pipeline permutations: the front face is set per batch, so a mirrored draw needs no pipeline of its own |
| Push descriptors | 1.4 | Per-pass uniform and storage buffers |
| Dynamic rendering local read | 1.4 | Tile-friendly subpass-style reads on mobile |
| Maintenance 5 and 6 | 1.4 | Simpler pipeline and descriptor handling |
| Host image copy | 1.4, optional feature | Faster texture uploads when present; not used yet, every upload goes through staging |

Vulkan 1.4 also raises minimum limits (push constants, bound descriptor sets, image dimensions), which the design assumes.

Depth uses reversed-Z: `D32_SFLOAT`, cleared to 0, `GREATER` compare, infinite far plane. Projection uses `GLM_FORCE_DEPTH_ZERO_TO_ONE`. Clip-space Y is flipped by a negative viewport height (core since 1.1) so triangle winding stays counter-clockwise front-facing, matching glTF. A draw whose transform mirrors — a negative determinant in its upper 3×3, which a negative scale gives — reverses that winding on screen, so it is drawn with a clockwise front face ([GPU-driven submission](#gpu-driven-submission)).

## Platform notes

- **Windows, Linux**: current vendor drivers and Mesa ship Vulkan 1.4. Lavapipe (Mesa CPU implementation) is used in CI.
- **macOS, iOS**: MoltenVK 1.4+ layers Vulkan 1.4 over Metal (macOS 12+, iOS 15+). It is a portability implementation: the instance must enable `VK_KHR_portability_enumeration` and the device must enable `VK_KHR_portability_subset` when present. Geometry shaders, triangle fans and some format and tessellation features are missing; the engine uses none of them. Descriptor indexing on MoltenVK requires Metal argument buffers, which MoltenVK enables by default in recent versions; the device selector verifies the required descriptor-indexing features rather than assuming them. MoltenVK has no `drawIndirectCount` (confirmed on 1.4.1 and 1.4.2 on an Apple M4 Max), because a Metal indirect draw cannot take its number of draws from a buffer, and it encodes one Metal draw per indirect command, on the CPU, when the frame is submitted. The engine uses neither the count nor a command per draw: each batch is one instanced command, so the number a pass submits is the batch count, which the CPU knows ([ADR-0016](decisions/0016-instanced-batches.md)). Slang loads a storage-buffer element as a whole struct, and SPIRV-Cross cannot translate that load when the struct holds a pointer. So no struct in a storage buffer holds one, and vertices are pulled through a bindless array rather than a pointer in `ObjectData` ([ADR-0015](decisions/0015-bindless-vertex-buffers.md)). SPIRV-Cross types a whole bindless array as Metal depth textures when any use of it compares, and a depth texture reads as its red channel alone, so depth images have an array of their own and colour textures are never compared ([ADR-0017](decisions/0017-depth-images-in-their-own-bindless-array.md)).
- **Android**: devices launching with Android 16 or later must support Vulkan 1.4. Older devices are unsupported, which is accepted in ADR-0001. Mobile GPUs are tile-based: the render graph keeps passes mergeable and uses dynamic rendering local read for G-buffer-style reads instead of round trips to memory. Textures are shipped as KTX2 with ASTC or ETC2.
- **Loader**: SDL3 loads the Vulkan library. `SDL_Vulkan_GetVkGetInstanceProcAddr` seeds both vk-bootstrap and the Vulkan-HPP dynamic dispatcher so there is one loader in the process. The loader only has to be 1.1: the 1.4 requirement is on the physical device, because distributions ship older loaders in front of current drivers (Ubuntu 24.04 has 1.3) and the engine uses no 1.4 instance-level entry points.

## Object ownership

vk-bootstrap selects the physical device and creates the instance, debug messenger, device and swapchain. Every handle it returns is immediately adopted by a Vulkan-HPP RAII wrapper (`vk::raii::Instance`, `vk::raii::Device`, ...), which then owns it. `vkb::destroy_*` is never called. VMA is used through the Hpp bindings and destroyed before the device. RAII members are declared in reverse destruction order so lifetimes are correct by construction. Details in [ADR-0006](decisions/0006-vulkan-object-ownership.md).

## Memory

All GPU memory goes through VMA. `rhi` exposes:

- Device-local buffers and images with a staging ring for uploads: `IDevice::uploadBuffer` and `uploadImage` copy the data into the frame slot's ring at once and record the transfer into an upload command buffer that is submitted ahead of the frame's commands, so a resource uploaded at any point of a frame, or between frames, is complete for that frame's draws. Data larger than the ring gets a dedicated staging buffer released with the slot.
- Per-frame linear allocators for transient uniform and storage data: `IDevice::allocateTransient` hands out slices of one host-visible buffer per frame slot, aligned for both binding types, valid until the slot is reused.
- Budget queries through `VK_EXT_memory_budget` for the resource overlay: `IDevice::memoryBudget` reports usage and budget per heap.
- Leak detection: every allocation carries a debug name, and the device reports live allocations at shutdown in Debug builds.

## Shaders

Slang is the only shading language ([ADR-0005](decisions/0005-slang.md)). Engine shaders live in `modules/renderer/shaders/`, project shaders in the project's `shaders/` folder.

- **Build time**: `sonnet_add_shaders(<target> SHADERS ...)` (in `cmake/SonnetShaders.cmake`) runs `slangc` on each `.slang` file, emitting one SPIR-V 1.6 module per file that holds every `[shader("...")]` entry point under its own name (`-fvk-use-entrypoint-name`), scalar block layout (`-fvk-use-scalar-layout`, so C++ and Slang share struct layouts byte for byte), column-major matrices, debug information in Debug and `-O2` otherwise. The module lands in `shaders/<name>.spv` next to the target's binary, where `platform::Platform::basePath()` finds it, and a depfile makes edits to imported modules rebuild their users. `sonnet_add_engine_shaders(<target>)` does the same for the engine's own shaders, for every executable and test that renders through `renderer`. Release builds ship only SPIR-V.
- **Runtime**: `assets::ShaderCompiler` drives the Slang library with the same options as the build rule, and `Renderer::reloadShader` rebuilds every pipeline made from a module with the new SPIR-V, building all of them before destroying any so a module or pipeline the driver rejects changes nothing. The editor watches the checkout's shader sources and recompiles a changed entry-point file, or every one when a shared module such as `sonnet.slang` changes; compile errors are logged with their `file:line:column` and the previous pipelines stay ([editor.md](editor.md#shader-hot-reload)). The player ships only the SPIR-V the build produced.
- **Reflection**: the descriptor layout is the fixed one below and shaders declare the matching bindings; Slang's program layout is the reflection source when a shader has to be checked against it, and there is no separate reflection library.
- **Conventions**: the shared `sonnet.slang` module declares the bindless arrays of set 0, the per-pass buffers of set 1, the per-draw push constants and the vertex layout. Scene shaders `import sonnet` and never declare their own descriptor sets. Vertices are pulled from `vertexBuffers[objects[objectIndex].vertexBuffer]`, the bindless array at set 0 binding 5, indexed by `SV_VertexID` from the bound index buffer ([ADR-0015](decisions/0015-bindless-vertex-buffers.md)). No struct stored in a storage buffer holds a pointer: Slang loads such an element whole, however the source reads it, and Metal cannot compile the result. Pointers live in uniform and push-constant blocks, such as the frame constants. Post passes over an image (`outline.slang`) are the exception: they draw one full-screen triangle, declare the pass image binding and their own push constants, and import nothing. So is `debug.slang`, which pulls line vertices from the pass storage buffer and takes the view-projection matrix as its push constants.

## The rhi module today

Public headers under `sonnet/rhi/`: `Types.h` (handles, formats, usages, layouts, synchronization, attachments, pipeline state), `Device.h` (`IDevice`, `DeviceDesc`, `createDevice`), `Swapchain.h` (`ISwapchain`), `CommandList.h` (`ICommandList`) and `NullDevice.h` (the GPU-less implementation for tests). The Vulkan implementation lives in `src/` and is reached only through `createDevice`, the one `#if`-switched site.

- `IDevice` creates buffers, images, samplers and swapchains, hands out generation-checked handles, and runs the frame: `beginFrame` waits for the slot's previous submission on the timeline semaphore, reads that submission's timestamps, frees the resources parked in the slot, resets the pools, the transient allocator and the staging ring and starts recording; `endFrame` submits the slot's upload command buffer ahead of the frame's and presents every swapchain image acquired since. An upload between frames prepares the coming slot the same way first. Destroying a resource is always deferred: while recording it is parked in the current slot, between frames in the slot of the frame that was just submitted, so a handle can be released at any point of the frame that still draws with it.
- Colour formats are 8-bit UNORM and sRGB, `R16G16Sfloat` and `R16G16B16A16Sfloat` for HDR data, the block-compressed `BC4`, `BC5` and `BC7` for cooked textures, and `R32Uint` for entity ids, whose clear colour is taken as integers; the one depth format is `D32Sfloat`, cleared to 0 for reversed-Z. `formatInfo` gives block dimensions and sizes, `levelByteSize` the bytes of one tightly packed level. An `ImageDesc` may carry a mip chain and may be a cube map of six layers; barriers always cover the whole image, uploads address one level and layer. `GraphicsPipelineDesc` names the colour and depth formats, the depth test (`GreaterOrEqual` by default), the cull mode, the blend mode (none, alpha, additive) and the topology (triangle lists, or line lists for debug drawing); an empty fragment entry makes a depth-only pipeline. `ComputePipelineDesc` names one compute entry; `bindPipeline` takes either kind and `dispatch` runs the compute one. Storage buffers get a bindless index (`storageBufferIndex`) on first request, for vertex pulling. It is `InvalidBindlessIndex` without `Storage` usage or when the 4096 slots are taken, and it is freed with the buffer's deferred destruction. They also have a device address (`bufferAddress`) for the data the shaders reach through pointers. Index buffers bind with `bindIndexBuffer` and draw with `drawIndexed`. A buffer with `Indirect` usage holds `IndirectCommand`s, Vulkan's `VkDrawIndexedIndirectCommand` byte for byte, and `drawIndexedIndirect` submits a fixed number of them; a command with no instances draws nothing. A command's `firstInstance` reaches the vertex shader as `SV_StartInstanceLocation`, and each instance adds its `SV_InstanceID` to it, which is where the engine reads the draw's object from its visible list ([ADR-0016](decisions/0016-instanced-batches.md)). `memoryBarrier` orders a buffer written by one pass before the pass that reads it, with `PipelineStage::DrawIndirect` and `Access::IndirectCommandRead` naming the command fetch.
- Every image created with `Sampled` usage takes a slot in the bindless sampled-image array, or in the cube array for a cube map (`sampledImageIndex`); with `Storage` usage each mip level gets a slot in the storage-image array on first request (`storageImageIndex`), through a 2D-array view so one shader declaration covers plain images and cube maps. Samplers (`SamplerDesc`: filters, address mode, anisotropy) take a slot in the sampler array, or in the comparison-sampler array when they compare, with `GreaterOrEqual` for reversed-Z shadows. Slots are written into the set at creation and reused only after the deferred destruction of their resource, so a resource created mid-frame can be indexed by that frame's shaders.
- `ISwapchain::acquire` returns the image for this frame or nothing when the window is minimised; it recreates the swapchain when acquire or present reported out of date, or after `requestResize`. Swapchain images are registered as ordinary image handles. The swapchain prefers a UNORM format: what reaches it is already display-encoded, by the scene's output pass and by Dear ImGui's vertex colours, so an sRGB view would encode twice.
- `ICommandList` records whole-image barriers with explicit stages, accesses and layouts on both sides (`ImageBarrier`), dynamic rendering with colour and depth attachments, pipeline binds, the per-pass buffers and image as push descriptors (`bindBuffers`, `bindImages`), push constants, draws, image-to-buffer copies for readback, and timestamps. The render graph derives the barriers from how passes use their images; only tests spell them out.
- Every pipeline, graphics or compute, uses one shared layout: set 0 is the bindless set, bound again with every pipeline because Dear ImGui's own layout replaces it in between; set 1 holds a uniform buffer at binding 0, a storage buffer at binding 1 and a sampled image at binding 2 as push descriptors; `PushConstantSize` bytes of push constants are visible to every stage. The pass image is read with `Load`, without a sampler; it is what the outline pass reads the selection mask through. Viewport, scissor and front face are dynamic, and there is no vertex input state. Binding a graphics pipeline sets the front face to counter-clockwise; `ICommandList::setFrontFace` sets clockwise until the next bind, and the null device traces it as `setFrontFace Clockwise`.
- `writeTimestamp` records the GPU clock into one of `MaxTimestamps` slots per frame; `timestamps` returns, in nanoseconds, what the frame that last used the slot wrote, so results are `FramesInFlight` frames old and never stall.
- Validation messages are logged with their id and the debug names of the objects involved, and counted; the tests of every module fail when the count is non-zero. Loader messages go to `trace`.
- `DeviceInfo::blockCompressionSupported` says whether the BC formats can be used, which desktop GPUs and Lavapipe support and mobile GPUs do not; the feature is enabled where present rather than required, and the texture loader falls back to uncompressed data without it.
- Host-visible buffers are persistently mapped; `mappedRange` exposes them.
- `NullDevice` implements the same interface without a GPU: handles, descriptions, mapped memory, bindless slots, transient allocations and timestamp bookkeeping behave as on the Vulkan device, and `pipelineCount` and `bufferCount` report what is still alive, for tests that check an owner releases what it creates, and recording produces a readable trace (`barrier "scene" ColorAttachment->ShaderReadOnly`, `drawIndexed 36 x1`, `uploadImage "albedo" level 0 layer 0 4194304 bytes`, `dispatch 4 2 1`) that the tests of the modules above assert on.

Not there yet: pass merging and transient aliasing in the graph.

## Frame structure

Two frames in flight. Each frame owns a command pool and an upload command pool, a timeline semaphore value, a timestamp query pool, a transient allocator and a staging ring. The swapchain uses mailbox where available and FIFO otherwise.

A device belongs to the thread that created it. The frame bracket, resource creation and destruction, and the uploads and transient allocations that write into a frame slot all go through state that nothing guards, because nothing needs to guard it while the rule holds: work for the GPU reaches the device through `JobSystem::scheduleOnMainThread` ([ADR-0013](decisions/0013-job-system.md)), and a worker's share of a frame is writing into memory the main thread allocated for it, never calling the device. The rule is asserted rather than assumed — every device implementation records its creating thread and `SONNET_ASSERT`s it on those entry points — because the thread sanitizer cannot police it: policing it there would mean seeing through an uninstrumented Vulkan driver ([roadmap.md](roadmap.md#the-thread-sanitizer-cannot-see-two-libraries-the-engine-depends-on)). The null device carries the same assertion, so the suites above `rhi` that run imports and draw lists on a real pool are what prove the modules keep the rule. "The thread that created it" rather than "the main thread" is deliberate: `sonnet_cook` and any later loading thread of its own may own a device without being the process's first thread.

Descriptor layout:

- Set 0, the bindless set, one for the device: binding 0 the sampled 2D images, binding 1 the samplers, binding 2 the storage images (one 2D-array view per mip level), binding 3 the cube maps, binding 4 the comparison samplers, binding 5 the storage buffers, declared as `StructuredBuffer<Vertex>[]` for vertex pulling ([ADR-0015](decisions/0015-bindless-vertex-buffers.md)), binding 6 the sampled depth images, the only array used with comparison samplers ([ADR-0017](decisions/0017-depth-images-in-their-own-bindless-array.md)), each a runtime array that is partially bound and updated after bind. The device hands out the indices; shaders receive them in the frame constants, the material and object data or the push constants.
- Set 1, push descriptors: per-pass buffers and one image. The frame constants at binding 0, the object array at binding 1 and, for the outline pass, the selection mask at binding 2.
- Push constants: what varies per pass rather than per draw. Today only the shadow cascade; the draw's object index is the visible list's entry at `SV_StartInstanceLocation` plus `SV_InstanceID`, the list reached through its address in the frame constants, and the index of the buffer its vertices come from lives in that object's entry of the object array ([ADR-0016](decisions/0016-instanced-batches.md), [ADR-0015](decisions/0015-bindless-vertex-buffers.md)).

Per-object data lives in storage buffers addressed by index, so a scene pass records one indirect draw per batch and the GPU supplies the draws.

## Render graph

The render graph is an engine feature this time; the previous iteration kept it in the demo and regretted it. Passes declare the resources they read and write; the graph allocates transient images, orders passes, and emits synchronization2 barriers and image layout transitions. Aliasing of transient memory is a later optimisation with no API change.

`renderer::RenderGraph` is rebuilt every frame between `reset` and `execute`:

- `importImage` registers an image the caller owns (the swapchain image, the viewport target), whose contents are undefined at the start of the frame, with an optional final layout the graph transitions to after the last pass (`Present` for the swapchain). `createImage` declares a transient image; its usage bits come from the passes that use it.
- `addPass` takes a setup callback that declares the pass's colour and depth attachments, sampled images and transfer sources or destinations, and an execute callback that records into the `ICommandList`. A pass with attachments is a graphics pass: the graph opens dynamic rendering on them around execute, with the declared load, store and clear values.
- `execute` runs the passes in declaration order. Before each pass it compares every declared use with the image's current state and emits one barrier per image whose layout changes or whose previous or next access writes; reads after reads in the same layout merge their stages instead. An image's first barrier of the frame waits for all earlier commands and memory writes, since the previous frame wrote the same target and may still be running. Transient images come from a pool keyed on their description, reused across frames and released after a few frames without use. Each pass is bracketed by two timestamps and timed on the CPU; `statistics` reports both per pass, plus barrier and transient-image counts, for the editor's overlay.

Topological ordering and pass merging are not there yet: passes run in the order they are added, which the renderer controls.

`reset` also begins a frame with a serial, `frameSerial`, that no graph in the process has used before. It is what a caller keys per-frame state on, as the renderer does to prepare a frame once however many of its passes are added. `frameIndex` counts one graph's frames from zero, so it measures a distance between two of that graph's frames and never identifies one: keyed on it and on the graph's address, a graph built where an earlier one stood matched the earlier one's first frame, and the renderer drew the earlier view again from that frame's memory.

The main pipeline is clustered forward ([ADR-0008](decisions/0008-clustered-forward-rendering.md)). `Renderer::addScenePasses` declares it, in this order:

1. Precomputation that is pending: the BRDF lookup table on the first frame, an environment's cubes on the frame after its creation ([Image-based lighting](#image-based-lighting)).
2. Skinning, when the view has skinned draws: see [Skinning](#skinning).
3. Culling: one compute pass covering every drawing pass that follows, see [GPU-driven submission](#gpu-driven-submission).
4. Four shadow cascades for the sun, each a depth-only pass into its own transient `D32Sfloat` image of `shadowMapSize` pixels. The cascades split the view depth up to `shadowDistance` between logarithmic and uniform spacing; each fits a bounding sphere around its slice of the frustum, so its size stays put as the camera turns, and snaps that sphere's centre to shadow texels so edges do not shimmer as it moves. The projection is orthographic and reversed-Z, extended towards the light by the shadow distance so casters outside the view still cast.
5. The depth pre-pass over the opaque and masked draws into the target's depth image.
6. Light clustering: a compute pass over a 16 by 9 by 24 grid of clusters, tiles of the screen sliced exponentially in view depth, that tests every punctual light's sphere against each cluster's view-space box and writes up to 63 light indices per cluster into a device-local buffer, with the memory barriers around it.
7. The forward pass into a transient `R16G16B16A16Sfloat` image: opaque draws with an equal depth test, so each visible surface is shaded once; then the skybox, a full-screen triangle at the far plane that samples the environment cube by view direction; then the blended draws sorted back to front without depth writes. Shading is the metallic-roughness model: Cook-Torrance with GGX, Smith and Schlick for the sun and the cluster's lights, inverse-square falloff windowed at the light's range, spot cones by their cosines, the sun shadowed by the cascade its view depth selects with a 3x3 kernel of hardware comparisons on the cascades in the depth array, image-based lighting through the split-sum approximation, or a flat ambient term without an environment. Opaque draws are grouped by pipeline and mesh so bindings change rarely.
8. Bloom: a chain of half-resolution passes, a 13-tap downsample then a tent-filtered upsample that adds each level to the one above, all in HDR.
9. Tone mapping: exposure, the bloom blended in by `bloomStrength`, the ACES curve and the display encoding into the `R8G8B8A8Unorm` target, or into a transient copy of it when anti-aliasing is on.
10. FXAA into the target.

The editor adds the id, selection mask and outline passes after these. `RendererSettings` holds the sizes and sample counts, which the tests turn down and which the editor keeps at their defaults.

The player adds one more: `addPresentPass` copies the finished colour image into the acquired swapchain image with a full-screen triangle. A swapchain's format is decided by the surface and is usually `B8G8R8A8Unorm`, not the renderer's own `ColorFormat`, so the pipeline that writes it is built for `RendererSettings::presentFormat` and only exists when that is set. The editor leaves it unset: it shows the scene through Dear ImGui, which owns the pipeline that writes the swapchain image there ([editor.md](editor.md#the-ui-module)).

## The renderer module today

Public headers under `sonnet/renderer/`: `RenderGraph.h`, `Mesh.h` (`Vertex`, `SkinWeights`, `Submesh`, `MeshData`, `MeshHandle`, `generateTangents`), `Primitives.h` (box, sphere, plane, cylinder and capsule generators for scenes without assets), `Texture.h` (`TextureData`, `TextureHandle`, `generateMipChain`), `Material.h` (`MaterialDesc`, `MaterialHandle`), `Camera.h` (`Camera` and the reversed-Z infinite projection), `SceneView.h` (`DrawItem`, `DirectionalLight`, `Light`, `EnvironmentHandle`, `DebugLine`, `SceneView`), `Renderer.h`, `RenderTarget.h` and `Picker.h`. Engine shaders are `shaders/sonnet.slang` (the shared module), the scene passes `depth.slang`, `cluster.slang`, `cull.slang`, `forward.slang` and `skybox.slang`, the precomputation `ibl.slang`, the post passes `post.slang`, the skinning `skin.slang`, and the editor's `id.slang`, `outline.slang` and `debug.slang`.

- `Renderer` owns meshes, textures, materials, environments and the engine pipelines. `createMesh` uploads `MeshData` into device-local buffers: a storage buffer for vertex pulling and an index buffer, with the submeshes and bounds kept on the CPU. `createTexture` uploads every level and layer of a `TextureData` and `textureIndex` gives the bindless index shaders read it through. `createMaterial` keeps a `MaterialDesc`; `createEnvironment` takes an equirectangular map. `addScenePasses` declares the passes above for a `SceneView`; the first pass to record fills the frame constants, one `ObjectData` per draw, every material and every light from the transient allocator, and each pass pushes the constants and objects as the per-pass buffers and reaches the rest through buffer device addresses in the constants. Per batch it records `drawIndexedIndirect` of the one command the culling pass filled, binding the index buffer where the mesh changes ([GPU-driven submission](#gpu-driven-submission)). `statistics` counts scene draws and triangles, shadow draws, indirect calls, lights and the instances and vertices the skinning pass deformed, all as submitted rather than as drawn.
- Every `DrawItem` carries a 32-bit id, 0 for none. `addIdPass` draws the ids into an `R32Uint` image (`IdFormat`), depth-tested without writing against the depth the forward pass left, so only the visible surface of each entity remains; it is what picking reads. `addSelectionMaskPass` draws only the items whose id is listed into a second `R32Uint` image without a depth test, so the mask holds each selected entity's whole silhouette, occluded or not. `addOutlinePass` is the post pass over the colour image: it reads the mask through the pass image binding and colours the pixels within two of a masked silhouette, discarding the rest so the scene shows through. Because the mask ignores depth, an unselected object in front of a selected one never gets an outline of its own, and a selected object stays outlined through what hides it. None of the three passes is counted in the statistics.
- `addDebugLinePass` draws the view's `DebugLine`s, world-space segments with a colour, over a colour image as one line list pulled from the frame's transient memory. They are depth-tested against the scene's depth without writing it, pulled slightly towards the camera so lines lying on a surface, like a collider around its mesh, are not lost in it; the pass therefore goes before any pass that leaves the depth undefined, such as the id pass. The editor draws the physics colliders with it ([physics.md](physics.md#queries-and-forces)). Nothing is added when there are no lines, and the pass is not counted in the statistics.
- `Picker` answers "which id is under this pixel" without a stall: a request makes `addPass` copy this frame's id image into the frame slot's readback buffer, and `poll`, called once per frame after the device's `beginFrame`, returns the answer once the slot comes round `FramesInFlight` frames later. The editor turns the id back into an entity.
- `RenderTarget` is the colour and depth pair a viewport draws into, in the renderer's fixed formats (`R8G8B8A8Unorm`, `D32Sfloat`), kept across frames so Dear ImGui can display the colour image and recreated on resize with the device's deferred destruction.
- The draw list is handed down by the layer above (`world`); the renderer never asks where it came from.

## GPU-driven submission

Opaque draws are submitted by the GPU ([ADR-0012](decisions/0012-gpu-driven-rendering.md), [ADR-0016](decisions/0016-instanced-batches.md)). The CPU records neither a call nor a command per draw; it records one instanced command per *batch*, where a batch is a run of draws sharing a pipeline, a front face, a mesh and a submesh. The draw list is already sorted by double-sidedness, then by whether the transform mirrors, then by mesh, then by submesh, so those runs are simply its segments.

- **Candidates.** Once per frame the renderer writes a `CullDraw` per entry of an order list into transient memory: the draw's world-space bounds, the object it draws, its submesh's index range, which batch it belongs to and where that batch starts in the order list. The bounds are the mesh's object-space box through the draw's transform, all eight corners, so a rotation stays conservative. There are two arrays: the opaque draws, which the cascades, the depth pre-pass and the forward pass all test, and every draw, which the editor's id and selection-mask passes test.
- **Culling.** `cull.slang` runs one thread per candidate. It rebuilds the frustum from the pass's view-projection matrix by the Gribb-Hartmann method and rejects a candidate whose bounds fall outside any plane. A survivor takes an instance of its batch's command with an atomic add on the command's `instanceCount`, and writes its object index at that slot of the batch's run of the *visible list*, a device-local `uint` buffer with a slot per draw per job. The survivor that took slot zero also writes the command's index range and its `firstInstance`, the batch's first slot in the list. One compute pass covers every scene pass of the frame: a first dispatch per job writes each of its batches a command with no indices and no instances, then one dispatch per job culls, with barriers ordering the previous frame's command fetch and vertex reads before the writes and the writes before this frame's. A batch nothing survived in draws nothing, and so does every batch of a job whose candidates did not fit the frame's transient memory, since only the clearing ran. The selection-mask job also requires the candidate's `CullSelected` flag, so the mask holds exactly the selected silhouettes.
- **Submission.** Each drawing pass records, per batch, `drawIndexedIndirect` of that batch's one command, after `bind pipeline` where the pipeline changes, `bind index buffer` where the mesh does and `setFrontFace Clockwise` ahead of a mirrored batch; since every pass shares the batches, the shadow, depth, id and selection passes follow. The vertex shaders find their object as `visible[SV_StartInstanceLocation + SV_InstanceID]` (`drawObject` in `sonnet.slang`), so a batch's instances each draw their own. The number of commands a pass submits is its batch count, which the CPU knows, so no draw count is read from the GPU and `drawIndirectCount` is not used. A mesh whose submeshes take different materials makes a batch per submesh, which it already cost in pipeline and index-range changes.
- **What stays on the CPU.** Blended draws: their order is back to front and view-dependent, which is a sort rather than a filter. They take the same pipelines and the same shaders. The visible list ends in a *direct range* with a slot per draw of the frame holding its object index, uploaded through the staging ring on the frame's first direct draw, and each direct `drawIndexed` names its slot as its first instance, so every scene shader finds its object the same way however it was submitted. A pass that could not reserve a culling job, which only a second set of scene passes for the same view in one frame does, takes the same direct path. The per-frame object, material and light upload also stays on the CPU, and is the larger part of what a frame costs there.

`RendererSettings::jobs` spreads the per-frame fill — one `ObjectData` per draw, and the cull candidates per batch — over the job system ([ADR-0013](decisions/0013-job-system.md)); a null pool runs it on the calling thread, which is what the tests and `sonnet_cook` get. Every iteration writes one slot of its own, so the result does not depend on how it was split. It buys less than it looks like it should, because writing an entry per draw into `MemoryUsage::CpuToGpu` memory is bandwidth to host-visible device memory rather than computation, and threads cannot remove bandwidth. Writing less can. `ObjectData` carries no normal matrix: the vertex shader derives it from `model` as the cofactor matrix of its upper 3×3 (`transformNormal` in `sonnet.slang`), which is the inverse transpose times the determinant: a scale the normalised normal drops, and a sign under a mirroring transform that `transformNormal` multiplies back out, as the tangent's bitangent sign takes it too, so an entry is 96 bytes rather than 160 and the fill no longer inverts a matrix per draw. On the benchmark the fill went from 0.26 ms on one thread and 0.18 ms at best on the pool to 0.15 ms on one thread, and the pool no longer changes it at all. The rest of the cost is the objects that did not move, rewritten every frame; see [roadmap.md](roadmap.md#the-per-frame-fill-is-bandwidth-not-computation).
- **What this costs in visibility.** The CPU never learns how many draws survived: `RenderStatistics` reports what was submitted, and `indirectCallCount` the batches. The null device's trace shows `drawIndexedIndirect "draw commands" count 1` per batch, so the tests above `rhi` assert on the calls a pass makes. The GPU tests on Lavapipe are what prove culling keeps the right things. A ground plane wider than the frustum and a lit box still render, pixel for pixel, when a crowd of draws outside the frustum, in the box's own batch, is added to the scene. Two submeshes of one mesh draw in their own places, and three draws in two batches each draw in their own colour. An unselected box beside a selected one must add no instance to the mask.

Measured with `renderer_tests "[benchmark]"`, ten thousand draws of two meshes and a hundred lights at 1080p on an RTX 4090, Release:

| | Before | After |
|---|---|---|
| CPU, the six scene passes | 2.69 ms | 0.28 ms, of which 0.26 ms is the per-frame upload |
| GPU, whole frame | 1.24 ms | 0.64 ms |
| Draw calls recorded | 60000 | 12 |

The same scene in Debug went from about 93 ms of CPU recording, the figure M3 measured, to about 13 ms, nearly all of it the object upload. The GPU time falls because nothing culled the draws before.

The benchmark reports the frame's CPU split into recording the passes and submitting in `endFrame`. The submit time is where MoltenVK turns every recorded indirect command into its own Metal draw, which no pass's recording time includes. Before [ADR-0016](decisions/0016-instanced-batches.md) a batch was a command per draw, drawn through `drawIndirectCount` where the device had it and over every slot where it did not ([ADR-0014](decisions/0014-indirect-draws-without-count.md), superseded): on an Apple M4 Max that was sixty thousand commands a frame, 4.96 ms of submission and 0.37 ms of GPU time in shadow cascade 0. With one instanced command per batch, on the RTX 4090 in Release, three runs each against the counted form it replaced:

| | Command per draw, counted | Command per batch |
|---|---|---|
| CPU, recording the passes | 0.19–0.20 ms | 0.19–0.21 ms |
| CPU, submitting the frame | 0.003–0.004 ms | 0.003–0.004 ms |
| GPU, shadow cascade 0 | 0.001–0.002 ms | 0.001 ms |
| GPU, forward pass | 0.23 ms | 0.20 ms |
| GPU, whole frame | 0.60–0.62 ms | 0.50 ms |

The counted path lost nothing, and the forward pass gained, since the GPU now fetches one command per batch rather than one per survivor. On the Apple M4 Max (macOS 26.7, MoltenVK 1.4.1), the same benchmark, three runs each against the uncounted form it replaced:

| | Command per draw, every slot | Command per batch |
|---|---|---|
| CPU, recording the passes | 0.14–0.22 ms | 0.15–0.19 ms |
| CPU, submitting the frame | 5.01–5.16 ms | 0.25–0.26 ms |
| GPU, shadow cascade 0 | 0.38–0.41 ms | 0.015 ms |
| GPU, forward pass | 1.55–1.58 ms | 1.13–1.14 ms |
| GPU, whole frame | 4.73–4.75 ms | 2.08–2.12 ms |

Submission falls twentyfold and cascade 0 to what its survivors cost. The ADR expected submission under 0.1 ms; the 0.25 ms left is MoltenVK's alone, since the RTX 4090 submits the same twelve commands in 0.004 ms, and whether it grows with the draw count is what a run at a smaller scene would show.

## Skinning

A skinned draw carries the range of `SceneView::joints` that deforms it, each matrix taking the mesh's bind pose into the drawn entity's space, and a key naming the instance across frames (ADR-0010). The first pass the renderer declares in a graph frame, whether the scene passes or the editor's id or mask pass, is preceded by a compute pass that runs `skin.slang` once per instance: one thread per vertex blends up to four joint matrices, by the mesh's `SkinWeights` buffer, and writes the deformed vertex into a device-local buffer the renderer keeps for that instance, reusing it every frame and releasing it a few frames after its last draw. Every later pass pulls its vertices from that buffer through its slot in the bindless vertex-buffer array, which the draw's `ObjectData` names ([ADR-0015](decisions/0015-bindless-vertex-buffers.md)), so no vertex shader has a skinned variant and an instance is deformed once however many of the eight passes draw it. A memory barrier on each side of the pass orders it after the previous frame's draws and before this frame's.

A draw is skinned only when its mesh was created with skin weights and its joint range fits the view's; otherwise it draws in its bind pose. `world` builds the joint matrices from the skeleton ([world.md](world.md#animation)).

## Resources and materials

- Meshes: `Vertex` is position, normal, a tangent with the bitangent sign in `w`, and one uv set, 48 bytes under scalar layout; a skinned mesh has one `SkinWeights` per vertex besides, four joint indices and their weights; `generateTangents` derives tangents from the uv derivatives for meshes without them, the primitives included. A mesh is a list of submeshes, each an index range with a material slot, plus bounds; a `DrawItem` names one submesh and one material.
- Materials: the glTF metallic-roughness model in `MaterialDesc`: base colour, emissive, metallic, roughness, normal scale, occlusion strength, the five textures, an alpha mode (opaque, masked with a cutoff, blended), the texture wrap and double-sidedness. The renderer keeps the descriptions and writes them all into a transient storage buffer every frame, with the default material in slot 0, so a change shows on the next frame and a draw with an invalid handle uses the default. An invalid texture is the white default, or the flat normal for the normal map. Double-sided materials use pipelines that cull nothing and flip back-facing normals.
- Textures: `TextureData` holds every level tightly packed, level-major with a cube map's six faces inside each level, as KTX2 lays them out; `generateMipChain` box-filters an RGBA8 image, averaging sRGB data in linear space. Every material texture is sampled through one of three anisotropic samplers by wrap mode.
- Lights: the sun is the `DirectionalLight` of the view; `Light` is a point or spot light with a range, clustered by the renderer. Up to 1024 per view.
- Every resource is reached through a `Handle<Tag>` with generation checks ([architecture.md](architecture.md#resource-handles)).

## Image-based lighting

An environment is created from an equirectangular map, typically an RGBA16F HDR image, and precomputed by compute passes the next `addScenePasses` declares, in the render graph like everything else: the map is converted into a cube (`environmentSize` per face, RGBA16F), the cube's mip chain is built one level per pass, the diffuse irradiance cube is integrated with cosine-weighted samples of a blurred level, and the specular cube is prefiltered with GGX importance sampling at one roughness per level, reading the source at a lod chosen from the sample's solid angle so bright texels do not become fireflies. The split-sum BRDF lookup table is computed once per renderer on the first frame. All of these are storage images and stay in the General layout; the graph orders the forward pass's reads after the writes, so an environment lights the frame that computes it. The skybox pass samples the environment cube by view direction; `SceneView::environmentIntensity` scales both the lighting and the background, and `exposure` the tone mapping.

## Editor viewport and ImGui

The scene renders into an offscreen colour image that the viewport panel displays with `ImGui::Image`. Picking is a small pass that writes entity ids into an image and reads back the pixel under the cursor (`Picker`). The selection outline is a post pass over a mask image holding the selected entities' silhouettes.

ImGui uses its SDL3 and Vulkan backends, initialised in dynamic-rendering mode, drawing directly to the swapchain image after the scene. Multi-viewport is enabled on desktop. The `ui` module wraps both in `ImGuiLayer` ([editor.md](editor.md#the-ui-module)); the editor declares the ImGui draw as the last graph pass, rendering into the swapchain image and sampling the viewport target, so the graph orders it after the scene.

## Debugging

- Debug builds request `VK_LAYER_KHRONOS_validation` with synchronization validation enabled, and route messages to the log with the object names attached.
- Every Vulkan object gets a `VK_EXT_debug_utils` name from its handle's debug name, so RenderDoc and validation output are readable.
- GPU timestamps per render-graph pass feed the on-screen overlay and Tracy's GPU zones.
- `RendererSettings::debugView` makes the forward pass write one term of its shading in place of the final colour, before tone mapping: the albedo, the shading normal, the sun's direct light without its shadow, the shadow factor, the diffuse and specular image-based light, or the BRDF lookup table's scale and bias in red and green. The editor offers it under View > Shading term. Comparing these term by term between two platforms is how ADR-0017's cause was found.

## Testing

- `rhi` interfaces have a null implementation used by unit tests of `renderer`, `assets` and `world`, so those modules are tested without a GPU. `renderer_tests` checks the graph's barriers, pooling and timings and, against the null device's trace, the renderer's pass list and draw recording, the batches each pass submits indirectly, the sorting of blended draws on the direct path, texture uploads and material indices, an environment's precomputation, the id, mask and outline passes, the debug line pass, the skinning pass with its one dispatch per instance and the reuse and release of its buffers, the picker's readback timing, and that the renderer destroys every pipeline it creates.
- The Vulkan implementation is tested on Lavapipe in CI: device creation, resource lifetime including deferred destruction, a triangle drawn into an offscreen image and read back, vertex pulling with the per-pass buffers and the reversed-Z depth test, an `R32Uint` id image written by one pass and read by the next through the pass image binding, a mipmapped texture and a cube map uploaded through the staging ring and sampled through the bindless set, an upload larger than the ring, a compute pass filling a storage image, timestamps and the transient allocator, and later golden-image comparisons of sample scenes with a tolerance. `renderer_tests`, `ui_tests` and `editor_tests` also run GPU cases on Lavapipe: a lit box read back from the viewport target, the sun's shadow beside a box, a clustered point light that reaches only the ground within its range, an environment that fills the background and lights a sphere, a texture's green reaching the albedo in the shader that also compares depth, the BRDF lookup table's scale and bias, a box picked by id and outlined over several frames, a selected surface whose occluder stays unoutlined, a scene that renders pixel for pixel the same whether or not draws outside the frustum are in its draw list, debug lines hidden behind a box and drawn in front of it, a skinned box moved by its joint, ImGui frames drawn into a headless swapchain, and whole editor frames. Swapchain tests use SDL's offscreen video driver and `VK_EXT_headless_surface`, which Lavapipe supports; on drivers without headless surfaces those tests skip. Loaders before 1.4 emulate that extension for every driver and some drivers crash inside the surface queries, so on such loaders the tests run only on Lavapipe; `DeviceInfo` reports loader version and driver name for this. The test shader is compiled by the same `sonnet_add_shaders` rule the applications use.
- Validation-layer messages fail tests when they occur: `IDevice::validationMessageCount` is checked by the test fixture.
