# Rendering

Two modules: `rhi` (render hardware interface plus the Vulkan 1.4 implementation) and `renderer` (render graph, materials, passes, engine shaders). Everything above `rhi` is API-agnostic; everything in `rhi` is deliberately shaped like Vulkan.

## Vulkan baseline

Vulkan 1.4 is the minimum ([ADR-0001](decisions/0001-vulkan-1.4-only.md)), or Vulkan 1.3 with the engine's four 1.4 features as the extensions 1.4 promoted: `VK_KHR_push_descriptor`, `VK_KHR_dynamic_rendering_local_read`, `VK_KHR_maintenance5` and `VK_KHR_maintenance6` ([ADR-0019](decisions/0019-vulkan-1.3-devices-with-the-1.4-extensions.md)). The device selector rejects anything else, naming what each device lacks, and prefers neither form. On a 1.3 device `VulkanDevice` enables the four extensions and chains their feature structures in place of `VkPhysicalDeviceVulkan14Features`; recording is the same on both, since Vulkan-HPP's dispatcher resolves `vkCmdPushDescriptorSet` to the extension's entry point where the core one is absent. VMA takes the device's version, and `DeviceInfo` reports it with `vulkan14FeaturesAsExtensions`. Nothing may use Vulkan 1.4 beyond those four features without an ADR that retires 1.3 devices or names the extension that brings the feature to them. The engine relies on:

| Feature | Core since | Used for |
|---|---|---|
| Shader draw parameters | 1.1 | Slang lowers `SV_VertexID` through `gl_BaseVertex`, `SV_StartInstanceLocation` through `gl_BaseInstance`, and `SV_InstanceID` as `gl_InstanceIndex` less `gl_BaseInstance` |
| Timeline semaphores | 1.2 | Frame and upload synchronization |
| Buffer device address | 1.2 | Per-frame data without descriptor churn: materials, lights, clusters, the culling and skinning passes |
| Multi-draw indirect, indirect first instance | 1.0 features | GPU-driven submission ([ADR-0012](decisions/0012-gpu-driven-rendering.md), [ADR-0016](decisions/0016-instanced-batches.md)) |
| Descriptor indexing: partially bound, update-after-bind, runtime arrays | 1.2 (features required by this engine) | Bindless textures and buffers |
| Scalar block layout | 1.2 | Shared struct layouts between C++ and Slang |
| Dynamic rendering | 1.3 | No render pass or framebuffer objects |
| Synchronization2 | 1.3 | Barriers emitted by the render graph |
| Extended dynamic state | 1.3 | Fewer pipeline permutations: the front face is set per batch, so a mirrored draw needs no pipeline of its own |
| Push descriptors | 1.4 | Per-pass uniform and storage buffers |
| Dynamic rendering local read | 1.4 | Tile-friendly subpass-style reads on mobile |
| Maintenance 5 and 6 | 1.4 | Simpler pipeline and descriptor handling |
| Host image copy | 1.4, optional feature | Faster texture uploads when present; not used yet, every upload goes through staging |

Vulkan 1.4 also raises minimum limits (push constants, bound descriptor sets, image dimensions). The engine reaches none of the raised ones: it uses 128 bytes of push constants and two descriptor sets, within 1.3's minimums, which a 1.3 device relies on.

Depth uses reversed-Z: `D32_SFLOAT`, cleared to 0, `GREATER` compare, infinite far plane. Projection uses `GLM_FORCE_DEPTH_ZERO_TO_ONE`. Clip-space Y is flipped by a negative viewport height (core since 1.1) so triangle winding stays counter-clockwise front-facing, matching glTF. A draw whose transform mirrors — a negative determinant in its upper 3×3, which a negative scale gives — reverses that winding on screen, so it is drawn with a clockwise front face ([GPU-driven submission](#gpu-driven-submission)).

## Platform notes

- **Windows, Linux**: current vendor drivers and Mesa ship Vulkan 1.4. Lavapipe (Mesa CPU implementation) is used in CI.
- **macOS, iOS**: MoltenVK 1.4+ layers Vulkan 1.4 over Metal (macOS 12+, iOS 15+). It is a portability implementation: the instance must enable `VK_KHR_portability_enumeration` and the device must enable `VK_KHR_portability_subset` when present. Geometry shaders, triangle fans and some format and tessellation features are missing; the engine uses none of them. Descriptor indexing on MoltenVK requires Metal argument buffers, which MoltenVK enables by default in recent versions; the device selector verifies the required descriptor-indexing features rather than assuming them. MoltenVK has no `drawIndirectCount` (confirmed on 1.4.1 and 1.4.2 on an Apple M4 Max), because a Metal indirect draw cannot take its number of draws from a buffer, and it encodes one Metal draw per indirect command, on the CPU, when the frame is submitted. The engine uses neither the count nor a command per draw: each batch is one instanced command, so the number a pass submits is the batch count, which the CPU knows ([ADR-0016](decisions/0016-instanced-batches.md)). Slang loads a storage-buffer element as a whole struct, and SPIRV-Cross cannot translate that load when the struct holds a pointer. So no struct in a storage buffer holds one, and vertices are pulled through a bindless array rather than a pointer in `ObjectData` ([ADR-0015](decisions/0015-bindless-vertex-buffers.md)). SPIRV-Cross types a whole bindless array as Metal depth textures when any use of it compares, and a depth texture reads as its red channel alone, so depth images have an array of their own and colour textures are never compared ([ADR-0017](decisions/0017-depth-images-in-their-own-bindless-array.md)).
- **Android**: devices launching with Android 16 or later must support Vulkan 1.4. A device updated to Android 16 may still report 1.3 and carry the four features as extensions, as the Galaxy S25 Ultra does (1.3.284, Adreno 830); ADR-0019 accepts it. A 1.3 device without them is unsupported. Mobile GPUs are tile-based: the render graph keeps passes mergeable and uses dynamic rendering local read for G-buffer-style reads instead of round trips to memory. Textures are shipped as KTX2 with ASTC ([assets.md](assets.md#textures)); ETC2 is not used ([ADR-0018](decisions/0018-mobile-export.md#textures)).
- **Loader**: SDL3 loads the Vulkan library. `SDL_Vulkan_GetVkGetInstanceProcAddr` seeds both vk-bootstrap and the Vulkan-HPP dynamic dispatcher so there is one loader in the process. The loader only has to be 1.1: the 1.4 requirement is on the physical device, because distributions ship older loaders in front of current drivers (Ubuntu 24.04 has 1.3) and the engine uses no 1.4 instance-level entry points.

### MoltenVK 1.4.2 integer-attachment warning

MoltenVK 1.4.2 warns that blending is enabled for `VK_FORMAT_R32_UINT` when the id and selection-mask pipelines are created, although both use `BlendMode::None`. Its warning condition checks whether the format supports blending but omits the pipeline's `blendEnable`. This is a driver diagnostic bug, not blending of entity ids: the existing RHI id-image test reads the correct ids and fails only its zero-validation-message check. The same test passes without warnings on MoltenVK 1.4.1.

[Upstream issue 2811](https://github.com/KhronosGroup/MoltenVK/issues/2811) identifies the same problem; [fix f92b64c3](https://github.com/KhronosGroup/MoltenVK/commit/f92b64c3a5084c6cfa78f581e0b863b40d2d16fa) adds the missing `blendEnable` check. As checked on 2026-09-29, the latest release is still 1.4.2, so the prebuilt library installed by `ports/moltenvk` still has the warning. [Sonnet issue 59](https://github.com/Pacheco95/sonnet/issues/59) stays open for a release containing the fix. Pipeline state and diagnostic handling are unchanged. The [investigation report](reports/moltenvk-id-blending.md) records the reproduction and the checks needed when updating the port.

## Object ownership

vk-bootstrap selects the physical device and creates the instance, debug messenger, device and swapchain. Every handle it returns is immediately adopted by a Vulkan-HPP RAII wrapper (`vk::raii::Instance`, `vk::raii::Device`, ...), which then owns it. `vkb::destroy_*` is never called. VMA is used through the Hpp bindings and destroyed before the device. RAII members are declared in reverse destruction order so lifetimes are correct by construction. Details in [ADR-0006](decisions/0006-vulkan-object-ownership.md).

## Memory

All GPU memory goes through VMA. `rhi` exposes:

- Device-local buffers and images with a staging ring for uploads: `IDevice::uploadBuffer` and `uploadImage` copy the data into the frame slot's ring at once and record the transfer into an upload command buffer that is submitted ahead of the frame's commands, so a resource uploaded at any point of a frame, or between frames, is complete for that frame's draws. Data larger than the ring gets a dedicated staging buffer released with the slot.
- Per-frame linear allocators for transient uniform and storage data: `IDevice::allocateTransient` hands out slices of one host-visible buffer per frame slot, aligned for both binding types, valid until the slot is reused.
- Budget queries through `VK_EXT_memory_budget` for the resource overlay: `IDevice::memoryBudget` reports usage and budget per heap.
- Leak detection: every allocation carries a debug name, and the device reports live allocations at shutdown in Debug builds.

## Shaders

Slang is the only shading language ([ADR-0005](decisions/0005-slang.md)). Engine shaders live in `modules/renderer/shaders/`, project shaders in the project's `shaders/` folder.

- **Build time**: `sonnet_add_shaders(<target> SHADERS ...)` (in `cmake/SonnetShaders.cmake`) runs `slangc` on each `.slang` file, emitting one SPIR-V 1.6 module per file that holds every `[shader("...")]` entry point under its own name (`-fvk-use-entrypoint-name`), scalar block layout (`-fvk-use-scalar-layout`, so C++ and Slang share struct layouts byte for byte), column-major matrices, debug information in Debug and `-O2` otherwise. The module lands in `shaders/<name>.spv` next to the target's binary, and a depfile makes edits to imported modules rebuild their users. `sonnet_add_engine_shaders(<target>)` does the same for the engine's own shaders, for every executable and test that renders through `renderer`. Release builds ship only SPIR-V.
- **Android**: after `slangc`, the Android build passes every module through `tools/spirv_for_adreno.py`, which rewrites two valid shapes Slang emits for the pointers in `FrameConstants` that Adreno's compiler rejects ([roadmap.md](reports/m9-mobile-export.md#the-adreno-shader-compiler)). Slang declares a pointer to a struct ahead with `OpTypeForwardPointer` and uses it in the block before defining it, and the driver segfaults on that. It reaches a member of `lights[i]` through a pointer to the element and then a second access chain, or loads the element whole, and the driver returns `VK_ERROR_UNKNOWN` on that when `i` is not a constant. The pass folds each chain of access chains on a buffer pointer into one chain from the root pointer, splits a whole struct or array loaded through one into a load per member, and sorts the types so every pointer is defined before its first use. What a module computes is unchanged. The editor's screenshots are byte-identical with the rewritten modules, and `renderer_spirv_for_adreno` runs the pass over the engine's modules on every desktop build. Desktop modules are left as `slangc` wrote them. The pass rejects a shape it does not know (a recursive pointer type, a whole struct stored through a pointer, a matrix loaded through one) and fails the build rather than ship a module that might crash the driver.
- **Loading**: `Renderer` takes the directory of the compiled modules and reads each through `platform::Platform::openContent` ([platform.md](platform.md#paths)). `runtime::Game` passes the relative `shaders`, so the player reads them from beside its binary on desktop and from the APK's `assets/shaders/` on Android. The editor, the cook and the tests pass the absolute `basePath() / "shaders"`, which is an ordinary directory on disk.
- **Runtime**: `editor::ShaderCompiler` drives the Slang library with the same options as the build rule, and `Renderer::reloadShader` rebuilds every pipeline made from a module with the new SPIR-V, building all of them before destroying any so a module or pipeline the driver rejects changes nothing. The editor watches the checkout's shader sources and recompiles a changed entry-point file, or every one when a shared module such as `sonnet.slang` changes; compile errors are logged with their `file:line:column` and the previous pipelines stay ([editor.md](editor.md#shader-hot-reload)). The player ships only the SPIR-V the build produced.
- **Reflection**: the descriptor layout is the fixed one below and shaders declare the matching bindings; Slang's program layout is the reflection source when a shader has to be checked against it, and there is no separate reflection library.
- **Conventions**: the shared `sonnet.slang` module declares the bindless arrays of set 0, the per-pass buffers of set 1, the per-draw push constants and the vertex layout. Scene shaders `import sonnet` and never declare their own descriptor sets. Vertices are pulled from `vertexBuffers[objects[objectIndex].vertexBuffer]`, the bindless array at set 0 binding 5, indexed by `SV_VertexID` from the bound index buffer ([ADR-0015](decisions/0015-bindless-vertex-buffers.md)). No struct stored in a storage buffer holds a pointer: Slang loads such an element whole, however the source reads it, and Metal cannot compile the result. Pointers live in uniform and push-constant blocks, such as the frame constants. Post passes over an image (`outline.slang`) are the exception: they draw one full-screen triangle, declare the pass image binding and their own push constants, and import nothing. So is `debug.slang`, which pulls line vertices from the pass storage buffer and takes the view-projection matrix as its push constants.

## The rhi module today

Public headers under `sonnet/rhi/`: `Types.h` (handles, formats, usages, layouts, synchronization, attachments, pipeline state), `Device.h` (`IDevice`, `DeviceDesc`, `createDevice`), `Swapchain.h` (`ISwapchain`), `CommandList.h` (`ICommandList`) and `NullDevice.h` (the GPU-less implementation for tests). The Vulkan implementation lives in `src/` and is reached only through `createDevice`, the one `#if`-switched site.

- `IDevice` creates buffers, images, samplers and swapchains, hands out generation-checked handles, and runs the frame: `beginFrame` waits for the slot's previous submission on the timeline semaphore, reads that submission's timestamps, frees the resources parked in the slot, resets the pools, the transient allocator and the staging ring and starts recording; `endFrame` submits the slot's upload command buffer ahead of the frame's and presents every swapchain image acquired since. An upload between frames prepares the coming slot the same way first. Destroying a resource is always deferred: while recording it is parked in the current slot, between frames in the slot of the frame that was just submitted, so a handle can be released at any point of the frame that still draws with it.
- Colour formats are 8-bit UNORM and sRGB, `R16G16Sfloat` and `R16G16B16A16Sfloat` for HDR data, the block-compressed `BC4`, `BC5` and `BC7` and the `ASTC4x4` and `ASTC6x6` formats, UNORM and sRGB, for cooked textures, and `R32Uint` for entity ids, whose clear colour is taken as integers; the one depth format is `D32Sfloat`, cleared to 0 for reversed-Z. `formatInfo` gives block dimensions and sizes (4×4 for BC and ASTC 4×4, 6×6 for ASTC 6×6, 16 bytes a block for all but `BC4`), `levelByteSize` the bytes of one tightly packed level, rounded up to whole blocks, and `toString` the format's name for logs. An upload copies a level's whole extent, which for a level whose size is no multiple of the block ends at the image's edge, as Vulkan allows. An `ImageDesc` may carry a mip chain and may be a cube map of six layers; barriers always cover the whole image, uploads address one level and layer. `GraphicsPipelineDesc` names the colour and depth formats, the depth test (`GreaterOrEqual` by default), the cull mode, the blend mode (none, alpha, additive) and the topology (triangle lists, or line lists for debug drawing); an empty fragment entry makes a depth-only pipeline. `ComputePipelineDesc` names one compute entry; `bindPipeline` takes either kind and `dispatch` runs the compute one. Storage buffers get a bindless index (`storageBufferIndex`) on first request, for vertex pulling. It is `InvalidBindlessIndex` without `Storage` usage or when the 4096 slots are taken, and it is freed with the buffer's deferred destruction. They also have a device address (`bufferAddress`) for the data the shaders reach through pointers. Index buffers bind with `bindIndexBuffer` and draw with `drawIndexed`. A buffer with `Indirect` usage holds `IndirectCommand`s, Vulkan's `VkDrawIndexedIndirectCommand` byte for byte, and `drawIndexedIndirect` submits a fixed number of them; a command with no instances draws nothing. A command's `firstInstance` reaches the vertex shader as `SV_StartInstanceLocation`, and each instance adds its `SV_InstanceID` to it, which is where the engine reads the draw's object from its visible list ([ADR-0016](decisions/0016-instanced-batches.md)). `memoryBarrier` orders a buffer written by one pass before the pass that reads it, with `PipelineStage::DrawIndirect` and `Access::IndirectCommandRead` naming the command fetch.
- Every image created with `Sampled` usage takes a slot in the bindless sampled-image array, or in the cube array for a cube map (`sampledImageIndex`); with `Storage` usage each mip level gets a slot in the storage-image array on first request (`storageImageIndex`), through a 2D-array view so one shader declaration covers plain images and cube maps. Samplers (`SamplerDesc`: filters, address mode, anisotropy) take a slot in the sampler array, or in the comparison-sampler array when they compare, with `GreaterOrEqual` for reversed-Z shadows. Slots are written into the set at creation and reused only after the deferred destruction of their resource, so a resource created mid-frame can be indexed by that frame's shaders.
- `ISwapchain::acquire` returns the image for this frame or nothing when the window is minimised, the swapchain is suspended or its surface was lost ([Suspend and resume](#suspend-and-resume)); it recreates the swapchain when acquire or present reported out of date or suboptimal, unless only the surface's transform differs ([Rotation](#rotation)), or after `requestResize` when the window's pixel size differs from the swapchain's extent: SDL reports a pixel size change at startup, on Android and X11 alike, for the size the swapchain was just created at, and recreating for it would rebuild the swapchain on the first frame for nothing (issue #51). Swapchain images are registered as ordinary image handles. The swapchain prefers a UNORM format: what reaches it is already display-encoded, by the scene's output pass and by Dear ImGui's vertex colours, so an sRGB view would encode twice. Its images also take `TransferSrc` usage where the surface allows it, which `readable` reports, so the editor can copy a finished frame out for a screenshot ([editor.md](editor.md#screenshots)).
- `ICommandList` records whole-image barriers with explicit stages, accesses and layouts on both sides (`ImageBarrier`), dynamic rendering with colour and depth attachments, pipeline binds, the per-pass buffers and image as push descriptors (`bindBuffers`, `bindImages`), push constants, draws, image-to-buffer copies for readback, and timestamps. The render graph derives the barriers from how passes use their images; only tests spell them out.
- Every pipeline, graphics or compute, uses one shared layout: set 0 is the bindless set, bound again with every pipeline because Dear ImGui's own layout replaces it in between; set 1 holds a uniform buffer at binding 0, a storage buffer at binding 1 and a sampled image at binding 2 as push descriptors; `PushConstantSize` bytes of push constants are visible to every stage. The pass image is read with `Load`, without a sampler; it is what the outline pass reads the selection mask through. Viewport, scissor and front face are dynamic, and there is no vertex input state. Binding a graphics pipeline sets the front face to counter-clockwise; `ICommandList::setFrontFace` sets clockwise until the next bind, and the null device traces it as `setFrontFace Clockwise`.
- `writeTimestamp` records the GPU clock into one of `MaxTimestamps` slots per frame; `timestamps` returns, in nanoseconds, what the frame that last used the slot wrote, so results are `FramesInFlight` frames old and never stall.
- Validation messages are logged with their id and the debug names of the objects involved, and counted; the tests of every module fail when the count is non-zero. Loader messages go to `trace`.
- `DeviceInfo::blockCompressionSupported` says whether the BC formats can be used (`textureCompressionBC`), and `astcSupported` whether the ASTC ones can (`textureCompressionASTC_LDR`). Each feature is enabled where present rather than required, and the device's log line lists the ones it has. The RTX 4090, RADV and Lavapipe have BC and no ASTC; the Galaxy S25 Ultra and the iPhone 15 Pro Max have both ([ADR-0018](decisions/0018-mobile-export.md#open-questions)). `formatSupported(info, format)` says whether a device samples a format, and `createImage` asserts it. The texture loader transcodes UASTC to BC7 with block compression, to ASTC 4×4 with ASTC but no BC, and to RGBA8 with neither, and refuses a KTX2 file in a format the device cannot sample ([assets.md](assets.md#textures)). The renderer's debug line for each texture it creates names its format.
- Host-visible buffers are persistently mapped; `mappedRange` exposes them.
- `NullDevice` implements the same interface without a GPU: handles, descriptions, mapped memory, bindless slots, transient allocations and timestamp bookkeeping behave as on the Vulkan device, and `pipelineCount` and `bufferCount` report what is still alive, for tests that check an owner releases what it creates, and recording produces a readable trace (`barrier "scene" ColorAttachment->ShaderReadOnly`, `drawIndexed 36 x1`, `uploadImage "albedo" level 0 layer 0 4194304 bytes`, `dispatch 4 2 1`) that the tests of the modules above assert on.

Not there yet: pass merging and transient aliasing in the graph.

## Suspend and resume

On Android the window's surface goes away when the application is sent to the background, and iOS allows no GPU work from a background application ([ADR-0018](decisions/0018-mobile-export.md#where-it-lives)). The swapchain lets go of the surface for that time and creates it again afterwards:

- **`suspend`** waits for the device to go idle, releases the swapchain's images (their handles through the usual deferred destruction), then the swapchain and then the surface, and logs `swapchain suspended` at `info`. It is called between frames: the player calls it on `WillEnterBackground` ([player.md](player.md#the-lifecycle)). A second `suspend` does nothing.
- **While suspended**, `acquire` returns nothing, as it does for a minimised window, so the frame goes on without an image and `Game::render` draws nothing. A resize request changes nothing, since `resume` creates the swapchain at the window's size then. `imageCount` is 0 and `extent` keeps the last one.
- **`resume`** creates the surface from the window again, checks that the graphics queue presents to it, and creates the swapchain at the window's pixel size, logging `swapchain resumed at WxH` at `info`. Without a suspend it does nothing. A failure, from SDL or from Vulkan, comes back as an `Error` and leaves the swapchain suspended, so it never throws into the event that called it.
- **A surface lost first.** On Android the surface can go a few milliseconds before the application hears about it ([platform.md](platform.md#background-and-foreground)). A `VK_ERROR_SURFACE_LOST_KHR` from acquire or present, or a failure to recreate the swapchain inside `acquire`, marks the surface lost: one warning, then `acquire` returns nothing, and nothing on the frame path throws. The `suspend` that follows releases what is left, and `resume` recovers from a lost surface as from a suspend, so a lost surface outside the lifecycle waits for a resume that the desktop never sends. Recreating a surface for any other reason is not done.

The null device's swapchain follows the same rules without a surface: `suspend` destroys its images and `resume` creates them at the window's size. Neither call is traced, since neither records a command.

On the Galaxy S25 Ultra (Adreno 830, Android 16) `suspend` took about 5 ms and `resume` about 3 ms, across ten trips to the background, and the resumed swapchain was 1080×2340 with 5 images, as at startup.

## Rotation

A phone reports how its display is turned as the surface's current transform: `Rotate90` in landscape, with the surface's extent already landscape. A swapchain created with that transform as its pre-transform promises frames drawn rotated, and the engine draws them upright at the window's size, so the compositor turned them a second time: sideways and stretched ([#47](https://github.com/Pacheco95/sonnet/issues/47)). The swapchain asks for the identity pre-transform wherever the surface supports it, and the compositor rotates the upright frame. Every desktop surface, Lavapipe's headless one and the phone support it. A surface without it gets its current transform, as before.

With identity chosen while the display is turned, Android reports `VK_SUBOPTIMAL_KHR` from every present, and recreating the swapchain does not stop it. So on suboptimal, from acquire or present, the swapchain reads the surface's capabilities and keeps going when their current extent is the swapchain's and only the transform differs from the one it chose. Any other suboptimal recreates at the next acquire, as before. A turn between portrait and landscape changes the extent: the swapchain is recreated once, either by that check or by the window's resize, whichever comes first. A turn by 180° changes the transform alone and recreates nothing.

The alternative Android recommends is to follow the transform and rotate while the present pass copies into the swapchain image, so the compositor never rotates. That needs the swapchain to report its transform and the renderer and the screenshots to follow it. On the Galaxy S25 Ultra it would save nothing: `dumpsys SurfaceFlinger` shows the player's layer composed by the display hardware (`DEVICE`) with `ROT_90` in landscape and `ROT_180` upside down, not by a GPU pass. A phone that falls back to GPU composition for a rotated layer would be the reason to do it.

## Frame structure

Two frames in flight. Each frame owns a command pool and an upload command pool, a timeline semaphore value, a timestamp query pool, a transient allocator and a staging ring. The swapchain uses mailbox where available and FIFO otherwise, except on Android, where it always uses FIFO: mailbox kept a phone's GPU fully busy drawing frames the display never showed, and the phone throttled within two minutes ([player.md](player.md#frame-rate)).

A device belongs to the thread that created it. The frame bracket, resource creation and destruction, and the uploads and transient allocations that write into a frame slot all go through state that nothing guards, because nothing needs to guard it while the rule holds: work for the GPU reaches the device through `JobSystem::scheduleOnMainThread` ([ADR-0013](decisions/0013-job-system.md)), and a worker's share of a frame is writing into memory the main thread allocated for it, never calling the device. The rule is asserted rather than assumed — every device implementation records its creating thread and `SONNET_ASSERT`s it on those entry points — because the thread sanitizer cannot police it: policing it there would mean seeing through an uninstrumented Vulkan driver ([roadmap.md](roadmap.md#the-thread-sanitizer-cannot-see-the-vulkan-driver)). The null device carries the same assertion, so the suites above `rhi` that run imports and draw lists on a real pool are what prove the modules keep the rule. "The thread that created it" rather than "the main thread" is deliberate: `sonnet_cook` and any later loading thread of its own may own a device without being the process's first thread.

Descriptor layout:

- Set 0, the bindless set, one for the device: binding 0 the sampled 2D images, binding 1 the samplers, binding 2 the storage images (one 2D-array view per mip level), binding 3 the cube maps, binding 4 the comparison samplers, binding 5 the storage buffers, declared as `StructuredBuffer<Vertex>[]` for vertex pulling ([ADR-0015](decisions/0015-bindless-vertex-buffers.md)), binding 6 the sampled depth images, the only array used with comparison samplers ([ADR-0017](decisions/0017-depth-images-in-their-own-bindless-array.md)), each a runtime array that is partially bound and updated after bind. The device hands out the indices; shaders receive them in the frame constants, the material and object data or the push constants.
- Set 1, push descriptors: per-pass buffers and one image. The frame constants at binding 0, the object array at binding 1 and, for the outline pass, the selection mask at binding 2.
- Push constants: what varies per pass rather than per draw. Today only the shadow map, a cascade or a local light's; the draw's object index is the visible list's entry at `SV_StartInstanceLocation` plus `SV_InstanceID`, the list reached through its address in the frame constants, and the index of the buffer its vertices come from lives in that object's entry of the object array ([ADR-0016](decisions/0016-instanced-batches.md), [ADR-0015](decisions/0015-bindless-vertex-buffers.md)).

Per-object data lives in storage buffers addressed by index, so a scene pass records one indirect draw per batch and the GPU supplies the draws.

### Several views in one frame

`Renderer::addScenePasses` can be called more than once in a graph frame, each time with a `SceneView` of its own and a target of its own: the editor's Scene view and the Game view of [#79](https://github.com/Pacheco95/sonnet/issues/79) are the same objects through two cameras. What a view owns lives in a `ViewState` the view's passes capture: the resolved draws, the orders and batches, the cull jobs, the cascades and their images, the frame constants and the statistics. The command and visible buffers are shared and sliced, each view taking the range after the ones declared before it, and the objects, materials and lights are uploaded per view. The lookup table's and the environments' graph imports are made once per frame and shared. `statistics(view)` reports a view's own numbers, and `statistics()` the first's. The id, mask and outline passes belong to the Scene view: they find its state by its `SceneView` and target size, and the selection is not per view. A second view costs what the first does, on the CPU and the GPU, and 98 MiB of graph images at 1080p with the default cascades. [ADR-0021](decisions/0021-two-views-in-one-frame.md) has the measurements, what is frame-wide and what is not, and what #79 changes.

## Render graph

The render graph is an engine feature this time; the previous iteration kept it in the demo and regretted it. Passes declare the resources they read and write; the graph allocates transient images, orders passes, and emits synchronization2 barriers and image layout transitions. Aliasing of transient memory is a later optimisation with no API change.

`renderer::RenderGraph` is rebuilt every frame between `reset` and `execute`:

- `importImage` registers an image the caller owns (the swapchain image, the viewport target), whose contents are undefined at the start of the frame, with an optional final layout the graph transitions to after the last pass (`Present` for the swapchain). `createImage` declares a transient image; its usage bits come from the passes that use it.
- `addPass` takes a setup callback that declares the pass's colour and depth attachments, sampled images and transfer sources or destinations, and an execute callback that records into the `ICommandList`. A pass with attachments is a graphics pass: the graph opens dynamic rendering on them around execute, with the declared load, store and clear values.
- `execute` runs the passes in declaration order. Before each pass it compares every declared use with the image's current state and emits one barrier per image whose layout changes or whose previous or next access writes; reads after reads in the same layout merge their stages instead. An image's first barrier of the frame waits for all earlier commands and memory writes, since the previous frame wrote the same target and may still be running. Transient images come from a pool keyed on their description, reused across frames and released after a few frames without use. Each pass is bracketed by two timestamps and timed on the CPU; `statistics` reports both per pass, plus barrier and transient-image counts, for the editor's overlay.

Topological ordering and pass merging are not there yet: passes run in the order they are added, which the renderer controls.

`reset` also begins a frame with a serial, `frameSerial`, that no graph in the process has used before. It is what a caller keys per-frame state on, as the renderer does to prepare a frame once however many of its passes are added. `frameIndex` counts one graph's frames from zero, so it measures a distance between two of that graph's frames and never identifies one: keyed on it and on the graph's address, a graph built where an earlier one stood matched the earlier one's first frame, and the renderer drew the earlier view again from that frame's memory.

The main pipeline is clustered forward ([ADR-0008](decisions/0008-clustered-forward-rendering.md)). `Renderer::addScenePasses` declares it, in this order:

1. Precomputation that is pending: the BRDF lookup table on the first frame, an environment's cubes on the frame after its creation ([Image-based lighting](#image-based-lighting)).
2. Skinning, when the view has skinned draws: see [Skinning](#skinning).
3. Culling: one compute pass covering every drawing pass that follows, see [GPU-driven submission](#gpu-driven-submission).
4. Four shadow cascades for the sun, each a depth-only pass into its own transient `D32Sfloat` image of `shadowMapSize` pixels. The cascades split the view depth up to `shadowDistance` between logarithmic and uniform spacing; each fits a bounding sphere around its slice of the frustum, so its size stays put as the camera turns, and snaps that sphere's centre in NDC to steps of `2 / shadowMapSize` so edges do not shimmer as it moves. Each slice overlaps the last 10% of the preceding slice and reserves five texels per edge for the receiver offset, bilinear PCF footprint and snapping. The projection is orthographic and reversed-Z, extended towards the light by the shadow distance so casters outside the view still cast.
   Then the depth maps of the spot and point lights that ask for them (`Light::castsShadows`), one for a spot light and six for a point light, within a budget ([Local shadows](#local-shadows)).
5. The depth pre-pass over the opaque and masked draws into the target's depth image.
6. Light clustering: a compute pass over a 16 by 9 by 24 grid of clusters, tiles of the screen sliced exponentially in view depth, that tests every punctual light's sphere against each cluster's view-space box and writes up to 63 light indices per cluster into a device-local buffer, with the memory barriers around it.
7. The forward pass into a transient `R16G16B16A16Sfloat` image: opaque draws with an equal depth test, so each visible surface is shaded once; then the skybox, a full-screen triangle at the far plane that samples the environment cube by view direction; then the blended draws sorted back to front without depth writes. Shading is the metallic-roughness model: Cook-Torrance with GGX, Smith and Schlick for the sun and the cluster's lights, inverse-square falloff windowed at the light's range, spot cones by their cosines, the sun shadowed by the cascade its view depth selects with a 3x3 kernel of hardware comparisons on the cascades in the depth array, image-based lighting through the split-sum approximation, or a flat ambient term without an environment. Opaque draws are grouped by pipeline and mesh so bindings change rarely.
8. Bloom: a chain of half-resolution passes, a 13-tap downsample then a tent-filtered upsample that adds each level to the one above, all in HDR.
9. Tone mapping: exposure, the bloom blended in by `bloomStrength`, the ACES curve and the display encoding into the `R8G8B8A8Unorm` target, or into a transient copy of it when anti-aliasing is on.
10. FXAA into the target.

The editor adds the id, selection mask and outline passes after these. `RendererSettings` holds the sizes and sample counts, which the tests turn down and which the editor keeps at their defaults.

The player adds one more: `addPresentPass` copies the finished colour image into the acquired swapchain image with a full-screen triangle. A swapchain's format is decided by the surface and is usually `B8G8R8A8Unorm`, not the renderer's own `ColorFormat`, so the pipeline that writes it is built for `RendererSettings::presentFormat` and only exists when that is set. The editor leaves it unset: it shows the scene through Dear ImGui, which owns the pipeline that writes the swapchain image there ([editor.md](editor.md#the-ui-module)).

## The renderer module today

Public headers under `sonnet/renderer/`: `RenderGraph.h`, `Mesh.h` (`Vertex`, `SkinWeights`, `Submesh`, `MeshData`, `MeshHandle`, `generateTangents`), `Primitives.h` (box, sphere, plane, cylinder, capsule, cone, torus, ramp, stairs, hemisphere, arch and icosphere generators for scenes without assets, each centred on its bounds; the ramp and stairs rise towards -Z and the arch's opening runs through its Z depth; the cylinder, capsule, cone, torus, ramp, stairs and arch are textured in metres, about one texture repeat per metre on every face (a whole number of repeats round a circle, so the texture meets itself at the seam), the hemisphere outwards from its pole so nothing pinches, and the icosphere by longitude (whole repeats round the equator) and distance from the top pole; the sphere still runs one texture over its whole surface), `Texture.h` (`TextureData`, `TextureHandle`, `generateMipChain`), `Material.h` (`MaterialDesc`, `MaterialHandle`), `Camera.h` (`Camera`, the reversed-Z infinite projection, and `rayDirection`, the ray through a point of a view, which the editor's gizmo and the scripts' `camera.ray` share), `SceneView.h` (`DrawItem`, `DirectionalLight`, `Light`, `EnvironmentHandle`, `DebugLine`, `SceneView`), `Renderer.h`, `RenderTarget.h` and `Picker.h`. Engine shaders are `shaders/sonnet.slang` (the shared module), the scene passes `depth.slang`, `cluster.slang`, `cull.slang`, `forward.slang` and `skybox.slang`, the precomputation `ibl.slang`, the post passes `post.slang`, the skinning `skin.slang`, the particles `particles.slang`, and the editor's `id.slang`, `outline.slang` and `debug.slang`.

- `Renderer` owns meshes, textures, materials, environments and the engine pipelines. `createMesh` uploads `MeshData` into device-local buffers: a storage buffer for vertex pulling and an index buffer, with the submeshes and bounds kept on the CPU. `createTexture` uploads every level and layer of a `TextureData` and `textureIndex` gives the bindless index shaders read it through. `createMaterial` keeps a `MaterialDesc`; `createEnvironment` takes an equirectangular map. `addScenePasses` declares the passes above for a `SceneView`; the first pass to record fills the frame constants, one `ObjectData` per draw, every material and every light from the transient allocator, and each pass pushes the constants and objects as the per-pass buffers and reaches the rest through buffer device addresses in the constants. Per batch it records `drawIndexedIndirect` of the one command the culling pass filled, binding the index buffer where the mesh changes ([GPU-driven submission](#gpu-driven-submission)). `statistics` counts scene draws and triangles, shadow draws, the local shadow maps, indirect calls, lights and the instances and vertices the skinning pass deformed, all as submitted rather than as drawn.
- Every `DrawItem` carries a 32-bit id, 0 for none. `addIdPass` draws the ids into an `R32Uint` image (`IdFormat`), depth-tested without writing against the depth the forward pass left, so only the visible surface of each entity remains; it is what picking reads. `addSelectionMaskPass` draws only the items whose id is listed into a second `R32Uint` image without a depth test, so the mask holds each selected entity's whole silhouette, occluded or not. `addOutlinePass` is the post pass over the colour image: it reads the mask through the pass image binding and colours the pixels within two of a masked silhouette, discarding the rest so the scene shows through. Because the mask ignores depth, an unselected object in front of a selected one never gets an outline of its own, and a selected object stays outlined through what hides it. None of the three passes is counted in the statistics.
- `addDebugLinePass` draws the view's `DebugLine`s, world-space segments with a colour, over a colour image as one line list pulled from the frame's transient memory. They are depth-tested against the scene's depth without writing it, pulled slightly towards the camera so lines lying on a surface, like a collider around its mesh, are not lost in it; the pass therefore goes before any pass that leaves the depth undefined, such as the id pass. The editor draws the physics colliders with it ([physics.md](physics.md#queries-and-forces)). Nothing is added when there are no lines, and the pass is not counted in the statistics.
- `Picker` answers "which id is under this pixel" without a stall: a request makes `addPass` copy this frame's id image into the frame slot's readback buffer, and `poll`, called once per frame after the device's `beginFrame`, returns the answer once the slot comes round `FramesInFlight` frames later. The editor turns the id back into an entity.
- `RenderTarget` is the colour and depth pair a viewport draws into, in the renderer's fixed formats (`R8G8B8A8Unorm`, `D32Sfloat`), kept across frames so Dear ImGui can display the colour image and recreated on resize with the device's deferred destruction.
- The draw list is handed down by the layer above (`world`); the renderer never asks where it came from.

### Local shadows

Spot and point lights that set `castsShadows` get depth maps, each a `D32Sfloat` image of `localShadowMapSize` pixels (1024 by default) drawn by the same shadow pipelines and the same culling and indirect path as the sun's cascades, so masked materials and skinned meshes cast as they do there. A spot light has one map; its projection is the light's cone as a reversed-Z perspective over an infinite far plane: twice the outer angle (at most 160 degrees) widened by four texels, with a near plane of a hundredth of the range, between 5 and 50 centimetres. A point light has six, the faces of a cube: the same perspective with a 90 degree field of view widened by four texels, looking along +X, -X, +Y, -Y, +Z and -Z (the Y faces take +Z as their up vector, the others +Y), so a surface falls in the face of the light's dominant axis towards it. Each face is a map of its own, a culling job and a pass, and the forward shader reads the one a surface falls in (see Sampling below).

- **A budget, per view.** `maxLocalShadows` (8 by default) is how many lights a view gives maps to, spot and point together, independent of the 1,024-light limit of the illumination. Like the cascades the maps belong to a view, so the Game view pays for its own. When more lights ask, the first ones in the `SceneView::lights` order are chosen, so the same lights are chosen on every run; the rest illuminate without a shadow. The renderer clamps the budget to `Renderer::MaxLocalShadows`, 28, and that is also how many maps a view holds: the device has 64 bindless depth images ([ADR-0017](decisions/0017-depth-images-in-their-own-bindless-array.md)), the two views the editor declares each take half, and a view's four cascades come out of its half. A point light's six maps count against the 28, so four point lights fill 24 of them and the default budget of eight lights cannot all be point lights; a light whose maps no longer fit is passed over, and a spot light after it can still be granted. `localShadowBudget()` gives the clamped light count, and zero when `shadows` is off.
- **Where the shader finds them.** The frame constants carry `localShadows`, the address of one `LocalShadow` per rendered map (the light-space matrix and the slot in `depthTextures[]`), and each `Light` in the light buffer carries `shadow`, its index into that array or `0xFFFFFFFF` without a map. A point light's six faces are consecutive entries in the order above, and its `shadow` is the first. The shadow vertex shader takes its matrix from the push constant `shadow`: a cascade below `CascadeCount`, a local map above it.
- **Sampling.** The forward shader multiplies `spotShadow` into a shadowed spot light's attenuation, and `pointShadow` into a shadowed point light's, inside the cluster loop, for opaque and blended surfaces alike; the sun's cascades and the lights without a map are untouched, so turning `castsShadows` off, passing the budget or disabling the light leaves the illumination as it was. It is the cascades' 3x3 kernel of hardware comparisons on the light's map: the receiver moves along its geometric normal by three texel footprints at its distance from the light, the filter must fit inside the map (a point outside it is lit), and the receiver also moves two texels towards the light in view depth, a distance rather than the `shadowBias` of the cascades: the map's depth is near over distance, so a constant in it grows with the square of the distance and at ten metres left a strip of light behind a plinth. The map's index differs between the fragments of a draw, so it goes through `NonUniformResourceIndex`; the cascades' unrolled branches ([Shadow sampling](#shadow-sampling)) are not an option for up to 28 maps. `pointShadow` picks the cube face by the major axis of the point's offset from the light (+X, -X, +Y, -Y, +Z, -Z, the order of the maps) and samples that face the same way, with the normal offset of one face texel at the distance, `2 * distance / size`. The faces are wider than 90 degrees by four texels, so the filter's taps, clamped to the face, stay on the map across a seam. A GPU test with two shadowed lights in one cluster, each shadowed by a different map, guards the case on Lavapipe and on the NVIDIA driver, and it passes on MoltenVK (Apple M4 Max, checked by hand with the basic sample's shadows on and off); the phone's compiler path is unchecked.
- **Cost.** Each map is a culling job and a pass, named `shadow spot N` or `shadow point N face F` after the light's index in `SceneView::lights`, timed with the rest in the graph's statistics, so the editor's overlay lists it. `RenderStatistics::localShadowCount` is the lights a view rendered maps for, `localShadowMapCount` the maps they took, and `shadowDrawCount` includes their draws. `Renderer::localShadows(view)` returns each map's light, face, matrix and graph image for tests and tools. A 1024 by 1024 map is 4 MiB of graph images, so a point light is 24 MiB of them.

### Shadow sampling

The four cascade sampling branches are statically unrolled, keeping each comparison image index uniform inside its branch. Selecting the image dynamically at a view-depth split produced a dark row on an unobstructed plane on Intel and Lavapipe; annotating that index as non-uniform alone did not remove it. The GPU regression covers all four cascades at two shadow-map resolutions and compares every pixel against the same plane with shadows disabled.

A receiver is offset along its interpolated geometric normal, before normal mapping, by three world-space shadow texels times the sine of its angle to the light. `shadowBias` adds a small constant reversed-Z depth bias; it no longer grows with the cascade index. Sampling requires the whole filter footprint (1.5 texels from the map edge) to fit, otherwise it tries a farther cascade. The last 10% of each slice blends into the next cascade, whose projection includes that overlap; the last cascade fades to unshadowed at `shadowDistance`.

## GPU-driven submission

Opaque draws are submitted by the GPU ([ADR-0012](decisions/0012-gpu-driven-rendering.md), [ADR-0016](decisions/0016-instanced-batches.md)). The CPU records neither a call nor a command per draw; it records one instanced command per *batch*, where a batch is a run of draws sharing a pipeline, a front face, a mesh and a submesh. The draw list is already sorted by double-sidedness, then by whether the transform mirrors, then by mesh, then by submesh, so those runs are simply its segments.

- **Candidates.** Once per frame the renderer writes a `CullDraw` per entry of an order list into transient memory: the draw's world-space bounds, the object it draws, its submesh's index range, which batch it belongs to and where that batch starts in the order list. The bounds are the mesh's object-space box through the draw's transform, all eight corners, so a rotation stays conservative. There are two arrays: the opaque draws, which the cascades, the depth pre-pass and the forward pass all test, and every draw, which the editor's id and selection-mask passes test.
- **Culling.** `cull.slang` runs one thread per candidate. It rebuilds the frustum from the pass's view-projection matrix by the Gribb-Hartmann method and rejects a candidate whose bounds fall outside any plane. A survivor takes an instance of its batch's command with an atomic add on the command's `instanceCount`, and writes its object index at that slot of the batch's run of the *visible list*, a device-local `uint` buffer with a slot per draw per job. The survivor that took slot zero also writes the command's index range and its `firstInstance`, the batch's first slot in the list. One compute pass covers every scene pass of the frame: a first dispatch per job writes each of its batches a command with no indices and no instances, then one dispatch per job culls, with barriers ordering the previous frame's command fetch and vertex reads before the writes and the writes before this frame's. A batch nothing survived in draws nothing, and so does every batch of a job whose candidates did not fit the frame's transient memory, since only the clearing ran. The selection-mask job also requires the candidate's `CullSelected` flag, so the mask holds exactly the selected silhouettes.
- **Submission.** Each drawing pass records, per batch, `drawIndexedIndirect` of that batch's one command, after `bind pipeline` where the pipeline changes, `bind index buffer` where the mesh does and `setFrontFace Clockwise` ahead of a mirrored batch; since every pass shares the batches, the shadow, depth, id and selection passes follow. The vertex shaders find their object as `visible[SV_StartInstanceLocation + SV_InstanceID]` (`drawObject` in `sonnet.slang`), so a batch's instances each draw their own. The number of commands a pass submits is its batch count, which the CPU knows, so no draw count is read from the GPU and `drawIndirectCount` is not used. A mesh whose submeshes take different materials makes a batch per submesh, which it already cost in pipeline and index-range changes.
- **What stays on the CPU.** Blended draws: their order is back to front and view-dependent, which is a sort rather than a filter. They take the same pipelines and the same shaders. The visible list ends in a *direct range* with a slot per draw of the frame holding its object index, uploaded through the staging ring on the frame's first direct draw, and each direct `drawIndexed` names its slot as its first instance, so every scene shader finds its object the same way however it was submitted. A pass that could not reserve a culling job, which only a second set of scene passes for the same view in one frame does, takes the same direct path. The per-frame object, material and light upload also stays on the CPU, and is the larger part of what a frame costs there.

`RendererSettings::jobs` spreads the per-frame fill — one `ObjectData` per draw, and the cull candidates per batch — over the job system ([ADR-0013](decisions/0013-job-system.md)); a null pool runs it on the calling thread, which is what the tests and `sonnet_cook` get. Every iteration writes one slot of its own, so the result does not depend on how it was split. It buys less than it looks like it should, because writing an entry per draw into `MemoryUsage::CpuToGpu` memory is bandwidth to host-visible device memory rather than computation, and threads cannot remove bandwidth. Writing less can. `ObjectData` carries no normal matrix: the vertex shader derives it from `model` as the cofactor matrix of its upper 3×3 (`transformNormal` in `sonnet.slang`), which is the inverse transpose times the determinant: a scale the normalised normal drops, and a sign under a mirroring transform that `transformNormal` multiplies back out, as the tangent's bitangent sign takes it too, so an entry is 96 bytes rather than 160 and the fill no longer inverts a matrix per draw. On the benchmark the fill went from 0.26 ms on one thread and 0.18 ms at best on the pool to 0.15 ms on one thread, and the pool no longer changes it at all. The rest of the cost is the objects that did not move, rewritten every frame; see [roadmap.md](roadmap.md#the-per-frame-fill-is-bandwidth-not-computation).
- **What this costs in visibility.** The CPU never learns how many draws survived: `RenderStatistics` reports what was submitted, and `indirectCallCount` the batches. The null device's trace shows `drawIndexedIndirect "draw commands" count 1` per batch, so the tests above `rhi` assert on the calls a pass makes. The GPU tests on Lavapipe are what prove culling keeps the right things. A ground plane wider than the frustum and a lit box still render, pixel for pixel, when a crowd of draws outside the frustum, in the box's own batch, is added to the scene. Two submeshes of one mesh draw in their own places, and three draws in two batches each draw in their own colour. An unselected box beside a selected one must add no instance to the mask.

Measured with `renderer_tests "[benchmark]"`, ten thousand draws of two meshes and a hundred lights at 1080p on an RTX 4090, Release:

| | Before | After |
|---|---|---|
| CPU, the six scene passes | 2.69 ms | 0.28 ms, of which 0.26 ms is the per-frame upload |
| GPU, whole frame | 1.24 ms | 0.64 ms |
| Draw calls recorded | 60000 | 12 |

The same scene in Debug went from about 93 ms of CPU recording, the figure M3 measured, to about 13 ms, nearly all of it the object upload. The GPU time falls because nothing culled the draws before.

The benchmark reports the frame's CPU split into recording the passes and submitting in `endFrame`. The submit time is where MoltenVK turns every recorded indirect command into its own Metal draw, which no pass's recording time includes. Before [ADR-0016](decisions/0016-instanced-batches.md) a batch was a command per draw, drawn through `drawIndirectCount` where the device had it and over every slot where it did not ([ADR-0014](decisions/0014-indirect-draws-without-count.md), superseded): on an Apple M4 Max that was sixty thousand commands a frame, 4.96 ms of submission and 0.37 ms of GPU time in shadow cascade 0. ## Skinning

A skinned draw carries the range of `SceneView::joints` that deforms it, each matrix taking the mesh's bind pose into the drawn entity's space, and a key naming the instance across frames (ADR-0010). The first pass the renderer declares in a graph frame, whether the scene passes or the editor's id or mask pass, is preceded by a compute pass that runs `skin.slang` once per instance: one thread per vertex blends up to four joint matrices, by the mesh's `SkinWeights` buffer, and writes the deformed vertex into a device-local buffer the renderer keeps for that instance, reusing it every frame and releasing it a few frames after its last draw. Every later pass pulls its vertices from that buffer through its slot in the bindless vertex-buffer array, which the draw's `ObjectData` names ([ADR-0015](decisions/0015-bindless-vertex-buffers.md)), so no vertex shader has a skinned variant and an instance is deformed once however many of the eight passes draw it. A memory barrier on each side of the pass orders it after the previous frame's draws and before this frame's.

A draw is skinned only when its mesh was created with skin weights and its joint range fits the view's; otherwise it draws in its bind pose.

Morph targets run in the same pass ([ADR-0023](decisions/0023-animation-blending-morph-targets-and-particles.md)). A mesh created with `MeshData::morphTargetCount` targets keeps their `MorphDelta`s (position, normal and tangent, 36 bytes a vertex a target, target after target; at most `MaxMorphTargets`, 8) in a storage buffer of its own. A draw with `morphWeightCount` weights from `SceneView::morphWeights` and a `skinInstance` gets its instance buffer like a skinned draw: the pass first adds each target's delta times its weight to the bind-pose vertex, renormalises the normal and tangent, and then skins the result if the draw also has joints. A draw whose weights do not fit the view's, or whose mesh has no targets, draws as it is. Culling still uses the bind-pose bounds, so a morph that moves vertices outside them can be culled early. `world` builds the joint matrices from the skeleton ([world.md](world.md#animation)).


## Particles

A `ParticleEmitterItem` in `SceneView::particles` is a GPU particle emitter for the frame ([ADR-0023](decisions/0023-animation-blending-morph-targets-and-particles.md)): its `key` names it across frames, and the renderer keeps its particles under that key in three device buffers, a ring of `maxParticles` 32-byte particles, the alive list of their slots and one indirect command, released eight graph frames after the emitter was last drawn. `addScenePasses` resolves the emitters into jobs. The first view of a graph frame to see an emitter advances it: the CPU decides how many particles are born, `rate * deltaTime` with the fraction carried and the item's `burst` once when the state is created, and moves the ring's head past them; the `particles` compute pass, after light clustering, then resets each command, and `simulate` runs one thread per slot: slots from the head round the ring start a particle from a hash of the emitter's seed and the particle's serial, which is why the same sequence of frames gives the same particles on any machine, and every other live slot integrates gravity, drag and velocity, and appends itself to the alive list through an atomic on the command's instance count. A second view in the same frame only draws. An emitter with `simulate` false runs the pass with nothing born and no time passed, so it still compacts and draws.

The forward pass draws the emitters after the blended meshes, far to near by their position, each with one `drawIndexedIndirect` of the shared quad's six indices and the command's instance count: camera-facing quads, depth-tested against the scene without writing depth, alpha or additive by `blend`. Size and colour interpolate from birth to death; without a texture a particle is a soft disc, and the colour of an additive emitter is weighted by its alpha so fading out fades the glow. Particles are not in the shadow, depth, id or mask passes, so they are not picked or outlined, and particles within one emitter are not sorted. `statistics` reports `particleEmitterCount` and `particleSlotCount`, the slots simulated rather than the live count, which the CPU never reads back. `resetParticles(key)` forgets an emitter so it starts again with its burst.

## Resources and materials

- Meshes: `Vertex` is position, normal, a tangent with the bitangent sign in `w`, and one uv set, 48 bytes under scalar layout; a skinned mesh has one `SkinWeights` per vertex besides, four joint indices and their weights; `generateTangents` derives tangents from the uv derivatives for meshes without them, the primitives included. A mesh is a list of submeshes, each an index range with a material slot, plus bounds; a `DrawItem` names one submesh and one material.
- Materials: the glTF metallic-roughness model in `MaterialDesc`: base colour, emissive, metallic, roughness, normal scale, occlusion strength, the five textures, an alpha mode (opaque, masked with a cutoff, blended), the texture wrap and double-sidedness. The renderer keeps the descriptions and writes them all into a transient storage buffer every frame, with the default material in slot 0, so a change shows on the next frame and a draw with an invalid handle uses the default. An invalid texture is the white default, or the flat normal for the normal map. Double-sided materials use pipelines that cull nothing and flip back-facing normals.
- Textures: `TextureData` holds every level tightly packed, level-major with a cube map's six faces inside each level, as KTX2 lays them out; `generateMipChain` box-filters an RGBA8 image, averaging sRGB data in linear space. Every material texture is sampled through one of three anisotropic samplers by wrap mode.
- Lights: the sun is the `DirectionalLight` of the view; `Light` is a point or spot light with a range, clustered by the renderer. Up to 1024 per view.
- Every resource is reached through a `Handle<Tag>` with generation checks ([architecture.md](architecture.md#resource-handles)).

## Image-based lighting

An environment is created from an equirectangular map, typically an RGBA16F HDR image, and precomputed by compute passes the next `addScenePasses` declares, in the render graph like everything else: the map is converted into a cube (`environmentSize` per face, RGBA16F), the cube's mip chain is built one level per pass, the diffuse irradiance cube is integrated with cosine-weighted samples, each read at the level whose texels match the solid angle the sample stands for (at least the level that is 32 texels wide), so a sky with fine detail does not blotch a smooth surface, and the specular cube is prefiltered with GGX importance sampling at one roughness per level, reading the source at a lod chosen from the sample's solid angle so bright texels do not become fireflies. The split-sum BRDF lookup table is computed once per renderer on the first frame. All of these are storage images and stay in the General layout; the graph orders the forward pass's reads after the writes, so an environment lights the frame that computes it. The skybox pass samples the environment cube by view direction; `SceneView::environmentIntensity` scales both the lighting and the background, and `exposure` the tone mapping.

## Editor viewport and ImGui

The scene renders into an offscreen colour image that the viewport panel displays with `ImGui::Image`. Picking is a small pass that writes entity ids into an image and reads back the pixel under the cursor (`Picker`). The selection outline is a post pass over a mask image holding the selected entities' silhouettes.

ImGui uses its SDL3 and Vulkan backends, initialised in dynamic-rendering mode, drawing directly to the swapchain image after the scene. Multi-viewport is enabled on desktop. The `ui` module wraps both in `ImGuiLayer` ([editor.md](editor.md#the-ui-module)); the editor declares the ImGui draw as the last graph pass, rendering into the swapchain image and sampling the viewport target, so the graph orders it after the scene.

## Debugging

- Debug builds request `VK_LAYER_KHRONOS_validation` with synchronization validation enabled, and route messages to the log with the object names attached.
- Every Vulkan object gets a `VK_EXT_debug_utils` name from its handle's debug name, so RenderDoc and validation output are readable.
- GPU timestamps per render-graph pass feed the on-screen overlay and Tracy's GPU zones.
- `RendererSettings::debugView` makes the forward pass write one term of its shading in place of the final colour, before tone mapping: the albedo, the shading normal, the sun's direct light without its shadow, the shadow factor, the diffuse and specular image-based light, the BRDF lookup table's scale and bias in red and green, or the view-depth cascade index (red, green, blue and yellow). The cascade diagnostic shows the nominal splits without blending, so they can be compared with the shadow-factor image. The editor offers it under View > Shading term. Comparing these term by term between two platforms is how ADR-0017's cause was found.

## Testing

- `rhi` interfaces have a null implementation used by unit tests of `renderer`, `assets` and `world`, so those modules are tested without a GPU. `renderer_tests` checks the camera's projection and the ray through the centre and a corner of a known view, the graph's barriers, pooling and timings and, against the null device's trace, the renderer's pass list and draw recording, the batches each pass submits indirectly, the sorting of blended draws on the direct path, texture uploads and material indices, an environment's precomputation, the id, mask and outline passes, the debug line pass, the skinning pass with its one dispatch per instance and the reuse and release of its buffers, two views in one graph with their own passes, statistics and cull slices, the local shadow budget, the six faces a point light takes from it and which lights it picks, the picker's readback timing, and that the renderer destroys every pipeline it creates.
- The Vulkan implementation is tested on Lavapipe in CI: device creation, resource lifetime including deferred destruction, a triangle drawn into an offscreen image and read back, vertex pulling with the per-pass buffers and the reversed-Z depth test, an `R32Uint` id image written by one pass and read by the next through the pass image binding, a mipmapped texture and a cube map uploaded through the staging ring and sampled through the bindless set, an upload larger than the ring, a solid-colour compressed image of 13×7 texels with its full mip chain uploaded and sampled at its first and last levels (BC7 everywhere; ASTC 4×4 and 6×6 only where `astcSupported`, so on Apple silicon and phones, not in CI), a compute pass filling a storage image, timestamps and the transient allocator, and later golden-image comparisons of sample scenes with a tolerance. `renderer_tests`, `ui_tests` and `editor_tests` also run GPU cases on Lavapipe: a lit box read back from the viewport target, the sun's shadow beside a box, a clustered point light that reaches only the ground within its range, an environment that fills the background and lights a sphere, a texture's green reaching the albedo in the shader that also compares depth, the BRDF lookup table's scale and bias, a box picked by id and outlined over several frames, a selected surface whose occluder stays unoutlined, a scene that renders pixel for pixel the same whether or not draws outside the frustum are in its draw list, debug lines hidden behind a box and drawn in front of it, a skinned box moved by its joint, a spot light's shadow map and a point light's faces read back as depth, a spot light's shadow on the ground behind a box (moved with the box, gone without the request or the budget, and one light's map apart from another's), the same for a point light seen through two different cube faces, two cameras drawn into two targets in one frame, each showing its own box, including on the frame that computes the lookup table and an environment, ImGui frames drawn into a headless swapchain, and whole editor frames. Swapchain tests use SDL's offscreen video driver and `VK_EXT_headless_surface`, which Lavapipe supports; on drivers without headless surfaces those tests skip. They include a resize request that recreates the swapchain at the window's new size and one at the swapchain's own size that keeps every image, a swapchain suspended after three frames, acquiring nothing while suspended, even after a resize request, and resumed at the same extent for three frames more, and `suspend` twice and `resume` without a suspend, each doing nothing more, all with validation silent. Loaders before 1.4 emulate that extension for every driver and some drivers crash inside the surface queries, so on such loaders the tests run only on Lavapipe; `DeviceInfo` reports loader version and driver name for this. The test shader is compiled by the same `sonnet_add_shaders` rule the applications use. CTest runs `rhi_tests` twice: as it is, and as `rhi_tests_vulkan_1_3`, with `SONNET_TEST_API_VERSION_CAP=1.3` making every test device take `DeviceDesc::apiVersionCap`. The cap lowers the version the instance asks for, which bounds the device's, so a 1.4 device takes ADR-0019's extension path and the validation layer fails any 1.4 command or structure used without its extension; enabling `VkPhysicalDeviceVulkan14Features` under the cap fails `vkCreateDescriptorSetLayout` for the push-descriptor flag, for example.
- Validation-layer messages fail tests when they occur: `IDevice::validationMessageCount` is checked by the test fixture.
