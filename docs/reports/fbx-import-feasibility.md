# FBX fits Sonnet’s existing asset pipeline

**Adding FBX import is feasible; ufbx is the recommended parser.** Sonnet already represents models, meshes, materials, skins, animation clips and morph targets, so a defined game-asset subset can use the existing renderer and cooked bundle format. The work is principally source conversion and integration across the asset pipeline. Estimate **5–10 engineer-days for bounded static support**, including a short spike, and **another 5–10 days for animation within current engine limits**. These are planning estimates, conditional on named exporters and representative fixtures. They do not cover arbitrary DCC scene fidelity or FBX export. ([Importer types, line 51](../../modules/assets/include/sonnet/assets/Importers.h); [cook, line 110](../../modules/assets/src/Cook.cpp))

Investigation date: **2026-11-09**, checkout **`4c18021`**. This assessment combines repository inspection and upstream documentation. No parser was compiled, FBX asset imported, conversion benchmark run or visual comparison performed. The detailed notes are [ufbx](fbx-import-feasibility/ufbx.md), [alternatives](fbx-import-feasibility/alternatives.md) and [Sonnet integration](fbx-import-feasibility/sonnet-integration.md).

The parser choice is reasonably clear for the requested scope:

| Option | Fit for Sonnet | Recommendation |
|---|---|---|
| **ufbx** | C99/C++11-compatible source library with an MIT license option; supports ASCII/binary FBX, meshes, skinning, morphs, textures and animation evaluation. Godot uses it by default for new FBX imports since 4.3. ([Build](https://ufbx.github.io/getting-started/), [license](https://github.com/ufbx/ufbx/blob/main/LICENSE), [features](https://github.com/ufbx/ufbx), [Godot](https://docs.godotengine.org/en/stable/tutorials/assets_pipeline/importing_3d_scenes/available_formats.html#importing-fbx-files-in-godot)) | Best initial candidate for an FBX-specific addition. |
| **Assimp** | Viable FBX importer with animation, weights, embedded textures and pivot controls. Its broader format support and standard vcpkg dependencies exceed this request. ([Configuration](https://github.com/assimp/assimp/blob/master/include/assimp/config.h.in), [package](https://vcpkg.io/en/package/assimp.html)) | Prefer if several additional source formats become a concrete requirement. |
| **Autodesk FBX SDK** | Vendor SDK under its own EULA. Current platform summary lists Windows, macOS, iOS and Linux, without Android. ([SDK](https://aps.autodesk.com/developer/overview/fbx-sdk)) | Consider for a demonstrated fidelity requirement; packaging and distribution need separate review. |
| **Convert to GLB** | Blender offers a practical manual workflow. Godot’s FBX2glTF fork explicitly ended active maintenance, and its binaries include Autodesk SDK code. ([Workflow](https://godotengine.org/article/introducing-the-improved-ufbx-importer-in-godot-4-3/), [converter](https://github.com/godotengine/FBX2glTF/blob/master/README.md)) | Useful immediately; avoid making the retired converter a mandatory dependency. |

The checked ufbx release is **0.23.1**. Sonnet’s pinned vcpkg baseline contains no ufbx port, and none was found at the current upstream port paths. Use a small pinned overlay port, or the documented `FetchContent` exception for a library without a port; retain fastgltf. ufbx’s desktop CI coverage supports evaluating it, but Sonnet’s Android/iOS toolchains still need compilation checks. ([Changelog](https://github.com/ufbx/ufbx/blob/main/misc/changelog.md); [baseline tree](https://github.com/microsoft/vcpkg/tree/a1cae005c39be7b18ba319fced856b68d7276271/ports); [port location checked](https://raw.githubusercontent.com/microsoft/vcpkg/master/ports/ufbx/vcpkg.json); [build policy](../build.md); [platform coverage](https://github.com/ufbx/ufbx#platforms))

**Import-time behavior is not automatically an editor-only dependency.** The assets target currently links fastgltf unconditionally, and the player can open source projects as well as bundles. Placing ufbx alongside fastgltf therefore requires target-platform builds under today’s architecture. Cooked playback would still consume native payloads without FBX files or FBX curve evaluation. Separating all importers into host tooling would be a distinct architectural change. ([Assets CMake](../../modules/assets/CMakeLists.txt); [player modes](../player.md))

There is no importer plugin interface to implement. The existing plain functions already return engine-owned data, although their names are glTF-specific. Generalize that shared result and dispatch to format-specific parsers, keeping one model pipeline. The main implementation surface is:

| Location | Required change |
|---|---|
| [Importers.h, line 51](../../modules/assets/include/sonnet/assets/Importers.h) | Generalize `GltfImport`, structure and animation metadata; add FBX full import, structure-only read and dependency enumeration. |
| [AssetDatabase.cpp, lines 38, 717, 794, 1292, 1807, 1994](../../modules/assets/src/AssetDatabase.cpp) | Recognize `.fbx`; extend sub-asset discovery, async import/publication, hierarchy reads, mobile texture cooking, moves and reimport. |
| [AssetCommands.cpp, line 536](../../modules/editor/src/AssetCommands.cpp), [Editor.cpp, line 1571](../../modules/editor/src/Editor.cpp), [InspectorPanel.cpp, line 608](../../modules/editor/src/InspectorPanel.cpp) | Generalize dependency copying, import/duplicate behavior, file filter and inspector animation metadata. |
| [Assets CMake](../../modules/assets/CMakeLists.txt), [manifest](../../vcpkg.json) | Add the pinned parser dependency and FBX implementation; update affected documentation with the supported subset. |

Models already become complete prefab hierarchies, while meshes and materials are sub-assets. Preserve identical node ordering and helper-node naming between structure-only and full import; the database relies on stable hierarchy storage. Mesh/material/clip UUIDs currently derive from indices, whereas prefab-node UUIDs derive from name paths. Identical reimports can be stable, but arbitrary exporter reordering, renamed nodes or duplicate names can change bindings and overrides. Document that boundary and test it; improving semantic identity would need a deliberate policy change. ([Prefab construction, line 754](../../modules/world/src/Scene.cpp); [sub-assets, line 381](../../modules/assets/src/AssetDatabase.cpp); [hierarchy lifetime test, line 595](../../modules/assets/tests/DatabaseTests.cpp); [ADR-0030](../decisions/0030-model-node-identities.md))

The first release should promise static polygon meshes with triangulation, hierarchy/instances, material assignments, normals/tangents/vertex colours, up to two UV sets, supported textures and conversion to Sonnet’s axes and metres. ufbx supplies triangulation, independently indexed attributes and instance material data; Sonnet must preserve seams and construct its own vertex layout. Embedded and external textures need consistent handling across import, move, duplicate, reimport and mobile cook. Define relative-path resolution and missing-texture diagnostics rather than retaining hidden dependencies on an exporter’s machine. ([ufbx meshes](https://ufbx.github.io/elements/meshes/); [mesh types](../../modules/renderer/include/sonnet/renderer/Mesh.h); [existing dependency policy, line 1018](../../modules/assets/src/GltfImporter.cpp))

**Transforms and materials carry the largest static-import risk.** FBX supports pivots, geometric transforms and scale inheritance that require evaluation or helper nodes. Use ufbx’s computed transforms and conversion options, preserving helpers where needed; blindly flattening matrices into one translation/rotation/scale node can lose shear. Sonnet’s metallic-roughness materials also require mapping or approximation of legacy FBX materials, potentially packing separate metallic/roughness textures. Arbitrary shader graphs, procedural geometry and camera/light fidelity should be outside the first contract. ([ufbx transforms](https://ufbx.github.io/fbx/node-transforms/); [nodes](https://ufbx.github.io/elements/nodes/); [material capabilities](https://ufbx.github.io/reference); [MaterialSource, line 85](../../modules/assets/include/sonnet/assets/Asset.h))

Animation can reuse existing clips and skins after import-time baking. ufbx can bake layered/Euler animation into linear translation, quaternion rotation and scale tracks; choose explicit tolerances and verify bind poses, take ranges and rotation continuity. Sonnet supports **four influences per vertex and eight morph targets**. Excess weights need selection, renormalization and diagnostics. Dual-quaternion skinning cannot be reproduced exactly by linear skinning, and progressive/in-between morphs need conversion or explicit exclusion. Retargeting, live control rigs and animation-layer editing remain separate features. ([ufbx animation](https://ufbx.github.io/elements/animation/); [deformers](https://ufbx.github.io/elements/deformers/); [Sonnet mesh limits](../../modules/renderer/include/sonnet/renderer/Mesh.h); [clip types](../../modules/assets/include/sonnet/assets/Animation.h))

The proposed delivery gates are engineering judgment, not measured commitments:

| Gate | Estimated effort | Evidence needed |
|---|---|---|
| Parser/conversion spike | **1–2 engineer-days** | Build the dependency; import a few static and rigged fixtures into existing CPU data; check axes, scale, pivots and bind pose. |
| Bounded static support | **5–10 days total**, including spike | Complete editor/database/reimport integration, supported materials/textures, desktop/mobile cooking and regression fixtures. |
| Animated support | **Another 5–10 days; 10–20 total** | Validated skinning, baked takes and supported morph animation, with source/cooked pose comparisons. |
| Broad exporter compatibility | **At least 4–8 weeks**, lower confidence | Larger exporter/version corpus and ongoing fixes; no finite schedule guarantees unrestricted FBX fidelity. |

Acceptance should cover ASCII/binary exports from Blender and at least one Autodesk DCC; centimetres/metres and Y/Z-up; mirrored/nonuniform scale and pivots; n-gons, UV seams, instancing and multiple materials; embedded/external/missing textures; duplicate/unnamed nodes and reordered sub-assets; multiple clips, excess influences and morphs; malformed/truncated input. Check async publication, metadata/full hierarchy agreement, supported reimport identities, import undo/redo, viewport placement and mobile texture cooking. Assert that cooked bundles contain every expected sub-asset: the current cook can warn and omit an asset while otherwise succeeding. Use existing null-RHI tests and engine-generated editor/player captures, and keep glTF regression tests green. ([Database tests](../../modules/assets/tests/DatabaseTests.cpp); [cook tests](../../modules/assets/tests/CookTests.cpp); [cook warning behavior, line 160](../../modules/assets/src/Cook.cpp); [capture guidance](../../AGENTS.md))

The next useful step is the **1–2 day spike against a small, redistributable corpus chosen from the intended asset producers**. It should resolve transform policy, material expectations and platform builds before committing to a release estimate. No user FBX corpus was supplied, so exporter-specific fidelity, import cost, memory use and actual cross-platform success remain unmeasured.
