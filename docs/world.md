# world

The entity component system: a flecs world with the engine's components, phases and systems, the scene and prefab files, and the draw list handed to the renderer. flecs types appear unwrapped in the public headers by decision ([ADR-0003](decisions/0003-ecs-library.md)). Depends on `assets`, flecs and nlohmann-json.

| Header | Contents |
|---|---|
| `Components.h` | The core components as plain structs: `Identity`, `Name`, `Transform`, `WorldTransform`, `MeshRenderer`, `SkinnedMesh`, `Animator`, `AnimationLayer`, `MorphWeights`, `SkinPose`, `Camera`, the three lights, `Environment`, `Spin`, and the tags `Static`, `EditorOnly`, `Disabled` |
| `World.h` | `World`: the flecs world with everything registered, entity creation with identities, hierarchy helpers and world matrices, prefab instantiation, the component registry open to subsystems, JSON per component, play mode, the fixed timestep and `progress` |
| `Scene.h` | The scene and prefab file format: `saveScene`, `loadScene`, `savePrefab`, `loadPrefab` and their file variants, and `loadModelPrefab` for a glTF file's hierarchy |
| `Animation.h` | `AnimationSystem`: the clip playback and skin palette systems, constructed on a world and the asset database |
| `DrawList.h` | `buildDrawList` (of the scene, of a prefab's tree, of one mesh), `buildLightList`, `sceneLight`, `sceneCamera`, `buildCameraList`, `sceneEnvironment`: what the world hands the renderer |

## Components

Every component is registered with flecs reflection in `World`, under the name scene files use, so the inspector, the serializer and the scripting bindings enumerate fields through one system. Subsystems register theirs the same way through `World::registerComponent`, which returns the flecs component to add members to and makes it inheritable by prefab instances: `physics` its bodies and colliders ([physics.md](physics.md#components)), `gui` its UI elements ([gui.md](gui.md#components)), `scripting` its `Scripts` ([scripting.md](scripting.md#scripts-and-instances)) (ADR-0009, ADR-0022, ADR-0026). GLM's `vec2`, `vec3`, `vec4` and `quat` are registered as structs, `std::string` as text, and `registerVector<Elem>` teaches reflection a `std::vector` of an already registered struct through flecs' opaque collections, so a component can hold a list of structs: the JSON serializer writes an array, the meta cursor the inspector uses can walk and grow it, and loading a shorter array replaces a longer one. A string member that holds JSON text is marked with `embedJson` and then appears in scene files, and in the copies undo keeps, as the JSON itself rather than as an escaped string (`Scripts` slots do this for their properties); `core::Uuid` is an opaque type that serializes as its canonical string, which is how asset references appear in files; angles carry the flecs `Radians` unit, which the inspector reads to show degrees ([conventions.md](conventions.md#math-conventions)).

Four components are structural and are not in the registry: `Identity` holds the UUID that scenes, prefab references and undo refer to; `WorldTransform` and `SkinPose` are derived every frame; `Name` is written as the file envelope's `name`. `World::createEntity` gives every scene entity all three plus a `Transform`.

`Transform` is local. The transform system, in the `PreRender` phase, computes `WorldTransform` as parent times local, parents first through the flecs `cascade` ordering over `ChildOf`; `World::worldMatrix` computes one entity's from the hierarchy directly, for code that runs before the transform system in a frame. `World::setParent` keeps the world transform when reparenting, so an entity stays where it is on screen. `Transform::fromMatrix` decomposes a matrix back, discarding shear.

`PreviousWorldTransform` keeps last frame's `WorldTransform` for the renderer's motion vectors ([ADR-0024](decisions/0024-temporal-anti-aliasing-and-occlusion-culling.md)). It is structural like the world transform: derived, not serialized, not inherited. A system copies the world matrix into it at the start of `PreRender`, before the transform system moves it on, and a second one, after the transform system, gives an entity that has none its current matrix, so an entity that appears has no motion in its first frame.

`MeshRenderer` references a mesh asset by identity ([assets.md](assets.md#identity)), a built-in primitive or a glTF mesh, with an optional material that overrides every slot of the mesh (nil keeps the mesh's own materials) and a colour that multiplies the material's base colour; on an opaque material the colour's alpha below 1 dithers the mesh out and leaves its shadow whole ([rendering.md](rendering.md#resources-and-materials)). `PointLight` and `SpotLight` are punctual lights at their entity's position, the spot shining along its -Z. A point or spot light's `castsShadows` (default false, so older scenes load unshadowed) is saved with the scene, shown in the inspector and carried by `buildLightList` into `renderer::Light`; the renderer draws depth maps for the first lights that ask, one for a spot light and six (a cube) for a point light, up to `RendererSettings::maxLocalShadows` (8) lights per view, and the lights past that budget light without a shadow ([rendering.md](rendering.md#local-shadows)). The basic sample's lamp (a point light) and spot light cast one each. `Environment` names the equirectangular map that lights the scene and fills its background; the first entity that has one wins. `Spin` turns its entity about an axis in play mode and is the script-free behaviour M2's sample uses. `SkinnedMesh`, `Animator` and `MorphWeights` are described under [Animation](#animation), `ParticleEmitter` under [Draw list](#draw-list).

`Camera::projectionKind` selects `Perspective` (the default, infinite far plane) or `Orthographic`. Orthographic cameras use `orthoHeight` (full view height in metres, default 10) and `farPlane` (default 500 m); both kinds use `nearPlane`. These fields are reflected, saved, and available to scripts.

`Camera::exposure` (default 1.0) scales tone mapping and `Camera::bloomStrength` (0 to 1, default 0.04) mixes the blurred HDR image. Both are reflected, saved, editable in the inspector and available to scripts. `Camera::ambientOcclusion` (default false), `ambientOcclusionRadius` (metres, default 0.5) and `ambientOcclusionStrength` (default 1) request the view's screen-space ambient occlusion of its indirect light ([ADR-0039](decisions/0039-screen-space-ambient-occlusion-and-contact-shadows.md), [rendering.md](rendering.md#ambient-occlusion)); `placedCamera` carries them into `renderer::Camera`, the editor and `runtime::Game` copy them into `SceneView`, and the renderer takes the radius within 0 to 2 m and the strength within 0 to 1, a non-finite value as the default, without changing what is saved. They are additive: a scene or prefab saved before them loads with the request off and looks as it did, the scene version stays 9 and the cooked bundle carries them in its CBOR scenes unchanged; an instance that changes one of them stores that member alone (ADR-0037). The character sample's camera asks for it; no other sample does. `Environment::intensity` scales the sky and its lighting; exposure belongs to the camera. The Game view and player use their camera's values; the editor Scene view uses the defaults. `DirectionalLight::contactShadows` (off by default), `contactShadowLength` (0.2 m) and `contactShadowThickness` (0.02 m) ask for the sun's screen-space contact shadows ([rendering.md](rendering.md#contact-shadows), [ADR-0039](decisions/0039-screen-space-ambient-occlusion-and-contact-shadows.md)); they are reflected the same way, `sceneLight` carries them to the renderer for the editor's views and the player, and only the first directional light, the scene's sun, uses them. A scene saved before they existed loads with them off, so it looks as it did, and the schema stays at version 9.

The basic sample includes `scenes/orthographic.scene.json`: two shapes viewed with a 6 m orthographic camera. Open the Game view and play, or run the player with `--scene scenes/orthographic.scene.json`; click or touch a shape to tint it green using `camera.ray` and a physics raycast.

## Phases and play mode

The phases `Input`, `FixedUpdate`, `Update`, `PostUpdate` and `PreRender` are flecs phase entities in a dependency chain; systems name theirs with `kind(world.phase(...))`. Systems marked with `addToSimulation` (the spin system, physics and scripts) belong to play mode; the transform system runs always. Within a phase, systems run in the order they are declared, which is the order their owners are constructed in: the animation system before the script runtime in `Update`, and in `PostUpdate` the physics interpolation (`PhysicsInterpolate`) before the scripts' `lateUpdate` (`ScriptLateUpdate`), since the script runtime takes the physics world in its constructor. A play-mode frame is then: the fixed steps (`PhysicsStep`, then `fixedUpdate`), animation playback, `update`, the interpolation of what is drawn, `lateUpdate`, and in `PreRender` the transform system and the skin palettes; the application reads the camera after `progress` returns ([ADR-0038](decisions/0038-character-controller.md#the-frame)).

`progress(dt)` runs the phases as three flecs pipelines inside one flecs frame: `Input`, then `FixedUpdate` as many times as the accumulated time holds whole fixed steps, then `Update`, `PostUpdate` and `PreRender`. The first and last pipelines come in an edit and a play variant, the play one with the simulation systems, and `setPlaying` picks between them; the fixed pipeline runs only in play mode. `setPaused` freezes a playing world: the frame takes the edit pipelines, the fixed steps stop and the accumulator is kept, so transforms and skin palettes still follow edits and resuming carries on where it stopped; leaving play mode clears the pause. `setTimeScale` makes game time run at that multiple of the frame's: flecs' world time scale scales the delta `progress` hands every pipeline and the accumulator, so 0 stops the fixed steps and gives the other systems a zero delta while they still run, which is how a game's pause screen keeps its buttons ([scripting.md](scripting.md#game)). A negative scale is 0, starting or stopping play sets it back to 1, and a system on real time reads flecs' unscaled `delta_time_raw`, as audio does. The fixed step is `WorldDesc::fixedDelta`, 1/60 s by default, and systems in `FixedUpdate` see it as their delta time. A frame runs at most `maxFixedSteps` steps, four by default, and drops the rest of its backlog, so a long frame slows the simulation down instead of making the next frame longer still. `fixedAlpha` is the fraction of a step left in the accumulator, what physics interpolates the drawn poses by ([physics.md](physics.md#the-simulation)); starting play resets the accumulator.

`Disabled` is the engine's tag, not flecs' built-in one, so a disabled entity still appears in the hierarchy. The draw list and the simulation systems (scripts, audio, animation, `Spin`, physics) leave out the entity and everything under it, as the game UI's layout does, so a hidden part of an instance takes its children with it ([Prefabs](#prefabs)). A query asks for that with `.without<Disabled>().self().up(flecs::ChildOf)`, which flecs re-matches when an ancestor gains or loses the tag or an entity is moved under one, and code checking one entity calls `World::isDisabled`, which looks at the entity and its ancestors. Showing the entity again resumes its subtree: an animator carries on from its time, a script starts a new instance, a looping sound starts again and a body is built again where its entity is.

## Animation

Skeletal animation is part of `world` ([ADR-0010](decisions/0010-audio-and-animation.md)): the components belong to the model prefab this module builds, and a pose is the hierarchy of `Transform`s it already owns. `AnimationSystem`, constructed on a `World` and an `AssetDatabase` like the subsystems of ADR-0009, registers two systems:

1. `AnimationPlayback`, a simulation system in `Update`: every enabled `Animator` advances its `time` by `speed` while `playing`, wrapping when it loops and stopping at the end when it does not, and writes its clip's pose into the local `Transform` of the entity at each channel's path, under the entity carrying the `Animator`. The pose is written whenever there is a clip, so setting `time` on a stopped animator scrubs it.
2. `SkinPalette`, in `PreRender` after the transform system, in edit and play mode: every enabled `SkinnedMesh` gets a `SkinPose`, one matrix per joint of its skin, each the joint's world transform times its inverse bind matrix, brought back into the skinned entity's own space. `buildDrawList` hands those to the renderer, which deforms the mesh on the GPU ([rendering.md](rendering.md#skinning)).

Both resolve their targets by path: the joints of a skin under the nearest ancestor of the skinned entity where all of them resolve, which for a model instance is its root, and a clip's channels under the `Animator`'s own entity. `World::findByPath` walks names; a binding is cached per entity and rebuilt when the clip or skin changes, when its revision does because the file was re-imported, or when a bound entity is destroyed. A path that resolves nowhere is reported once and moves nothing; a skin whose joints are not all found leaves the mesh in its bind pose. Both systems ask for their skin or clip with the request form ([assets.md](assets.md#database)), since they ask every frame and a model is placed before its file is imported: until the file arrives, a skinned mesh has no `SkinPose` and an `Animator` does not advance.

`loadModelPrefab` is what puts them there: a node with a skin gets a `SkinnedMesh`, and a model with clips gets an `Animator` on its root with the first of them, playing and looping. ADR-0023 adds blending to the playback. An `Animator` also holds `layers`, more clips playing at once with their own `time`, `speed`, `weight` and `fadeRate`; each target's pose is the weight-normalised blend of every layer with a positive weight that has a channel for it (translations and scales mixed linearly, rotations by a normalised lerp along the shorter arc), and a target no such layer reaches keeps the pose it last had. Assigning `clip` while `fade` is above zero is a crossfade: the system remembers what the animator played last frame, and the clip it was replaced from carries on at its own speed, losing weight until it is gone, while the new one gains it over `fade` seconds. `rootMotion` takes the translation of the root bone (`rootBone`, or the clip's translation channel nearest the root) out of the pose, keeping it at its first-frame value, and moves the animator's entity by what it moved each frame, across loops too; only translation is extracted. `AnimationSystem::events()` returns the clip events the animators crossed in the last `Update`, from every layer above a weight of 0.05, ordered by entity; `scripting` delivers them as `onAnimationEvent`. The system is constructed before the script runtime, so its events reach scripts in the frame they happen.

[ADR-0038](decisions/0038-character-controller.md#animation-weights-and-synchronisation) makes the weights explicit for blended locomotion:

- `Animator::weight` (default 1, taken as 0 to 1) scales the animator's own clip: its blend weight is `weight` times the crossfade's ramp, which is 1 except while a crossfade raises it. A weight of exactly 0 contributes nothing, so pure idle, walk or run is one weight at 1 and the others at 0, and any weights that do not all vanish are a mix; the blend normalises, so they need not sum to 1. With the default, a scene animates as it did before.
- `AnimationLayer::sync` (default false) makes a layer follow the animator's phase: after the clip advances, the layer's `time` is the clip's `time / duration` times the layer's duration, and its own `speed`, `playing` and `loop` are ignored. It therefore holds, runs backwards, wraps or sits at its own end when the clip does. While the animator has no clip, its file has not arrived, or it lasts zero seconds, the layer holds its time (still posed there) and crosses nothing; when the clip is back the layer takes its phase. Assigning `clip` keeps `time`, so a new clip's phase is the old time over the new duration; a script that switches gaits and wants the phase kept sets `time` to the old phase times the new duration in the same `set`. A time outside the clip, which a shorter new clip or a script leaves, is brought into it (wrapped when the clip loops, clamped when it does not) before the frame advances it.
- Events: a synchronised layer crosses the interval the animator's clip crossed this frame, mapped onto its own duration with the clip's direction and wrap, and fires when its weight is at least 0.05, like any layer. The interval starts from the animator's `time` as the frame found it, so a `time` a script assigned crosses nothing on the way there: resetting the phase fires no footsteps. Synchronising phases does not align gaits; the clips' foot contacts must fall at the same phases.
- Transition state is not in `layers`. The clips a crossfade leaves are kept by `AnimationSystem` per entity, start at the blend weight they had (`weight` times the ramp) and fade to zero over `fade` seconds, unsynchronised; a crossfade that interrupts another adds the interrupted clip at the weight it had reached, so the pose does not jump. `layers` holds only what the scene or a script put there (a layer with a negative `fadeRate` still loses weight and is removed at zero).

A locomotion script owns its `layers` and may write them whole every frame without cutting a crossfade short, for example the walk and run layers synchronised to an idle or walk primary:

```lua
self.entity:set("Animator", {
  weight = idleWeight,
  layers = {
    { clip = self.walk, weight = walkWeight, sync = true },
    { clip = self.run, weight = runWeight, sync = true },
  },
})
```

A synchronised layer's `time` is recomputed every frame, so writing it does nothing; the times worth keeping are the animator's own (left out of the table, it stays where playback put it) and those of unsynchronised layers, which a script keeps by reading the component, changing the weights and setting it back ([scripting.md](scripting.md)). Compute the weights in `fixedUpdate` from `physics.character` and the same frame's playback applies them; in `update` they apply one frame later.

`MorphWeights` holds the weights of the morph targets of the entity's mesh; `loadModelPrefab` adds it, at the file's weights, to a node whose mesh has targets, a `Weights` channel of a clip blends into it like the other paths, and `buildDrawList` hands the weights to the renderer in a vector of its own beside the joints, the draw items naming their range and the entity as the instance.

Because the pose is ordinary `Transform`s, play-mode snapshots undo it, physics sees animated kinematic bodies move, and the joints are entities in the hierarchy panel.

## Hierarchy

Hierarchy is flecs `ChildOf`. `roots` and `children` return entities in creation order (`SiblingOrder`, a counter in `World`), since flecs table order changes as components are added, ids are recycled, and a panel needs a stable order; a scene loaded in file order therefore lists in file order. `setSiblingIndex` moves an entity among its siblings by renumbering them, and `siblingIndex` reads its position; since a save writes the tree in sibling order, the file keeps the new order with no field of its own. An instance's copied children take their order from their sources in the prefab, at every depth, so the hierarchy is the same after every load, play snapshot and tab switch. `destroyEntity` deletes the subtree. `clearScene` deletes every scene root and keeps prefabs and editor-only entities.

The low 32 bits of a flecs id are the pick id the id pass writes ([rendering.md](rendering.md#the-renderer-module-today)); `fromPickId` resolves it back to the live entity.

## Prefabs

A prefab is a flecs prefab entity with an `Identity`, loaded from a `.prefab.json` file, and an instance is an entity that `IsA` it. Loading a prefab file (`loadPrefabFile`, `loadPrefabFiles`, or a `PrefabDocument` with its `file` set) puts a `PrefabFile` holding the path and the file's write time when it was read (`readPrefabDocument` takes it before reading) on the prefab's root, which is how the editor's asset browser lists prefabs; it is neither inherited nor serialized, and a model's prefab or one loaded from memory has none. Registered components are inherited (`OnInstantiate, Inherit`): an instance shares the prefab's values until it writes a component, which overrides it. `Identity` and `WorldTransform` are never inherited; `instantiate` gives the instance the identity it is asked for (a fresh one by default), its own name and transform, and gives the instantiated descendants world transforms of their own.

Prefabs nest to any depth ([ADR-0028](decisions/0028-nested-scene-instances.md)): a prefab file may place instances of other prefabs, and an instance of it brings them along. flecs copies a prefab's descendants into an instance as plain entities that own every component and keep no link back, so the world keeps the link itself. `World::makePrefab`, which every way of building a prefab ends with, tags the whole subtree as flecs prefabs and gives each entity a `PrefabOrigin` holding its own identity. flecs copies it, and `instantiate` turns it into the copy's `PrefabSource` and gives the copy the identity `World::instancedIdentity(instance, source)`, a `Uuid::derive` of the two. The same instance identity therefore gives the same descendants on every load, in the editor's undo and in a script's `instantiate`, and two instances give different ones. Inside a prefab of prefabs the inner instance's copies are prefab entities with derived identities of their own, and an instance of the outer prefab derives from those. `World::instanceOf` names the instance a descendant's identity derives from and `World::sourceOf` the prefab entity it was copied from. `World::applyTarget` follows those links on, through `sourceOf` and an instance root's `prefabOf`, to the prefab entity an instance's change to one member or component would be written to: the deepest prefab with a file whose value reaches the instance unchanged ([editor.md](editor.md#applying-to-a-prefab)). `world::documentsPlacing` names the scene and prefab documents that place a prefab, directly or through other prefabs among them. Neither component is serialized. `World::makeLocal` turns an instance into ordinary entities with the same identities: the instance, and every instance copied inside it, takes its own copy of each component it inherits and drops its `IsA`, and the descendants drop their `PrefabSource`. The instances inside go local too, since their parts' links point into the outer prefab, and a part without a link under an instance would be loaded twice, once from the prefab and once as an added child.

A scene stores an instance as its prefab's UUID plus the components it owns, then one `instanced` entry for each descendant that differs from the prefab entity it came from ([Scenes](#scenes)). Since flecs copied the descendants, the difference is found by comparing reflected values (`World::differs`, which the inspector's marking uses too). A changed component is stored as the members that differ from the prefab's ([ADR-0037](decisions/0037-per-field-instance-overrides.md)), on an instance's own components and its descendants' alike, except the instance's `Transform`, which places it and is stored whole; every member the file leaves out, and every component the instance did not change, comes from the prefab each time the scene loads. A source child is hidden with `Disabled` rather than deleted, which the comparison stores like any other added component, and a child added under a descendant is an ordinary entity whose parent is the descendant's derived identity. Only prefabs can be placed, never a scene file, whose many roots have no single entity to be the instance.

The children of an instance load as its prefab's copies in the prefab's order, then the added children in file order. A scene that says otherwise stores an `order` ([ADR-0032](decisions/0032-instance-child-order.md)), written by `saveScene` only when the live order differs from `World::defaultChildren`, so an unchanged instance saves as before.

`loadPrefabs` loads a set of prefab documents in dependency order, so the files can come in any order, and `loadPrefabFiles` reads files into one. The editor and the player both load the models' prefabs first, since a model's prefab references nothing, and then every `.prefab.json` through it. A prefab that contains itself, directly or through others, is refused with the chain named, and the others load.

## Scenes

Scenes and prefabs share one JSON format ([assets.md](assets.md#scene-file)), an engine-owned envelope around flecs' JSON for each component value:

```json
{
  "version": 9,
  "entities": [
    {
      "uuid": "6f1c...", "name": "Box", "parent": "a3e9...",
      "components": {
        "Transform": { "position": [0, 0.5, 0], "rotation": [0, 0, 0, 1], "scale": [1, 1, 1] },
        "MeshRenderer": { "mesh": "a464...", "color": [0.9, 0.35, 0.25, 1], "visible": true },
        "Static": null
      }
    },
    { "uuid": "b7d2...", "name": "Crate 1", "prefab": "c0ff...", "components": { "Transform": { "position": [4, 0, 0] } } },
    { "uuid": "41a8...", "instanced": true, "name": "Lid open", "components": { "Transform": { "rotation": [0.7, 0, 0, 0.7] } }, "removed": ["Static"] },
    { "uuid": "9e02...", "instanced": true, "components": {
        "PointLight": { "intensity": 4 },
        "Scripts": { "slots": { "5a0c...": [ { "properties": { "speed": 6, "target": null, "$removed": ["range"] } } ] } } } }
  ]
}
```

A `vec2`, `vec3`, `vec4` or `quat` member is an array of its components in `x, y, z, w` order ([ADR-0029](decisions/0029-compact-scene-files.md)); the quaternion keeps that order, glTF's, whatever order glm stores it in. `World::valueToJson` and `World::componentFromJson` convert at the JSON boundary by walking the component's reflected members, so undo copies and the recovery file use arrays too, while flecs reflection, the inspector and Lua keep the named members. A script's property values inside `Scripts` are the script's own JSON and keep their `{x, y, z}` and `{r, g, b, a}` objects. `world::sceneText` writes a document with two-space indentation and every array of numbers on one line, so moving an entity changes one line; `tools/scene_json.py` does the same for the scene generators.

Entities are written parents first, tags as `null`, and editor-only entities not at all. A component of an instance, or of an instance's descendant, that its source also has is a patch (version 9, [ADR-0037](decisions/0037-per-field-instance-overrides.md)): only the members whose value differs, recursing into nested objects. `world::componentPatch` writes it and `world::mergePatch` applies it on load onto the source's current value, so a member the file leaves out follows the prefab. A number, string, boolean, `null` or array is one value written whole, a vector or a repeated member such as `Animator.layers` included, and so is each value inside embedded JSON such as a script's property, so a patch never merges onto half of another value. `null` is a value (a cleared property), never "follow the prefab"; a member of an embedded JSON object the source has and the instance lacks, a script property reset to its default while the prefab sets it, is listed in that object's `"$removed"`. A repeated member registered with `World::matchBy` pairs its elements by one of their members: `Scripts.slots` by `script`. While the instance runs the same scripts in the same order as its source, `slots` is an object keyed by script identity, each key holding one patch per slot running that script in order, `{}` for an unchanged one ahead of a changed one; loading applies the n-th patch for a script to the n-th slot running it in the prefab's current list, so a prefab that reorders or adds slots is followed, and a patch whose slot the prefab lost is skipped with a warning naming the entity and the script. An instance that added, removed, reordered or re-pointed a slot writes `slots` whole as an array, which replaces the prefab's. A component the source lacks has nothing to merge onto and is written whole, as is everything of an ordinary entity. An `instanced` entry (version 4) holds what a prefab instance's descendant changed, addressed by its derived identity: a `name` if it was renamed, the `components` whose value differs from its source's or that its source lacks, and a `removed` list of its source's components it no longer has. It follows its instance in the file, and one whose entity is no longer in the prefab is skipped with a warning naming its identity and is gone after the next save. Loading creates every entity, then resolves parents, so the order in the file does not matter; a load that fails part way removes what it created and reports why, with the UUID of a missing prefab or parent. A prefab an instance refers to has to be loaded first, which the editor and the player do for every `.prefab.json` in the project ([Prefabs](#prefabs)). An `order` (version 8) is an array of the identities of an entity's children, source and added together, in sibling order. It sits on an instance's entry or on the `instanced` entry of a descendant, which an unchanged descendant gets with an empty `components`. After the parents are resolved, each `order` is applied once: an identity that is not a child is skipped with a warning (a source child the prefab dropped), a repeated one counts at its first position, and a child the list leaves out, such as one the prefab gained, goes right after the child that precedes it in the default order, or first when it has none. Unknown component names are logged and skipped.

`version` is the schema version, independent of the engine version ([conventions.md](conventions.md#versioning)). A newer version than the engine knows is refused; older ones are migrated on load, oldest first, logging the file and both versions, and never written back. Version 2 references meshes by asset identity; version 1 named a primitive (`"primitive": "Box"`), which the migration turns into the built-in mesh of the same shape. Version 3 replaces the `Script` component by `Scripts`, a list of slots ([ADR-0022](decisions/0022-gameplay-events-and-script-properties.md)); the migration turns each `Script` into a one-slot `Scripts` with no changed properties. Version 4 adds the `instanced` entries; a version 3 file has none and loads unchanged. Version 9 stores an instance's components as patches; an older file stores them whole, and its values replace the prefab's as they did (a merge would bring back a property the instance had reset to the script's default), until a save writes them as patches with the same values. Version 8 adds `order` to instance entries; an older file has none and loads unchanged. Version 7 adds camera projection kind, orthographic height and far plane; older cameras load as perspective with height 10 m and far plane 500 m. Version 6 moves exposure from `Environment` to `Camera` and adds camera bloom strength. Loading an older file removes every environment exposure and copies the first environment's non-default exposure into every camera lacking its own; a camera without an environment keeps exposure 1.0. This applies to prefabs too. Version 5 writes vectors as arrays. Only reflection knows which members are vectors, so this one is not a step on the raw JSON: `loadEntities` tells the component reader the file's own version, and a file older than 5 may give a vector as an `{x, y, z}` object. In a version 5 file an object, or an array of the wrong length, where a vector belongs is logged as malformed, naming the component and member, and the member keeps its value while the rest of the component loads.

A glTF file is a prefab too: `loadModelPrefab` builds one from the file's `assets::Model`, the root under the model's identity and name, every node a prefab child with its transform and, for a node with geometry, a `MeshRenderer` of its mesh, for a node with a camera a `Camera` with its projection kind, field of view or orthographic height, and clipping planes (so a scene exported with its framing camera plays through it, `sceneCamera` taking the first camera there is), for a node with a punctual light the `DirectionalLight`, `PointLight` or `SpotLight` of its type, unshadowed, with identities derived from the model's and the node's name path (`Set/Lamp`; equal siblings take `Lamp#1`, `Lamp#2`, and an unnamed node is `node<index>`) so an instance saves and loads the same way after a re-import, and an override stays on its node when the file gains or loses others. Renaming a node, or reordering equal siblings, moves its overrides; a scene saved under the old index scheme loses its model-instance overrides with the loader's usual warning (ADR-0030). The editor loads one for every model in the project alongside the `.prefab.json` files. The hierarchy is all a prefab needs, and it is all the database reads to give one ([assets.md](assets.md#database)), so the instances are whole entities from the frame the scene loads and their meshes draw once the file has imported.

## Draw list

`buildDrawList` fills `renderer::DrawItem`s from every entity with a `WorldTransform` and a visible, enabled `MeshRenderer`: one item per submesh (carrying `previousTransform`, the entity's `PreviousWorldTransform`), the mesh and materials resolved through the `AssetDatabase` every frame so a re-imported asset shows on the next one, and an entity whose mesh is missing or failed to import draws nothing. The mesh is resolved with `requestMesh`, so one that is not in memory yet imports on the job system and draws a frame or two later rather than stalling the frame that asks ([assets.md](assets.md#database)). An entity with a `SkinnedMesh` and a `SkinPose` appends its joint matrices to the list's `joints`, and its items carry that range and the entity as the skinned instance. `buildLightList` collects the enabled point and spot lights; `sceneLight` is the first directional light, shining along its entity's -Z; `sceneCamera` the first camera, placed by its entity's world transform, and `buildCameraList` every enabled one in the same order, for the editor's camera gizmos; `sceneEnvironment` the first `Environment` whose map loads. The editor draws through its own camera and uses the scene's lights and environment; the player uses the camera too. Two more forms serve the Assets panel's thumbnails ([editor.md](editor.md#rendered-pictures)): `buildDrawList(world, assets, root, ...)` lists the items under one entity, a prefab's root for one, reading the tree as it is, with the root at the origin, no pose (a skinned mesh is drawn in its bind pose) and `Disabled` parts left out, and `buildDrawList(assets, mesh, ...)` lists one mesh by identity with its own materials.

`ParticleEmitter` is the authored half of the renderer's GPU particles ([rendering.md](rendering.md#particles), [ADR-0023](decisions/0023-animation-blending-morph-targets-and-particles.md)): its rate, burst, lifetime and speed ranges, cone, gravity, drag, size and colour over a particle's life, an optional texture, alpha or additive blending, world or local space and a seed. `buildParticleList` turns every enabled one with a world transform into a `renderer::ParticleEmitterItem` keyed by its entity's id; `simulate` is on in play mode while the emitter's `playing` is, and off in edit mode, where the editor turns it on for the selected emitters only. Colours are linear and may exceed 1, so an additive emitter can glow past what a surface does.

## Debugging

`WorldDesc::explorer` imports the flecs statistics module and serves the REST API, so the [flecs explorer](https://www.flecs.dev/explorer) shows the live world. The editor turns it on in Debug builds.
