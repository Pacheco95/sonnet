# Overlay ports

Patched copies of vcpkg ports, picked up through `vcpkg-configuration.json` ahead of the registry ([ADR-0004](../docs/decisions/0004-vcpkg-first.md)). Each directory says what was changed and why, so the patch can be dropped once upstream carries it.

| Port | Change |
|---|---|
| `imgui` | Dear ImGui 1.93.0, from the upstream tags `v1.93.0` and `v1.93.0-docking` (the docking branch is the one the editor builds, [ADR-0036](../docs/decisions/0036-dear-imgui-stays-the-editor-ui.md); [moving the pin](#moving-the-dear-imgui-pin) says how the version changes). Three changes to the registry port, copied at baseline `a1cae005`, which carried 1.92.9. The `sdl3-binding`, `sdl3-renderer-binding` and `sdlgpu3-binding` features depend on `sdl3` with its default features off: the registry port depends on `sdl3` with defaults on, which on Linux re-enables `ibus`, and through it `dbus[systemd]` and `libsystemd`, for every consumer, even one that disabled them at the top level. The `vulkan-binding` feature depends on `vulkan-headers` only and compiles the backend with `IMGUI_IMPL_VULKAN_NO_PROTOTYPES`: the registry port links the `vulkan-loader` port, which put a second loader into the process ahead of the one SDL loads, and vcpkg's loader is built without X11 or Wayland surface support, so the editor could not open a window outside an environment that put the SDK's loader first ([ADR-0006](../docs/decisions/0006-vulkan-object-ownership.md)). `viewport-images-start-undefined.patch`, applied to the docking variant only, since multi-viewport is not in `master`'s backend, removes the Vulkan backend's creation-time transition of a secondary viewport's swapchain images to `PRESENT_SRC_KHR`, submitted before any image is acquired, which the validation layer reports as `UNASSIGNED-non-acquired-swapchain-image-used` every time such a window is resized; the per-frame barrier now starts from `UNDEFINED`, which every viewport frame allows since it clears or discards the image. |
| `sdl3` | The X11 extensions an editor needs are enabled: XInput2 (relative mouse mode and raw motion), Xcursor, Xfixes, XRandR and XScrnSaver. The registry port turns every X11 extension off so host libraries cannot change SDL's capabilities, which leaves `SDL_SetWindowRelativeMouseMode` unsupported on X11. SDL loads these libraries at run time; the build needs their headers (`libxi-dev`, `libxcursor-dev`, `libxrandr-dev`, `libxss-dev` on Debian and Ubuntu) and stops with a message naming the missing one. The CI runners install them. For Android triplets the port also installs SDL's Java glue, `android-project/app/src/main/java/org/libsdl/app/*.java`, into `share/sdl3/android-java/`, which the registry port leaves out, and turns off `SDL_ANDROID_JAR`, since SDL builds `SDL3.jar` only when it happens to find a JDK and the Android SDK in the environment; `cmake/SonnetAndroid.cmake` compiles it into the APK, so the Java side always matches the native library it was built with ([ADR-0018](../docs/decisions/0018-mobile-export.md)). Desktop triplets install the same files as before. Copied from the registry at baseline `a1cae005` and bumped two port-versions. |
| `nlohmann-json` | `byte-swap-unreachable-code.patch` chains `binary_reader::byte_swap`'s `if constexpr` branches with `else`. Where the standard library has `std::byteswap`, the byte loop after them stays in every instantiation that returns early, and MSVC reports it as unreachable code (C4702) while generating code for the caller's translation unit, where `/external:W0` does not reach, so `Bundle.cpp`'s CBOR read failed the Windows build under `/WX`. Copied from the registry at baseline `a1cae005` and bumped one port-version. |
| `ktx` | KTX-Software 5.0.0-rc2, a release candidate, because it is the first release that encodes and transcodes Binomial's UASTC HDR 4x4 (`KTX_BASIS_CODEC_UASTC_HDR_4x4`, transcoded to BC6H or ASTC HDR), which the HDR environment cooking of [ADR-0024](../docs/decisions/0024-temporal-anti-aliasing-and-occlusion-culling.md) needs; 4.4.2, the latest stable release, has neither. Move to 5.0.0 when it ships. Six patches, re-derived for 5.0.0's restructured build (the sources moved to `lib/src`, Basis Universal to `external/basis_universal`). `0001-Use-vcpkg-zstd.patch` builds and links the registry's zstd instead of the vendored copy and includes `<zstd.h>` in Basis Universal's sources. `0004-quirks.patch` drops MSVC's `/Gz` for Debug and keeps the utility library out of `all`. `0005-no-vendored-libs.patch` takes `fmt` and `cxxopts` from the registry for the tools. `0006-fix-ios-install.patch` stops the Apple locked-OS builds from making a framework of the static library. `0007-clang-flags-per-language.patch`: KTX-Software decides its Clang-only floating-point flag (`-ffp-model=precise`) from the C++ compiler id and applies it to C sources too, so a GNU-style C compiler paired with Clang for C++ (`cc` from GCC next to a locally built `c++` from LLVM) fails on every C file; the patch decides per language with `COMPILE_LANG_AND_ID`. `0008-fix-stream-leak-on-short-read.patch`: `ktxTexture2_constructFromStream` leaks the stream it was handed (a heap allocation, for a memory stream) when the initial header read fails, because that only happens before `ktxTexture_constructFromStream` takes ownership of it; reading a file too short to hold a KTX2 header leaked 40 bytes under LeakSanitizer. Dropped with the upgrade: `0003-mkversion.patch`, `0009-job-pool-kill-flag-under-mutex.patch` (Basis Universal sets the flag under the mutex now; [issue #24](https://github.com/Pacheco95/sonnet/issues/24)) and `ktxread-libtool.diff` (5.0.0 merges the static libraries through `add_lib_dependencies`). The `ktxBasisParams::uastc` flag is `codec` in 5.0.0. Copied from the registry at baseline `a1cae005` and bumped to its own version. |
| `lua` | On Windows with dynamic linkage the C++ build (`lua-cpp`) never exported the `luaopen_*` functions: `luaconf.h` defines `LUAMOD_API` as plain `extern "C"` for C++, without the `dllexport` that `LUA_API` carries, so sol2's `open_libraries` failed to link in every binary using scripting. The portfile adds `LUA_API` to that definition on Windows dynamic builds only. Copied from the registry at baseline `a1cae005` and bumped one port-version. |

## Moving the Dear ImGui pin

[ADR-0036](../docs/decisions/0036-dear-imgui-stays-the-editor-ui.md) makes a new Dear ImGui release a regular task, taken against the release's breaking changes. The `imgui` port is pinned to one upstream release, named in `vcpkg.json` and expanded by the portfile into the tags `v<version>` and `v<version>-docking`. Upstream also tags patch releases with a letter (`v1.92.9b`); vcpkg versions have no letter, so a pin on one needs the portfile to name the tag by hand.

1. Read the docking branch's open issues for regressions of the release, and take its first patch release if one has shipped.
2. Read the release's `BACKWARD COMPATIBILITY` section in `imgui.cpp` (`docs/CHANGELOG.txt` has the same list under `Breaking Changes`) against what the editor calls. Search `modules` and `apps` for the names it lists. For drawing, that is every `ImDrawList` call: `grep -rnE "(->|\.)(Add[A-Za-z]+|Path[A-Za-z]+)\(" modules/editor modules/ui`. Pixel offsets and stroke placement change what a capture shows, not whether the code compiles. `ImGui_ImplVulkan_LoadFunctions` keeps its signature across releases so far; check it, since `ImGuiLayer` hands it the loader's entry point.
3. Take a baseline before changing anything: build the current pin and capture with the editor's own flags (`--screenshot-window`, and `--select` on a transform gizmo and on a GUI element), once with the Assets panel in its list view and once in its grid view, with a private `XDG_DATA_HOME` so the capture does not read or rewrite the real `layout.ini`. The hierarchy's drop indicator needs a real drag and no flag shows it.
4. Move the pin: set `version` in `vcpkg.json` (leave out `port-version`), download both tarballs, compute their SHA-512 (`sha512sum`), and put them in the portfile with `imgui_test_engine`'s for the `test-engine` feature. Re-derive `viewport-images-start-undefined.patch` against the new docking tag: `patch -p1 --dry-run` on an unpacked tarball, then regenerate the file with `diff -u` so its line numbers are right.
5. Adapt the editor to the breaking changes, a commit of its own, and touch every translation unit that includes `imgui.h`: the headers come from `vcpkg_installed` as system headers, which the build's dependency files do not follow, so an object compiled against the old header links against the new library and fails or misbehaves.
6. Validate: `ctest --preset linux-debug -R "ui_tests|editor_tests"` on Lavapipe (`VK_DRIVER_FILES` set to its ICD file) with the validation layer silent, the same captures as in step 3, compared side by side, and a check that the transform gizmo's drawn handles still line up with the hit test's maths. Changes the release notes describe are accepted in the pull request; others are bugs. Every CI job that builds the editor takes the new pin from the same files, so no workflow needs editing.
7. Undocking a panel into its own window, and resizing that window, are the paths the patch changes. They need real input: do them on a desktop with the validation layer on and check the log for `UNASSIGNED-non-acquired-swapchain-image-used`.

## Ports with no registry counterpart

Not patches of a registry port, so they carry no baseline and no port-version: each is an original portfile for something the registry does not package.

| Port | What it installs |
|---|---|
| `moltenvk` | Khronos's MoltenVK, which has no vcpkg registry port. The registry's own `vulkan-loader` and `vulkan-memory-allocator-hpp` still route through the `vulkan` stub for their `find_package(Vulkan)`, so this port only carries the static library the player links directly: `vcpkg_download_distfile` pulls the pinned `MoltenVK-ios.tar` or `MoltenVK-macos.tar` release archive (SHA-512 pinned in the portfile) for `arm64-ios` or an `osx` triplet, installs `MoltenVK/static/MoltenVK.xcframework/<slice>/libMoltenVK.a` unmodified, and writes a hand-authored `unofficial-moltenvk-config.cmake` exposing `unofficial::moltenvk::moltenvk` with the Apple frameworks it needs as `INTERFACE_LINK_LIBRARIES` ([ADR-0018](../docs/decisions/0018-mobile-export.md#builds)). No headers are installed: SDL finds `vkGetInstanceProcAddr` in the process before it looks for a Vulkan loader on disk, so nothing links against MoltenVK's own copy of the Vulkan headers. `apps/player/CMakeLists.txt` links the target on Apple platforms only, with `-Wl,-u,_vkGetInstanceProcAddr` so the linker keeps the archive's objects despite nothing referencing that symbol directly. MoltenVK is deprecated upstream; the port stays pinned to 1.4.2 and iOS has no replacement ([ADR-0035](../docs/decisions/0035-moltenvk-stays-pinned.md)). |
